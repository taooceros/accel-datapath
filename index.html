叠加实测

一个确定性的排队模型，用来对照假说和实测，不是 DSA 的真实实现。每轮提交的 store（MOVDIR64B 加上额外的普通 store）一起占用 store buffer；写出按“首个延迟 + 固定间隔”串行进行；设备端是 WQ（满了丢弃）→ engine 侧槽位 → E 个 engine。“CPU 提交”决定异步程度：同步 = 等上一个完成才交下一个；窗口 W = 最多 W 个在途（tonic 的 async encode 就是把 W 从 1 提到多个）；不等 = 一直交。

CPU 在等空位
时间线：谁在什么时候干活

每一行是一个 descriptor 的一生，从左到右：红 = CPU 等 store buffer 空位，灰 = 在 core 里排队写出，黄 = 在 WQ 里等，浅灰 = 等 engine，彩色 = 在某个 engine 上执行（颜色 = 哪个 engine）。并行：竖着看任一时刻，E0–E3 有几条同时亮着，就是几个 engine 在并行。异步：CPU 行变绿以后设备还在干活，这段时间 CPU 可以去做别的事；同步提交时 CPU 行大部分是黄色（在等完成）。鼠标移上去看细节。

每次 submit 测到的时间
x：第几个 submit；y：rdtscp 区间（ns）。线 = 模型，点 = 实测中位数。
最终被接受的 descriptor 数
x：提交总数；y：最终完成数。点 = 实测（noop sentinel 排空后的计数）。
knee 位置 vs 提交间隔
模型 knee = 第一次要等空位的 submit；实测 knee = 第一个中位数 ≥ 80 ns 的 K，竖线是 K 网格给出的区间。

和 hw-eval 旧数据的差别：prefill 加了 gap 以后，模型预测 knee 之后只卡“写出间隔 − 提交间隔”，旧的 X2 实测被计时的那次始终卡约 105 ns。干净计时下模型成立（gap 25 ns 时 63 ns）；旧数据多半是计时窗口里多了一个 store [推断]（Q8）。
