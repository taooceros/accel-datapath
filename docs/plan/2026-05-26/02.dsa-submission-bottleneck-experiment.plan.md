# DSA submission bottleneck experiment plan

## Goal

Localize why dedicated-WQ DSA submission looks cheap in an isolated `movdir64b` burst but much slower in sustained batch-size-1/no-batch execution.

The plan should answer one operational question:

> When the software keeps DSA work outstanding, where do the missing cycles first appear: WQ admission, hardware execution/completion visibility, CPU completion handling, host-fabric traffic, or benchmark correctness?

This is the implementation-facing experiment plan behind the presentation. The presentation explains the story; this document defines what to run, what must be added to `hw-eval`, and how to interpret the results.

## Current evidence

Known measurements and constraints:

- `submit_only_unloaded` on dedicated `/dev/dsa/wq0.0` reached 20 cycles per submit at burst 2 and stayed cheap through moderate bursts.
- The same unloaded study showed a knee around 64--128 submissions.
- `submit_only_pressure_ramp` and `submit_only_mfence` reached hundreds of cycles per submit under backpressure or serialization.
- Direct completion-visible latency from the current setup is sub-microsecond: NOOP around 379 ns, 64 B memmove around 575 ns, and 4 KiB memmove around 921 ns.
- Prior batch-size-1/no-batch async/raw throughput for small messages was around 8--10 Mops/s, far below a naive ceiling computed from only the 20-cycle submit number.
- `submit_admission_distinct` submitted unique completion-bearing NOOP descriptors without software in-flight gating. On this WQ it completed every descriptor up to burst 1024 while submit-loop time increased, supporting backpressured/admission-paced behavior rather than silent loss for this platform.

The working hypothesis is not “`movdir64b` is slow.” The working hypothesis is:

> `movdir64b` is cheap while the host/device admission path has credits. Sustained batch-size-1 throughput becomes limited when the closed loop exhausts a credit domain or spends too much CPU time discovering/reusing completions.

## Resource model

Treat the DSA path as a closed loop with separate resources:

1. CPU issues a 64-byte `movdir64b` store to the WQ portal.
2. Host fabric / WQ admission accepts or backpressures the descriptor.
3. The DSA engine executes the NOOP or memmove.
4. DSA writes the completion record.
5. CPU polling observes completion visibility.
6. CPU resets/reuses descriptor, completion, and payload slots.
7. CPU resubmits.

The timestamps should preserve this boundary:

- `t0`: immediately before the first measured submit.
- `t1`: immediately after the final measured submit instruction returns.
- `tc`: marker or first-old completion becomes CPU-visible.
- `t2`: all target completions for the sample are observed.

Primary derived metrics:

- `submit_cycles = t1 - t0`
- `submit_ns = tsc_to_ns(submit_cycles)`
- `completion_visible_cycles = t2 - t1`
- `marker_overlap = tc < t1`
- `completed`, `missing`, and `errors` for any over-depth/no-tracking push
- `polls_per_completion`
- `reset_to_submit_cycles`
- `ops_per_sec` for sustained fixed-window loops

Use TSC or RDPMC for cycle-shape studies. Wall time remains a sanity check. Avoid per-submit `rdtscp`; it would dominate the thing being measured.

## Run invariants

Keep these fixed unless an experiment explicitly varies them:

- Use release `hw-eval` only.
- Run hardware commands through `launch`, not by executing the binary directly.
- Use a dedicated DSA WQ unless the experiment is explicitly a shared-WQ follow-up.
- Record WQ sysfs state with each run:
  - device path;
  - WQ `mode`;
  - WQ `size`;
  - NUMA node if available.
- Pin the benchmark thread, normally `--pin-core 0`.
- Keep operation size, WQ, core, NUMA placement, and timer source constant inside a curve.
- Use unique completion records whenever counting loss or missing completions.
- Do not reuse descriptors, completion records, source buffers, or destination buffers before their completion is observed in any correctness-sensitive run.
- Separate batch size from concurrency/window:
  - these experiments use one logical operation per MMIO submission;
  - `window`, `occupancy`, or `K` means outstanding logical operations, not DSA `BATCH` descriptor size.

## Existing runnable baselines

These baselines should be run before adding new runner modes so every new result has a comparable reference.

### Baseline A: submit-only unloaded, pressure, and fence modes

Purpose: preserve the known submit-admission reference and confirm the platform is in the same regime.

Command:

```bash
cargo build --release -p hw-eval

launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-only \
  --submit-mode all \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 3000 \
  --sizes 64 \
  --submit-bursts 1,2,4,8,16,32,64,96,112,120,124,126,127,128,129,130,132,136,144,160,192,256 \
  --pin-core 0
```

Record:

- median empty calibration for every timer source;
- median submit cycles/ns per burst for `submit_only_unloaded`;
- pressure-ramp median for the same burst list;
- `mfence` median for the same burst list;
- first burst where unloaded cost leaves the cheap regime.

Interpretation:

- unloaded cheap through moderate bursts means posted/admitted submission is cheap;
- a sharp bend around WQ depth points to WQ/device admission;
- pressure-ramp and `mfence` hundreds-cycle rows are backpressure/serialization costs, not isolated submit costs.

### Baseline B: distinct-descriptor admission probe

Purpose: confirm over-depth dedicated-WQ behavior before trusting any no-tracking or blind-push experiment.

Command:

```bash
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-admission \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 100 \
  --sizes 64 \
  --submit-bursts 64,96,112,120,124,126,127,128,129,130,132,136,144,160,192,256,512,1024 \
  --pin-core 0
```

Record:

- submitted count;
- completed count;
- missing count;
- software/hardware error count;
- submit TSC ticks and submit ns.

Interpretation:

- `completed == submitted`, `missing == 0`, and submit time increasing means over-depth `movdir64b` is admission-paced/backpressured on this platform.
- Any missing completion or error means subsequent throughput numbers require strict in-flight tracking and cannot use blind push loops as performance evidence.

## New experiment 1: occupancy-conditioned one-submit latency

Status: requires a new `hw-eval` runner mode. Existing `submit_admission_distinct` is related but not identical: it times a whole blind burst, not one extra submit conditioned on a controlled prefill occupancy.

Purpose: directly test whether the latency of one extra submit is a function of WQ occupancy.

Procedure per sample:

1. Reset `K + 1` unique completion records.
2. Submit `K` completion-bearing NOOP descriptors to prefill occupancy.
3. Do not poll during the prefill.
4. Read `t0`.
5. Submit one additional completion-bearing NOOP descriptor.
6. Read `t1`.
7. Poll until the first prefilled descriptor completes; record `tc_first_old`.
8. Drain all remaining completions.
9. Record `K`, `t1 - t0`, `tc_first_old - t0`, completed count, missing count, and errors.

Sweep:

```text
K = 0, 32, 64, 96, 112, 120, 124, 126, 127, 128, 129, 132, 136, 144, 160
```

Run variants:

- NOOP first.
- 64 B memmove after NOOP if NOOP shows a useful knee.
- 4 KiB memmove only if the 64 B curve suggests payload traffic changes the knee.

Expected output row fields:

- benchmark name, e.g. `submit_occupancy_one_extra`;
- operation class;
- `k_prefill`;
- completed/missing/errors;
- `extra_submit_tsc_ticks`;
- `extra_submit_ns`;
- `first_old_completion_tsc_ticks`;
- timer label if multiple timers are emitted.

Interpretation:

- Flat extra-submit latency until near WQ depth: WQ admission credits are available for low occupancy.
- Knee near `wq.size`: WQ/device admission is the likely first limit.
- Knee well before `wq.size`: store/posting/IIO/BAR ingress or another upstream credit domain is limiting.
- High tail at/above depth: submit is waiting for device progress to free admission capacity.

## New experiment 2: marker completion overlap during submit

Status: requires a new `hw-eval` runner mode. Existing burst benchmarks wait after submission and cannot tell whether the device completed work before the submit loop ended.

Purpose: determine whether DSA execution/completion visibility overlaps the CPU submit tail.

Procedure per sample:

1. Choose burst length `N`, marker position `p`, and poll cadence `M`.
2. Reset unique completion records.
3. Submit no-completion fillers before `p` if the hardware path supports a no-completion filler safely; otherwise use completion-bearing fillers and ignore them for marker overlap.
4. Submit a marker descriptor with a unique completion record; record `tp`.
5. Continue submitting fillers until `N` descriptors have been issued.
6. Every `M` submissions, poll only the marker completion; if it completes, record `tc`.
7. Record `t1` after the final submit returns.
8. If the marker was not observed, wait for it and record late `tc`.
9. Drain all descriptors required to restore a clean queue state.

Sweep:

```text
N = 64, 96, 128, 160, 256
p = 1, N/2, N
M = 1, 4, 16, 64, never
operation = NOOP first
```

Expected output row fields:

- benchmark name, e.g. `submit_marker_overlap`;
- `n`;
- `marker_position`;
- `poll_cadence`;
- `tp_tsc`;
- `t1_tsc`;
- `tc_tsc`;
- `marker_completed_before_t1`;
- completed/missing/errors.

Interpretation:

- `tc < t1`: DSA execution and completion visibility overlap the CPU submit tail.
- `tc < t1` only for tight `M`: the observed overlap is polling-cadence sensitive.
- `tc >= t1` for early markers: either completion visibility is delayed or submission/backpressure dominates so strongly that the marker is not observed during the submit loop.
- If marker behavior changes when fillers request completions, completion-write traffic is part of the bottleneck.

## New experiment 3: traffic-class isolation ladder

Status: partially runnable with existing modes, but should be consolidated into one runner so the same loop, timer, WQ, and output schema are used for every traffic class.

Purpose: add one DSA traffic class at a time and identify which addition creates the first bend.

Traffic classes:

1. `SubmitOnly`: descriptor submissions that do not request per-descriptor completion inside the measured region.
2. `NoopCompletion`: NOOP descriptors with completion records.
3. `Memcpy64`: 64 B memmove descriptors with completion records.
4. `Memcpy4K`: 4 KiB memmove descriptors with completion records.

Procedure:

1. For each traffic class, run the same occupancy or fixed-window curve.
2. Use identical pacing, timer, WQ, core, and NUMA placement.
3. Record submit phase, completion-visible phase, completed/missing/errors, and throughput if the mode is sustained.
4. Do not change payload size, completion layout, or polling policy except where the traffic class requires it.

Initial sweep:

```text
window / occupancy = 1, 8, 32, 64, 96, 112, 120, 124, 128, 160, 256
traffic class = SubmitOnly, NoopCompletion, Memcpy64, Memcpy4K
```

Expected output row fields:

- benchmark name, e.g. `traffic_class_ladder`;
- traffic class;
- operation size;
- window or occupancy;
- submit cycles/ns;
- completion-visible cycles/ns;
- completed/missing/errors;
- ops/sec for sustained windows.

Interpretation:

- `SubmitOnly` bends first: submit/admission is enough to create the bottleneck.
- `NoopCompletion` adds a bend: completion writes or CPU visibility of completion records matter.
- `Memcpy64` adds a bend: small payload DMA read/write path matters.
- `Memcpy4K` adds a unique bend: memory-fabric bandwidth, locality, or larger DMA transfer time matters.

## New experiment 4: completion handling and reuse policy

Status: requires a new `hw-eval` sustained-window runner. Existing throughput loops have a policy, but the policy is not an experimental variable with per-policy output.

Purpose: determine whether CPU completion discovery, reset timing, cacheline layout, or resubmit policy limits sustained batch-size-1/no-batch throughput.

Fixed conditions:

- Dedicated WQ.
- NOOP first, then 64 B memmove if NOOP is sensitive.
- Fixed logical window, initially 128 outstanding logical operations.
- One operation per MMIO submission.
- Release binary through `launch`.

Policies to compare:

1. `PackedScan`: current-style packed completion records with scan-all polling.
2. `PaddedRoundRobin`: completion records padded/separated and polled round-robin.
3. `PollOnly`: poll completions but delay reset/resubmit outside the measured phase where possible.
4. `DelayedReset`: harvest completions first, reset records in a separate phase.
5. `BatchHarvest`: harvest multiple completions, then reset/resubmit as a group.

Procedure:

1. Fill the fixed window.
2. Run until a fixed operation count or fixed wall interval is reached.
3. For each completed descriptor, record polling work and reset-to-submit timing according to the selected policy.
4. Preserve one live descriptor/completion/buffer per in-flight operation.
5. Drain cleanly at the end.

Expected output row fields:

- benchmark name, e.g. `completion_reuse_policy`;
- operation class;
- window;
- policy;
- ops/sec;
- polls per completion;
- completion harvest cycles;
- reset-to-submit cycles;
- completed/missing/errors.

Interpretation:

- Padding helps: cacheline ownership or false sharing on completion records is relevant.
- Round-robin helps over scan-all: polling stream or branch/cache behavior is relevant.
- Delayed reset helps: completion reset/reuse traffic is on the critical path.
- Batch harvest helps: per-completion resubmit policy is too fine-grained or too bursty.
- No policy movement: bottleneck is lower in the host/device path, not CPU completion reuse.

## New experiment 5: blind push loss and correctness check

Status: mostly runnable today through `--benchmark submit-admission`. Keep it in the plan because it is the correctness gate for no-tracking high-rate submission loops.

Purpose: verify whether pushing past dedicated-WQ depth without software in-flight accounting loses requests, reports errors, or merely backpressures the submit loop.

Preferred existing command:

```bash
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-admission \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 100 \
  --sizes 64 \
  --submit-bursts 64,96,112,120,124,126,127,128,129,130,132,136,144,160,192,256,512,1024 \
  --pin-core 0
```

If a new mode is added, it should remain equivalent in correctness semantics:

1. Allocate one descriptor and one completion record per pushed request.
2. Reset every completion record before the push.
3. Push `N` descriptors without polling or in-flight accounting.
4. Poll after the push until completion or timeout.
5. Count completed ids, missing ids, and error statuses.
6. Drain queue state before the next sample.

Interpretation:

- `completed == submitted`, `missing == 0`, `errors == 0`: blind push does not lose requests on this platform/WQ, but still may be backpressured.
- `completed < submitted`: software must not use no-tracking push loops for performance evidence.
- `SWERROR` or descriptor status errors: treat as invalid submit behavior and restore bounded in-flight tracking.

## Execution order

Run the work in this order:

1. **Reconfirm baselines**
   - Baseline A: submit-only all modes with dense bursts.
   - Baseline B: submit-admission distinct descriptors.
   - Stop if the basic measurements no longer match the known regime.

2. **Implement and run Experiment 1**
   - Occupancy-conditioned one-extra-submit latency.
   - This is the first decisive localization of admission backpressure.

3. **Implement and run Experiment 2**
   - Marker completion overlap.
   - This determines whether completion/execution overlaps the submit tail.

4. **Implement and run Experiment 3**
   - Traffic-class ladder.
   - This names which DSA traffic class introduces the first new bend.

5. **Implement and run Experiment 4**
   - Completion reuse policies.
   - This decides whether sustained throughput is CPU completion-path limited.

6. **Keep Experiment 5 as a recurring correctness gate**
   - Run after any change that alters descriptor lifetime, completion layout, or no-tracking push behavior.

## Implementation plan

Add the new modes narrowly in `hw-eval`; do not redesign the full benchmark suite.

Required additions:

1. A benchmark selector or subselector for the DSA bottleneck experiments.
   - Keep existing `--benchmark submit-only` and `--benchmark submit-admission` behavior stable.
   - Prefer explicit JSON benchmark names over inferring mode from optional fields.

2. Shared DSA descriptor preparation for these experiments.
   - Allocate descriptor/completion arrays sized by the largest requested window/burst.
   - Keep source/destination buffers alive until completion.
   - Provide operation constructors for NOOP, 64 B memmove, and 4 KiB memmove.

3. Shared timing helpers.
   - Whole-phase timing only.
   - No per-submit `rdtscp`.
   - TSC first; RDPMC optional if the existing timer wrapper can be reused without complicating the hot loop.

4. JSON schema additions.
   - Keep old fields stable.
   - Add new arrays only when the corresponding experiment runs.
   - Include enough fields to reconstruct curves without parsing stdout.

5. Tests.
   - CLI contract tests for new selectors and invalid combinations.
   - Software-only tests for burst/window parsing and policy parsing.
   - Unit tests for result aggregation where hardware is not required.
   - No fake hardware completions as proof of behavior; hardware behavior must be verified with `launch`.

## Reporting plan

Write the final measurements under `docs/report/benchmarking/` as a new numbered report. It should include:

- platform metadata and WQ sysfs state;
- commands used;
- baseline confirmation;
- one section per experiment;
- plots or tables for:
  - extra-submit cycles vs occupancy;
  - marker overlap vs position/cadence;
  - traffic-class curves;
  - completion-policy throughput and polls/completion;
  - blind-push completed vs submitted;
- the attribution decision reached from the first bend;
- explicit limits:
  - results are for the tested dedicated WQ unless shared-WQ runs are added;
  - DSA WQ admission is not raw PCIe posted-write credit depth;
  - batch-size-1/no-batch submission is not a DSA hardware `BATCH` descriptor.

## Decision rules

Use these rules when interpreting results:

| Observation | Attribution | Next action |
|-------------|-------------|-------------|
| Extra-submit latency bends with `K` near WQ depth | WQ/device admission credits | Tune in-flight bound and compare WQ sizes |
| Extra-submit latency bends well before WQ depth | CPU/store/IIO/BAR ingress credit domain | Add host-fabric counters or antagonist traffic |
| Marker completes before submit loop ends | DSA execution overlaps submit | Focus on admission/reuse rather than raw execution latency |
| Marker does not complete before submit loop ends | Completion visibility or admission delay dominates | Compare NOOP vs memmove and poll cadence |
| Completion policy changes throughput | CPU polling/reset/reuse path | Redesign completion layout/polling policy |
| Traffic-class ladder bends only when payload DMA is added | Memory/fabric payload path | Add NUMA and payload-size sweeps |
| Blind push loses completions | Benchmark correctness failure | Restore strict in-flight accounting before performance claims |
| Blind push completes all but submit time grows | Backpressured/admission-paced dedicated-WQ behavior | Treat submit time as credit wait, not lost work |

## Completion criteria

The experiment campaign is complete when the report can answer all of the following without hand-waving:

1. At what WQ occupancy does one extra submit become expensive?
2. Does a marker completion become visible while the CPU is still submitting later descriptors?
3. Which traffic class first changes the curve: submit-only, completion write, 64 B payload DMA, or 4 KiB payload DMA?
4. Does changing CPU completion discovery/reuse policy materially change sustained batch-size-1/no-batch throughput?
5. Does any no-tracking push lose completions or report descriptor errors on the tested dedicated WQ?
6. Which credit domain or software invariant should be named as the current bottleneck?
