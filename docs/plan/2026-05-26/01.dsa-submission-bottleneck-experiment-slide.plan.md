# DSA submission bottleneck experiment deck plan

## Goal

Create a short technical deck for an advisor/project discussion that explains how to localize the bottleneck behind an apparent contradiction:

- isolated dedicated-WQ `movdir64b` submission can be near 20 cycles when the admission path is unloaded;
- single DSA operations have sub-microsecond completion-visible latency in the direct measurement setup;
- sustained batch-size-1 async/raw execution has previously been around 8--10 Mops/s for small operations.

The deck now combines the original experiment design with the first measured result from the new submit-occupancy runner. It should show how each measurement separates CPU-visible submit admission, hardware execution/completion visibility, CPU polling/reuse, and request loss when software overfills a dedicated WQ.

## Sources

The current presentation is grounded in:

- `docs/plan/2026-05-26/02.dsa-submission-bottleneck-experiment.plan.md`
  - implementation-facing experiment plan behind this deck;
  - defines which experiments are already runnable, which require new `hw-eval` support, and how to interpret each result.
- `docs/report/benchmarking/018.dsa_submit_workload_study_2026-05-24.md`
  - `submit_only_unloaded` reached 20 cycles per submit at burst 2;
  - unloaded submit stayed cheap through moderate bursts and showed a knee around 64--128 submissions;
  - pressure-ramp and `mfence` modes showed hundreds of cycles per submit under backpressure/serialization;
  - the interpretation is that `movdir64b` can be cheap while credits are available and expensive once the host/WQ path is under pressure.
- `docs/report/benchmarking/019.submit_occupancy_one_extra_2026-05-26.md`
  - Experiment 1 measured result;
  - NOOP and 64 B memmove both stay cheap through `K=114`, transition at `K=115`, and reach a ~224--226 TSC tick plateau at `K=116`;
  - no missing completions or descriptor errors were observed;
  - first bend is before nominal WQ size 128, pointing to admission/credit pressure rather than 64 B payload DMA.
- `docs/report/literature/papers/understanding-the-host-network/paper.md`
  - host datapaths are credit-limited domains;
  - an upstream operation can observe low unloaded latency but then stall once downstream credits are exhausted.
- `docs/report/literature/005.accelerator_hostpath_2026-03-28.md`
  - accelerator paths should be interpreted through host-fabric, memory, and device-queue resource boundaries.
- Direct 2026-05-26 latency measurement from the working session:
  - dedicated WQ `/dev/dsa/wq0.0`, release `hw-eval`, launcher flow, pinned core 0;
  - median NOOP latency around 379 ns;
  - median memmove latency around 575 ns for 64 B and around 921 ns for 4 KiB.
- Prior batch-size-1 async/raw observations:
  - sustained direct/no-batch throughput around 8--10 Mops/s for small messages;
  - this is far below the naive ceiling implied by only looking at an unloaded 20-cycle submit.

## Design goals

- Use one main idea per slide.
- Favor diagrams, short tables, and terse labels over prose-heavy explanations.
- Keep the visual order: question, host-path lens, DSA loop, traffic classes, five experiments, attribution rule.
- Use Chronos sequence diagrams to show measured intervals and resource boundaries.
- Use companion motivation/code pages after each numbered experiment so the audience sees both why the experiment exists and the loop shape a runner should implement.
- Avoid claiming that `movdir64b` is slow in general. The deck should ask when a cheap posted write becomes credit-limited in a closed loop.
- Keep batch and concurrency concepts separate. The deck discusses dedicated-WQ submission, occupancy/window depth, and batch-size-1/no-batch behavior; it should not imply DSA `BATCH` descriptors.

## Story spine

1. Start with the contradiction: cheap unloaded submit, sub-microsecond direct completions, but much lower sustained closed-loop throughput.
2. Reframe the problem with the Host Network lens: the number to find is the first resource boundary where credits run out.
3. Show the DSA loop and timestamp boundaries: `t0→t1` is submit/admission; `t1→t2` is hardware work plus completion visibility.
4. Separate DSA traffic classes so later experiments add only one pressure source at a time.
5. Run five discriminating experiments:
   - occupancy-conditioned one-submit latency;
   - marker completion overlap during a submit burst;
   - traffic-class isolation;
   - completion handling/reuse variants;
   - blind push loss check.
6. Close with an attribution table: first bend names the likely credit domain or software invariant that failed.
7. Append the measured Experiment 1 result and apply the attribution rule: the first observed bend is an admission/credit knee around 116--117 outstanding operations.

## Slide-by-slide content components

### Slide 1: Deciphering the DSA submission bottleneck

Purpose: set up the contradiction and central diagnostic target.

Key message: a cheap unloaded submit does not imply a cheap sustained closed loop.

Visible components:

- Title: `Deciphering the DSA submission bottleneck`.
- Main callout: `Diagnostic target` / `missing cycles under full-WQ pressure`.
- Three evidence rows:
  - `Unloaded submit`: `~20 cycles`, meaning posted/admitted write with credits available.
  - `Single request`: `sub-µs visible completion`, with `NOOP ~379 ns; 64B ~575 ns`.
  - `Full-loop async`: `~8--10 Mops/s`, meaning closed-loop cost rather than isolated submit.
- Thesis fragment: `cheap submit ≠ cheap closed loop`.
- Source line naming the submit-only study, Host Network lens, and direct latency measurement.

### Slide 2: Host path view: what to measure

Purpose: introduce the credit-domain model before showing DSA-specific experiments.

Key message: the experiment should vary one pressure source and find the first bend.

Visible components:

- Left table, `Where credits live`:
  - `domain`: processor / memory / peripheral path;
  - `credits`: outstanding request budget;
  - `unloaded latency`: cheap path when credits exist;
  - `wait`: upstream work gets slowed.
- Right table, `DSA implication`:
  - `movdir64b returns`: the WQ accepted the write;
  - `not proved`: DSA execution;
  - `not proved`: completion writeback;
  - `not proved`: CPU can see completion;
  - `full-loop cost`: first place that runs out of credits.
- Bottom design rule: `vary one pressure source → find first bend`.

### Slide 4: DSA traffic classes

Purpose: define the resource classes the experiments add or isolate.

Key message: different DSA actions exercise different host-path resources, so the experiment ladder should add them one at a time.

Visible components:

- Table mapping DSA actions to host path and diagnostic role:

  - `DSA source read`: peripheral → memory read; tests payload-read pressure.
  - `DSA destination write`: peripheral → memory write; tests write-buffer / fabric pressure.

- Callout linking:

  - `Exp. 5: collide classes`.

### Slide 5: Experiment 1: submit gets slow when WQ is full?

Purpose: directly test whether one extra submit gets slower as WQ occupancy rises.

Key message: the occupancy curve reveals whether submit/admission credits are the first bottleneck.

Visible components:

- Chronos setup:
  - CPU pre-fills `K` descriptors into the WQ.
  - CPU times one extra submit: `t0` to `t1`.
  - The WQ/DSA path drains an old slot.
  - DSA writes the first old completion at `tc`.
  - CPU observes `tc` and drains/resets.
- Sweep table:
  - `x`: `K = 0,32,64,96,112,120,124,127,128`;
  - `y`: extra-submit cycles;
  - `hold fixed`: operation, NUMA node, WQ, and core.
- Readout:
  - `submit latency vs. occupancy`.
  - `flat`: submit credits remain.
  - `knee near 128`: WQ/device credits.
  - `early knee`: store/posting/IIO/portal bottleneck.
  - `full-WQ tail`: wait for device progress.
- Bottom callout: `Fill WQ more → see when submit gets slow.`

### Slide 6: Experiment 1: why run it

Purpose: explain the decision value of Experiment 1 and show the runner loop shape.

Key message: this is not another throughput sweep; it conditions a single submit on known WQ occupancy.

Visible components:

- Motivation table:
  - `why`: fill the WQ, then time one extra submit;
  - `learn`: when the extra submit gets slow;
  - `record`: `K`, submit cycles, first old done time.
- Explanatory note:
  - if submit stays fast until the queue is nearly full, the unloaded 20-cycle result is still the right admission-regime number;
  - if it slows early, the host/WQ path is running out of credits before nominal WQ depth.
- Zebraw Rust sketch:
  - loop over `K`;
  - reset slots;
  - prefill `K` NOOP descriptors;
  - time `submit_one`;
  - poll first old completion;
  - drain all;
  - record `credit-knee`, `K`, `t1 - t0`, and first-done timestamp.
- Code note: real runner still sets descriptors, fences, and checks completions.

### Slide 7: Experiment 2: marker completion during submit

Purpose: test whether DSA execution/completion can overlap the tail of a submit burst.

Key message: a marker completion visible before `t1` proves overlap; poll-cadence sensitivity means the polling loop is part of the measurement.

Visible components:

- Chronos setup:
  - submit fillers before marker position `p`;
  - measure marker submit `tp`;
  - submit fillers after `p`;
  - marker reaches DSA;
  - DSA writes completion;
  - CPU polls every `M` submissions;
  - `tc` is seen;
  - `t1` is burst-done time.
- Sweep table:
  - `p`: `1`, `N/2`, `N`;
  - `M`: `1`, `4`, `16`, `64`, `never`;
  - `fillers`: no-completion NOOP first.
- Readout:
  - `overlap = tc < t1`;
  - `tc < t1`: device overlaps submit;
  - `only tight M`: poll-sensitive;
  - `no tc < t1`: late completion or long latency.
- Control note: same core and one TSC stream.

### Slide 8: Experiment 2: why run it

Purpose: explain why marker overlap is a better discriminator than only timing burst completion.

Key message: the experiment separates hidden hardware progress from CPU polling artifacts.

Visible components:

- Motivation table:
  - `why`: a burst can hide whether DSA work overlaps CPU submission;
  - `learn`: whether marker completion appears before the submit loop ends;
  - `control`: poll every `M` submits to test polling cost.
- Explanatory note:
  - a marker completing before `t1` means DSA work overlaps the submit tail;
  - if the result changes only with tight polling, polling is changing the result.
- Zebraw Rust sketch:
  - loop over marker position `p`;
  - loop over poll cadence `m`;
  - reset slots;
  - submit marker or no-completion filler;
  - sparse-poll during submission;
  - capture `t1`;
  - wait for marker if needed;
  - record whether `tc < t1`.

### Slide 9: Polling can change the result

Purpose: insert a control slide before more experiments so polling/reuse artifacts are not mistaken for DSA behavior.

Key message: CPU polling and resetting the completion cacheline can itself move the bottleneck.

Visible components:

- Three left-side boxes:
  - CPU keeps reading `status = 0`: tight load loop.
  - DSA writes `done`: completion line changes owner/state.
  - CPU resets the same line: slot reuse may add cacheline traffic.
- Right-side question box:
  - `Are we measuring DSA, or are we measuring our polling loop?`
- Control table:
  - `poll less`: does the result move?
  - `poll tight`: best possible notice time.
  - `delay reset`: separate reset cost.
  - `pad slots`: test cacheline sharing.
- Metric pill:
  - `if polling changes throughput, fix polling first`.

Key message: the first new slowdown after adding one class tells which host-path resource to inspect next.

Visible components:

### Slide 12: Experiment 4: completion handling loop

Purpose: test whether CPU-side completion discovery, reset, and resubmit policy is the sustained-throughput limiter.

Key message: if throughput changes with reuse policy, fix the CPU completion path before blaming lower-level hardware submission.

Visible components:

- Chronos reuse loop:
  - DSA writes completion;
  - CPU measures harvest policy;
  - CPU measures reset timing;
  - CPU measures resubmit timing;
  - WQ sends next descriptor to DSA.
- Variant table:
  - `layout`: packed / padded;
  - `poll`: scan-all / round-robin;
  - `reset`: none / delayed / immediate;
  - `submit`: per-completion / batch harvest.
- Readout:
  - `throughput sensitivity to reuse policy`;
  - `padding helps`: ownership / false sharing;
  - `scan hurts`: poll load stream;
  - `batch helps`: burstiness / cache churn;
  - `no movement`: lower-level path.

### Slide 13: Experiment 4: why run it

Purpose: explain the CPU-side discriminator and show the fixed-window loop.

Key message: completion handling is part of the closed loop and must be varied explicitly.

Visible components:

- Motivation table:
  - `why`: CPU completion handling can be the slow part;
  - `learn`: which CPU policy changes throughput;
  - `record`: ops/sec, polls/done, reset-to-submit cycles.
- Explanatory note:
  - if padding, scan order, or batch harvesting changes the curve, fix the CPU completion path before changing hardware submission.
- Zebraw Rust sketch:
  - iterate policies `PackedScan`, `PaddedRoundRobin`, `PollOnly`, `DelayedReset`, `BatchHarvest`;
  - configure policy;
  - fill a window of 128 NOOP descriptors;
  - harvest, reset, and resubmit during a fixed run interval;
  - record ops/sec and polls per done.

### Slide 14: Experiment 5: push without counting

Purpose: test dedicated-WQ behavior when software submits past depth without in-flight accounting.

Key message: before trusting throughput from a no-tracking push loop, prove requests are not disappearing once WQ depth is exceeded.

Visible components:

- Chronos setup:
  - CPU pushes `N` requests to the dedicated WQ;
  - CPU intentionally does not maintain an in-flight count;
  - WQ accepts requests until capacity;
  - possible drop after full;
  - DSA writes completions for accepted requests;
  - CPU counts done completion records.
- Sweep table:
  - `N`: `depth/2`, `depth`, `2×depth`, `4×depth`;
  - `op`: `NOOP` first, optional `64B memmove`;
  - `rule`: do not poll while pushing.
- Readout:
  - `completed count vs. pushed count`;
  - `same count`: no loss seen in this run;
  - `missing ids`: some pushes were dropped;
  - `loss after depth`: WQ full behavior;
  - `SWERROR set`: hardware noticed bad submit.
- Warning callout:
  - this intentionally stops counting in-flight work to test whether requests can disappear.

### Slide 15: Experiment 5: why run it

Purpose: explain why the loss check is a correctness prerequisite for blind high-rate submission loops.

Key message: if pushed count exceeds completed count, the benchmark must restore in-flight tracking before any throughput number is meaningful.

Visible components:

- Motivation table:
  - `why`: `movdir64b` does not tell us "WQ accepted it";
  - `learn`: whether pushing without counting loses requests;
  - `record`: pushed, completed, missing ids, SWERROR.
- Explanatory note:
  - if pushed count is larger than completed count, in-flight tracking is required before trusting any dedicated-WQ throughput number.
- Zebraw Rust sketch:
  - loop over `N = depth/2, depth, 2*depth, 4*depth`;
  - reset unique completion slots;
  - submit `N` NOOP descriptors without waiting;
  - wait for completions until timeout;
  - compute missing ids;
  - read software-error status;
  - record pushed count, completion count, missing ids, and SWERROR.
- Code note: use one completion slot per pushed request so slot reuse cannot hide loss.
