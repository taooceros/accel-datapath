# DSA submission bottleneck experiment deck plan

## Goal

Create a short presentation for a technical project/advisor discussion. The deck should explain how to experimentally decipher why isolated dedicated-WQ `movdir64b` submission can measure near 20 cycles, while sustained batch-size-1 async execution reaches only roughly 8--10 Mops/s.

The tone should be technical and diagnostic: the deck is not a results claim, but an experiment design that maps each measurement to the bottleneck it can reveal.

## Sources

The slide is grounded in:

- `docs/report/benchmarking/018.dsa_submit_workload_study_2026-05-24.md`
  - isolated/unloaded submit can reach about 20 cycles per submit at burst 2;
  - unloaded submit remains cheap through moderate bursts, then shows a knee around 64--128;
  - pressure-ramp and `mfence` modes show hundreds of cycles per submit under backpressure/serialization;
  - admission probe on dedicated WQ completed over-depth descriptors but submit time grew, supporting backpressured admission rather than silent loss.
- Direct latency measurement from the current conversation:
  - dedicated WQ `/dev/dsa/wq0.0`, release `hw-eval`, `launch`, pinned core 0;
  - median NOOP latency around 379 ns;
  - median memmove latency around 575 ns for 64 B and around 921 ns for 4 KiB.
- Prior batch-size-1 async/raw observations:
  - sustained direct/no-batch throughput is around 8--10 Mops/s for small messages in previous reports;
  - this is far below the naive 20-cycle submission ceiling.

## Intended output

Write `presentation/2026-05-26/dsa_submission_bottleneck_experiments.typ` as a multi-slide Typst deck using the existing `presentation/template.typ`.

The deck should use `@preview/chronos:0.3.0` for a sequence/timeline-style diagram of the closed-loop DSA path. The title slide should be:

- `Deciphering the DSA submission bottleneck`

## Design goals

- Do not crowd every experiment onto one slide.
- One main takeaway per slide.
- Use a Chronos sequence diagram to show what the CPU, host fabric, WQ/device, and completion memory each observe.
- The bottleneck must be localized by separating submit admission, hardware execution/completion, and software completion reuse.
- The deck should be detailed enough that a reader can understand what to run and why each experiment exists.
- Avoid claiming a final root cause; frame the experiments as discriminators.
- Keep the visual order: question, current evidence, mechanism timeline, phase-splitting experiments, occupancy experiments, software/host-network experiments, decision rule.

## Story spine

1. Open with the contradiction:
   - isolated `movdir64b` can be about 20 cycles;
   - single-request hardware latency is sub-microsecond;
   - sustained async batch-size-1 throughput is far lower than the naive ceiling.
2. Show why a single scalar "submission cost" is the wrong object:
   - `movdir64b` is only CPU issue/admission;
   - sustained throughput is a closed loop over WQ credits, DSA execution, completion writeback, CPU polling, completion reset, and resubmission.
3. Use a Chronos sequence diagram to explain where `t0`, `t1`, and `t2` should be placed.
4. Present the two decisive experiments first:
   - split burst timing (`t0 -> t1`, `t1 -> t2`);
   - one-submit latency as a function of WQ occupancy.
5. Present the software-side discriminator:
   - completion-reuse loop variants.
6. Close with the attribution rule:
   - if submit time grows with WQ occupancy, admission/backpressure is the culprit;
   - if completion phase grows while submit remains cheap, device/completion is the culprit;
   - if polling variants change throughput, software completion discovery/reuse is the culprit.

## Slide-by-slide content components

### Slide 1: Deciphering the DSA submission bottleneck

Purpose: set up the contradiction and the central diagnostic question.

Key message: the 20-cycle `movdir64b` number is real in an unloaded admission regime, but it does not explain sustained batch-size-1 async throughput.

Concrete components:

1. Title: `Deciphering the DSA submission bottleneck`.
2. Subtitle callout:
   - `Question: where do the missing cycles appear when the WQ is kept full?`
3. Three fact cards:
   - `Unloaded submit`: `~20 cycles/submit` from submit-only burst 2.
   - `Direct completion`: `NOOP ~379 ns; 64B memmove ~575 ns`.
   - `Sustained batch_size=1`: `~8--10 Mops/s`.
4. Bottom thesis:
   - `Do not average the whole loop and call it submission cost; split the loop by resource boundary.`

### Slide 2: The closed loop we need to time

Purpose: show the system path as a sequence rather than a flat pipeline.

Key message: sustained throughput depends on a loop: submit, admission, execution, completion writeback, CPU observation, reset, and resubmit.

Concrete components:

1. Chronos sequence diagram with participants:
   - `CPU thread`;
   - `Host fabric / WQ admission`;
   - `DSA engine`;
   - `Completion memory`.
2. Messages:
   - `movdir64b descriptor`;
   - `admit or backpressure`;
   - `execute NOOP/memmove`;
   - `write completion`;
   - `poll status`;
   - `reset slot + resubmit`.
3. Side note:
   - `20 cycles only covers one arrow when credits are available.`

### Slide 3: Experiment A — split burst timing

Purpose: make the first decisive measurement concrete.

Key message: separate the submit phase from the completion phase before attributing bottlenecks.

Concrete components:

1. Timeline equation:
   - `t0`: before first submit;
   - `t1`: after Nth submit instruction returns;
   - `t2`: after all completions are observed.
2. Measurement fields:
   - `submit_cycles = t1 - t0`;
   - `completion_cycles = t2 - t1`;
   - `total_cycles = t2 - t0`.
3. Sweep:
   - `N = 1,2,4,8,16,32,64,96,128,160,256`;
   - operations `NOOP`, `64B memmove`, `4KiB memmove`.
4. Interpretation box:
   - rising `submit_cycles` means host/WQ admission backpressure;
   - rising `completion_cycles` means DSA execution or completion writeback.

### Slide 4: Experiment B — one submit vs WQ occupancy

Purpose: directly test whether `movdir64b` latency is a function of WQ fullness.

Key message: if the one-submit latency curve cliffs near WQ depth, the sustained bottleneck is admission-paced submission, not raw instruction cost.

Concrete components:

1. Procedure steps:
   - prefill `K` completion-bearing descriptors;
   - time one additional `movdir64b`;
   - drain;
   - repeat.
2. Sweep:
   - `K = 0, 32, 64, 96, 112, 120, 124, 127, 128`.
3. Expected curve sketch:
   - flat around unloaded cost for low `K`;
   - knee near WQ capacity if credits are the limit;
   - high tail if full-WQ admission blocks until space is freed.
4. Bottleneck revealed:
   - WQ/device admission credits.

### Slide 5: Experiments C/D — distinguish software reuse from host-network pressure

Purpose: describe secondary experiments that distinguish CPU-side completion machinery from shared host-network contention.

Key message: once A/B localize the bend, vary polling/reuse and antagonist traffic to identify whether the culprit is software/cacheline churn or shared host resources.

Concrete components:

1. Experiment C card:
   - hold window at 128;
   - compare scan-all polling, round-robin polling, batch harvest, immediate resubmit, and padded completion records;
   - reveal CPU polling, cacheline ownership, and slot reuse overhead.
2. Experiment D card:
   - run fixed DSA workload while adding CPU reads, CPU writes, non-temporal writes, and remote-NUMA traffic;
   - reveal posted-write credits, IIO/PCIe admission, coherency, or memory-fabric contention.
3. Decision text:
   - if C changes throughput, optimize completion discovery/reuse;
   - if D shifts the curves, treat this as a Host-Network shared-resource bottleneck.

### Slide 6: Attribution rule and execution order

Purpose: close with a concise decision tree and the recommended order to run experiments.

Key message: run split timing and occupancy-conditioned submit first; use the other experiments only after the phase boundary is known.

Concrete components:

1. Ordered run list:
   - `1. Split burst timing`;
   - `2. One-submit vs WQ occupancy`;
   - `3. Completion-reuse variants`;
   - `4. Host-network antagonist`.
2. Decision table:
   - `submit curve bends`: admission/backpressure;
   - `completion curve bends`: DSA/completion writeback;
   - `polling variant changes`: software/cacheline reuse;
   - `antagonist shifts curve`: shared host-network resource.
3. Closing sentence:
   - `The goal is not to prove movdir64b is slow; it is to find when a cheap posted write becomes a credit-limited closed loop.`

## Visual guidance

## Revision: illustration-first experiment deck

The deck should now favor diagrams over explanation. The audience should see each experiment as a small timeline/interaction, then read only terse labels.

Updated design constraints:

- Use Chronos not only for the main DSA loop, but also for the experiment pages.
- Keep one experiment per page.
- Avoid full-sentence procedure prose where a diagram, short axis label, or fragment works.
- Remove heavy formal pseudocode from audience slides. The operational details stay as compact step labels and sequence arrows.
- Keep Lovelace out of the deck unless a later slide truly needs algorithm syntax.

Updated slide-visible components:

1. `Deciphering the DSA submission bottleneck`
   - three short evidence cells: `~20 cycles`, `sub-µs completion-visible`, `~8--10 Mops/s`.
   - thesis as compact fragment: `cheap submit ≠ cheap closed loop`.

2. `Host-Network lens`
   - left: credit-domain fragments: `domain`, `credits`, `unloaded latency`, `admission delay`.
   - right: DSA implication fragments: `movdir64b return = next-domain admission`, `not execution`, `not completion visibility`.
   - bottom rule: `vary one pressure source → find first bend`.
3. `The DSA loop`
   - Chronos sequence with one `CPU thread`, Host/WQ admission, DSA engine, and completion memory.
   - two phase labels only: `t0→t1 admission` and `t1→t2 completion visibility`.

4. `DSA traffic classes`
   - concise table mapping action to traffic class and diagnostic role.
   - no long prose.

5. `Experiment 1: credit knee`
   - Chronos sequence: `prefill K`, `timed extra movdir64b`, `first old completion`, `drain`.
   - axis/metric label: `x = K`, `y = extra-submit cycles`.
   - interpretation fragments: `flat`, `knee near WQ`, `early knee`, `full-WQ tail`.

6. `Experiment 2: sentinel overlap`
   - Chronos sequence: submit sentinel at position `p`, continue fillers, sparse poll, observe sentinel.
   - diagram labels: `tp`, `t1`, `tc`, `tc < t1?`.
   - sweep fragments: `p = 1, N/2, N`; `M = 1,4,16,64,never`.
   - interpretation fragments: `overlap`, `poll-sensitive`, `no overlap`.

7. `Polling control`
   - Chronos sequence around completion cacheline: CPU cached-zero polls, device completion write, CPU positive poll, CPU reset.
   - control table with short labels: `cached-zero`, `pre-complete`, `cadence`, `reset/reuse`.

8. `Experiment 3: traffic-class isolation`
   - Chronos/ladder visual with progressively enabled arrows: submit-only, completion NOOP, 64B memmove, 4KiB memmove.
   - result fragments: `A bends`, `B adds bend`, `C/D adds bend`.

9. `Experiment 4: completion reuse`
   - Chronos loop: DSA writes completion, CPU harvest policy, reset timing, resubmit.
   - variants as compact labels: `packed/padded`, `scan/RR`, `poll-only`, `delayed reset`, `batch harvest`.

10. `Experiment 5: blind push loss check`
   - Purpose: test what happens if software keeps submitting to a dedicated WQ without tracking in-flight descriptors.
   - Chronos sequence: CPU repeatedly issues `movdir64b`, WQ accepts until full, possible drops after full, DSA writes completions for accepted descriptors, CPU counts observed completions.
   - Sweep fragments: `N = depth/2, depth, 2*depth, 4*depth`; operations `NOOP` first, then optional `64B memmove`.
   - Interpretation fragments: `submitted == completed`, `completed < submitted`, `SWERROR`, `loss starts after depth`.
   - Safety note: use unique completion records and descriptor ids; do not reuse slots during the push phase.

11. `Attribution rule`
    - compact decision table with fragments only.
    - closing fragment: `find first bend → name credit domain`.
    - maps observed bends to submit/admission credit depletion, overlapped hardware execution, posting/admission visibility delay, completion reuse bottlenecks, or dropped descriptors when software exceeds dedicated-WQ depth.

## Revision: motivation + prototype pages

Add one companion page after each numbered experiment page. Each companion page should answer two audience questions before the code:

1. Why run this experiment instead of another throughput sweep?
2. What specific uncertainty should the result resolve?

Each companion page should include a small Rust prototype rendered with `zebraw`. The prototypes are intentionally simple and presentation-facing: they should show the control structure and measured variables without pretending to be the full hardware implementation.

Slide-visible additions:

1. `Experiment 1 motivation + Rust sketch`
   - Motivation: test whether `movdir64b` gets slow only when the WQ credit domain is occupied.
   - Learn: location and shape of the admission knee as a function of prefilled descriptors.
   - Code sketch: loop over `K`, `prefill(k)`, time `submit_one()`, then `drain_all()` and record `k, cycles`.

2. `Experiment 2 motivation + Rust sketch`
   - Motivation: decide whether execution/completion can overlap the tail of the submit burst.
   - Learn: whether sentinel completion can become visible before the submit loop finishes, and whether polling cadence changes that conclusion.
   - Code sketch: loop over sentinel position `p` and poll cadence `m`, submit fillers plus sentinel, sparse-poll while filling, record `tc < t1`.

3. `Experiment 3 motivation + Rust sketch`
   - Motivation: add one traffic class at a time rather than comparing unrelated workloads.
   - Learn: whether the first bend belongs to submit admission, completion writes, small payload DMA, or larger payload DMA.
   - Code sketch: iterate `SubmitOnly`, `Noop`, `Memcpy64`, `Memcpy4K`, run the same occupancy/throughput probe, record the curve per class.

4. `Experiment 4 motivation + Rust sketch`
   - Motivation: avoid blaming hardware for a CPU completion-reuse policy.
   - Learn: whether layout, polling order, reset timing, or harvest batching changes sustained throughput.
   - Code sketch: iterate reuse policies, run a fixed window workload, harvest completions according to the policy, record ops/sec and polls/completion.

5. `Experiment 5 motivation + Rust sketch`
   - Motivation: dedicated WQ submission with `movdir64b` is posted, so submit can appear to succeed even when software is over the WQ depth.
   - Learn: whether a no-inflight-tracking loop loses requests, and at what pushed count loss begins.
   - Code sketch: reset many unique completion records, push `N` descriptors without polling or in-flight accounting, drain/poll completions, then record submitted count, completion count, missing ids, and software-error status.

Visual guidance for the new pages:

- Use `@preview/zebraw:0.6.3` for Rust snippets.
- Keep each Rust snippet short enough to fit beside or below a motivation/learn table.
- The snippets should use stable names (`bench`, `run`, `record`) and abstract hardware calls (`submit_one`, `poll_one`, `drain_all`) so the audience focuses on experiment shape, not implementation details.
