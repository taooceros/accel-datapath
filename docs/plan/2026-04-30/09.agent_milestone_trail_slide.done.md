## Slide-by-slide content components

### New slide: `What the milestone trail revealed`

Purpose: make the agent-collaboration lesson concrete by naming the recurring unsatisfactory patterns and the standards they were corrected toward.

Key message: the agent was useful at preserving detail and verification, but the work only became satisfying once the claim, API taste, and proof standard were made explicit before implementation.

Concrete visible components:

1. Top callout: “The repeated problem was not missing effort. It was that the agent often moved forward on a technically workable path before the deeper research/API standard was explicit.”
2. Left panel titled `Where I was unsatisfied` with bullets:
   - duplicate FFI/package surfaces before integration
   - handwritten descriptor ABI instead of bindgen-backed truth
   - source-only or double-copy memmove APIs
   - host-free proof used where real hardware proof mattered
   - cleanup that added abstraction weight
   - technically correct details without a clear research claim
3. Right panel titled `What I kept correcting toward` with bullets:
   - one canonical `idxd-sys` / `idxd-rust` stack
   - explicit source and destination ownership
   - zero-copy / minimal-copy as API design pressure
   - proof strength matched to claim strength
   - lean `bon` / `snafu` usage only where it helps
   - small, elegant, replaceable abstractions
4. Three compact milestone cards:
   - `M003 → M004`: stopped integration because duplicated FFI surfaces and bad ABI/API foundations remained.
   - `M006 → M007`: moved the async API toward explicit `Bytes` / `BytesMut` ownership, then toward completion-record-driven Tokio proof.
   - `M010 → M011`: made the standard explicit: clean, lean, elegant, hardware-backed where claimed, and free of avoidable duplicate paths.
5. Bottom callout: “Lesson: the agent is useful when it preserves evidence, but the milestone only becomes satisfying when the claim, API taste, and proof standard are set before implementation.”
