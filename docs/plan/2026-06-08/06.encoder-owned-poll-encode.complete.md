# Encoder-owned poll_encode redesign

## Goal

Redesign Tonic's experimental async encode interface so `Encoder::poll_encode` mirrors `Body::poll_frame`: polling resumes encoder-owned state through `Pin<&mut Self>` and `Context`, without a caller-managed `Option<Item>` continuation protocol or a borrowed `EncodeBuf` passed on every poll.

## Scope

- Update the Tonic codec `Encoder` trait and `EncodedBytes` driver.
- Preserve gRPC framing, compression, max-send-size checks, and output chunking in `EncodedBytes` / `EncodeBody`.
- Preserve the prost CPU fast path and the experimental async DSA bytes path.
- Update in-tree encoder implementations and tests affected by the trait shape.

## Intended changes

- Introduce an explicit encode start step that gives the encoder the message and encode buffer storage for the current payload.
- Change `poll_encode` to take only pinned encoder state and a task context.
- Make pending encode buffer stability and cancellation behavior part of encoder-owned state rather than a convention coordinated through `&mut Option<Item>`.
- Keep Tonic's body layer responsible for finishing compression, writing the gRPC header, enforcing size limits, and yielding output chunks.

## Verification

Run targeted checks for the touched tonic crates, including codec tests that cover pending encoders and the async DSA bytes codec tests where possible.

## Completion notes

Completed. `Encoder::start_encode` now transfers the item and owned `EncodeBuffer` into async encoders, and `Encoder::poll_encode` takes only `Pin<&mut Self>` plus `Context`. `EncodedBytes` keeps gRPC framing, compression, max-size checks, and chunk yielding outside individual encoders. The prost ready path remains synchronous through `encode_ready`, while the async DSA bytes encoder owns its pending copy, encode buffer, direct-DMA pointer, and drop-drain behavior.
