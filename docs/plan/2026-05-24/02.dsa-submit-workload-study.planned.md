# DSA submit-only workload study

## Goal

Build a dedicated `hw-eval` workload family for measuring DSA MMIO submission behavior, then use live hardware runs to separate unloaded submission issue cost from queue/backpressure and fence-induced serialization.

The motivating question is narrow: how expensive is the MMIO submission operation itself (`movdir64b` on a dedicated WQ, `enqcmd` on a shared WQ), and when does that cost stop looking asynchronous?

## Background

`Understanding the Host Network` argues that host datapaths should be understood as credit-limited domains, not as a single bandwidth number. Writes and reads traverse different domains and have different credit-replenishment points. A posted-style write can appear cheap when it is admitted into a host/device queue, while later samples can become expensive once a downstream queue runs out of credits or backpressure reaches the issuer.

For DSA submission this means one scalar “submit cost” is ambiguous. The benchmark suite should distinguish at least:

- unloaded MMIO issue cost;
- sustained no-drain submission under WQ/IIO/device backpressure;
- fence-separated submission where CPU-visible ordering forces posted writes to become less asynchronous;
- full descriptor completion latency, which is useful but not the same measurement.

## Scope

Code changes are limited to `hw-eval`:

- add a submit-only workload selector below the existing `--benchmark submit-only` command-line option;
- keep the benchmark names explicit in JSON so reports can distinguish workloads;
- keep the implementation small and local to the existing DSA methodology and submit helper modules;
- preserve the existing JSON shape and existing DSA/IAX benchmark paths.

## Workload definitions

### Clean drained submit burst

Benchmark name: `submit_only_unloaded`

For each sample:

1. issue `N` NOOP descriptors with no completion request inside the timed region;
2. stop timing immediately after the last submission;
3. submit a sentinel NOOP with completion outside the timed region;
4. poll sentinel completion before the next sample.

This is the closest comparison point for a claim such as “one DSA submission costs about 20 cycles,” because the timed region contains only the burst of MMIO submissions and each sample begins from a drained queue.

### Sustained no-drain submit burst

Benchmark name: `submit_only_sustained`

For each sample:

1. issue `N` NOOP descriptors with no completion request inside the timed region;
2. do not poll or drain between samples.

This intentionally measures backpressured behavior. It is not the unloaded cost of `movdir64b`; it shows when the host/device submission path stops accepting cheap asynchronous writes.

### MFENCE-separated submit burst

Benchmark name: `submit_only_mfence`

For each sample:

1. issue `N` NOOP descriptors with no completion request;
2. execute `mfence` between adjacent submissions in the timed region;
3. stop timing after the last submission;
4. drain with an out-of-region sentinel before the next sample.

This probes whether the cheap submit number depends on posted-write buffering and asynchronous admission. The fence is placed between submissions, not after the last one, matching the experiment question.

## CLI shape

- `--benchmark submit-only` selects the submit-only family.
- `--submit-mode all|unloaded|sustained|mfence` selects which submit workload(s) to run.
- Default submit mode is `all` when the submit-only family is selected.
- `--benchmark all` keeps running a single unloaded submit-only baseline as part of the broader DSA suite, avoiding a long sustained-pressure run in the default full benchmark.

## Measurement points

Use burst sizes:

```text
1, 2, 4, 8, 16, 32, 64, 128, 256, 512
```

Report:

- cycles per batch;
- cycles per submit as `median(batch cycles) / burst`;
- ns per submit using the existing TSC frequency conversion;
- p95/p99 already carried in the `LatencyStats` structure.

Do not put `rdtscp` around every individual `movdir64b`; that would measure the timing instrumentation more than submission. Use batch medians and compare adjacent burst sizes when reasoning about marginal cost.

## Gradual execution strategy

1. Preserve the current sustained no-drain workload under an explicit name.
2. Add the drained workload and run it alone to establish the unloaded reference.
3. Add the `mfence` variant and run it alone to test serialization effects.
4. Run `--submit-mode all` after the individual checks agree with the expected direction.
5. Write a benchmarking report that states which numbers are unloaded submission cost and which are backpressure/fence behavior.

## Verification

Code-level verification:

- `cargo fmt --package hw-eval`
- `cargo test -p hw-eval`
- `cargo build --release -p hw-eval`

Hardware verification, release binary through launcher only:

```bash
launch ./target/release/hw-eval --accel dsa --benchmark submit-only --submit-mode unloaded --device /dev/dsa/wq0.0 --json --iterations 3000 --sizes 64 --pin-core 0
launch ./target/release/hw-eval --accel dsa --benchmark submit-only --submit-mode sustained --device /dev/dsa/wq0.0 --json --iterations 3000 --sizes 64 --pin-core 0
launch ./target/release/hw-eval --accel dsa --benchmark submit-only --submit-mode mfence --device /dev/dsa/wq0.0 --json --iterations 3000 --sizes 64 --pin-core 0
```

Then run the combined submit-only family once if individual runs succeed.

## Non-goals

- Do not redesign the full DSA benchmark matrix.
- Do not treat completion latency as MMIO submission cost.
- Do not add PMU/uncore counter collection in this change; the first cut should be a clean, reproducible timing harness.
- Do not create a second IDXD submission implementation outside the shared submit helper.
