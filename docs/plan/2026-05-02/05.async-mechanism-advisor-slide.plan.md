# Async mechanism advisor slide plan

## Goal

Create one advisor-facing slide that explains how three async mechanisms relate to this project:

- C++ `stdexec` sender/receiver composition.
- Rust Tokio task/future runtime integration.
- C++ coroutine suspension/resumption.

The slide should help an advisor quickly see what each mechanism controls, where work is suspended, who resumes it, and how each model maps to accelerator submission/completion paths.

## Scope

In scope:

- Produce a concise conceptual comparison for a presentation deck.
- Use plain language and a small diagram/table rather than framework-specific jargon.
- Tie the comparison to this project's DSA/IAX async data path work: submit work, wait for completion, resume dependent computation.
- Reuse the existing `presentation/` Typst style if the slide is implemented in the current deck.

Out of scope:

- No new benchmark, hardware, or performance claims.
- No implementation changes to `dsa-stdexec/`, `idxd-rust`, or benchmark code.
- No exhaustive tutorial for each framework.

## Intended slide sequence and design

Use a short advisor-facing sequence rather than one crowded comparison slide. The target is 5 content slides plus optional backup detail. Each slide should have one takeaway sentence at the top and a simple visual that reuses the same left-to-right async lifecycle.

### Slide 1: One shared async lifecycle

**Takeaway:** all three mechanisms solve the same systems problem: submit work without blocking the CPU, remember what must happen next, and resume it when completion arrives.

Design:
- Title: `One async shape behind three mechanisms`.
- Center visual: one horizontal pipeline with five boxes: `submit async work` → `save continuation state` → `pending / suspend` → `completion event` → `resume continuation`.
- Under the pipeline, add a small DSA/IAX mapping: `descriptor submit` → `buffer + completion record stay valid` → `CPU does other work` → `completion record / interrupt / poll` → `dependent code runs`.
- Speaker note: this slide sets the vocabulary; avoid framework names until the bottom labels.
- Bottom labels: `stdexec = operation graph`, `Tokio = Future + Waker`, `C++ coroutine = co_await + frame`.

### Slide 2: stdexec — explicit operation graph

**Takeaway:** `stdexec` makes the async graph and scheduling boundary explicit, which is useful for controlled C++ experiments.

Design:
- Layout: left side shows a small graph: `sender` → `then` → `scheduler/on` → `receiver`; right side has three bullets.
- Bullets:
  - `describe work lazily`; no work until connected/started.
  - `receiver gets value/error/stopped`; completion contract is explicit.
  - `scheduler is visible`; layers can be swapped for experiments.
- Project tie-in: add a small callout: `why we used it: remove or replace layers to measure overhead`.
- Avoid: deep P2300 terminology; keep `operation state` as a small annotation, not the headline.

### Slide 3: Tokio/Rust — polling, wakeups, and lifetime proof

**Takeaway:** Tokio gives a natural task/waker integration point, but Rust forces the hardware path to prove that all state crossing `.await` remains valid.

Design:
- Layout: two-column split.
  - Left column visual: `Future::poll(Pin<&mut Self>, Context)` returns `Pending`, stores `Waker`, later completion calls wake, Tokio polls again.
  - Right column visual: a lifetime box around `src buffer`, `dst buffer`, `completion record`, and `task state`, spanning across the `.await` gap.
- Bullets:
  - `Pending does not block`; it registers how to wake the task.
  - State used after `.await` is saved inside the future/task.
  - `tokio::spawn` pushes tasks toward `'static + Send`; suspended tasks may move between runtime threads.
  - `Pin` matters because polled async state machines can become address-sensitive.
- Project tie-in callout: `DSA/IAX danger: hardware may still own pointers while Rust wants to move/drop values; the API must make that impossible.`
- This is the most important slide for the advisor because it explains why the Rust design work is not just glue code.

### Slide 4: C++ coroutine — syntax-level suspension

**Takeaway:** C++ coroutines make async code look sequential, but the language only provides suspension mechanics; scheduling and I/O policy still come from libraries.

Design:
- Layout: code-shaped visual on the left: `submit(); co_await completion; continue();`.
- Next to it, show a `coroutine frame` box containing `locals`, `suspend point`, and `continuation handle`.
- Bullets:
  - `co_await` marks a possible suspension point.
  - The coroutine frame preserves state so execution can resume in the middle.
  - Awaiter/promise types decide suspend/resume behavior.
  - Runtime/library still decides where completion events come from and who resumes the coroutine.
- Project tie-in: `good syntax story, but not a complete accelerator runtime by itself`.

### Slide 5: Comparison for advisor decision

**Takeaway:** choose the mechanism based on which boundary we want to study: graph composition, Rust safety/lifetimes, or coroutine syntax/resumption.

Design:
- Layout: compact 4-row table: `Mechanism`, `What is explicit?`, `Who resumes?`, `Main project risk/value`.
- Rows:
  - `stdexec`: explicit graph/scheduler; receiver/scheduler resumes; value is clean layer-control experiments.
  - `Tokio`: task polling/waker/lifetime constraints; runtime polls after wake; value is real Rust integration, risk is lifetime/ownership around hardware-owned buffers.
  - `C++ coroutine`: suspension point/frame; awaiter/runtime resumes; value is syntax-level model, risk is missing policy/runtime by default.
- Final row or footer: `same lifecycle, different proof obligations`.
- Keep this slide as the advisor memory anchor; it should be understandable if photographed alone.

### Optional backup slide: Rust lifetime challenge in one concrete example

Use only if the advisor wants detail or if the main Tokio slide feels too abstract.

Design:
- Show a minimal pseudo-flow: `async memmove(&src, &mut dst).await`.
- Annotate what must be true while hardware is outstanding:
  - `src` cannot be dropped or mutated unsafely.
  - `dst` cannot be read as complete until completion.
  - `completion record` must remain pinned/valid for hardware or polling code.
  - task migration means captured state must satisfy `Send` if spawned.
- Close with: `Rust makes these constraints visible; the API design must encode them instead of relying on discipline.`

## Key message

These mechanisms are different interfaces to the same core problem: keep the CPU from blocking while accelerator work is outstanding, then resume the right continuation when completion arrives. The most project-specific teaching point is the Rust one: Tokio is not merely an executor choice; its `Future`/`Waker` model exposes lifetime, ownership, `Send`, and `Pin` obligations for hardware-backed async operations.
