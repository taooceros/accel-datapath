# idxd non-batch submission throughput plan

## Goal

Move the small-message `idxd-rust` hardware benchmark from the current ~1.1 Mops/sec ceiling toward the expected non-batched ENQCMD submission ceiling, roughly 5 Mops/sec before MMIO batching is introduced.

The target metric is **message throughput** (`ops_per_sec`), not bandwidth.

## Current evidence

The latest raw Tokio throughput snapshot is `docs/report/benchmarking/016.idxd_tokio_raw_throughput_2026-05-01.md`:

- 64 B: ~0.79 Mops/sec
- 256 B: ~1.10 Mops/sec
- 1 KiB: ~1.11 Mops/sec
- 4 KiB: ~0.97 Mops/sec
- 16 KiB: ~0.95 Mops/sec
- 64 KiB: ~0.48 Mops/sec with 64 page-fault retries

That result is better than the old benchmark, but it is still not measuring the non-batched hardware submission path cleanly enough.

## Working diagnosis

The current `raw_async_throughput` row still goes through the public async future path. Even after removing per-operation `tokio::spawn`, source generation, and byte comparison from the timed path, each operation still pays for runtime machinery that is far too heavy for a 5 Mops/sec target:

- `DirectAsyncMemmoveRuntime::memmove` allocates/builds a new pending operation and one-shot channel per operation.
- The pending registry uses a `HashMap<u64, Arc<PendingOperation>>`.
- `PendingOperation` uses multiple `Mutex<Option<...>>` fields around source, destination, state, snapshots, and reply state.
- The monitor snapshots pending operations into a `Vec<Arc<_>>` each loop and resolves futures via channels/wakers.
- The benchmark still pays async future completion overhead for each message.

At 5 Mops/sec, the per-message budget is ~200 ns. The current public async path cannot fit in that budget; it is the wrong measurement path for the non-batched submission ceiling.

## Approach

Add a benchmark-only non-batched submission runner that uses Tokio only as the process/runtime wrapper, not as the per-operation completion abstraction.

The runner should:

1. Open the DSA work queue once.
2. Preallocate a fixed ring of slots equal to `--concurrency`.
3. Preallocate each slot's descriptor, completion record, source buffer, destination buffer, and retry state.
4. Pre-touch/prefault source and destination buffers before timing.
5. Submit each slot once with ENQCMD.
6. Poll completion records in a tight current-thread loop.
7. On terminal success, reset that slot's completion/descriptor and immediately resubmit it.
8. Keep one ENQCMD per message: no MMIO batching and no batch descriptor submission in this slice.
9. Keep full byte validation out of the timed loop; run the existing post-run sample validation outside timing.
10. Emit a clearly named row such as `raw_nonbatch_submission_throughput` so it is not confused with the public async future path.

This is intentionally a benchmark path first. If it reaches the expected range, then a later runtime-design slice can decide whether the public async API should move from `HashMap`/`oneshot`/`Mutex` to a slab/ring completion registry.

The stronger design direction is a safe public boundary with an unsafe internal hot core: callers still pass safe requests and receive safe results, but the implementation may own preallocated slot storage and use raw pointers internally to avoid repeatedly moving buffers, locking ownership containers, or rebuilding descriptor/completion state.

Unsafe Rust is allowed in this slice when it removes overhead from the measured critical path. Start with a narrow benchmark-local abstraction, then move the same shape into internal `idxd-rust` runtime code if that is what closes the gap. Any unsafe block must have a local `SAFETY:` comment that states the pointer lifetime, alignment, initialization, aliasing, and completion-record ownership invariants. Do not expose unsafe through the public API while chasing benchmark numbers.

## Scope and unsafe boundary

Expected files:

- `idxd-rust/src/bin/tokio_memmove_bench/cli.rs` — add/select the non-batch submission benchmark row or suite.
- `idxd-rust/src/bin/tokio_memmove_bench/modes.rs` or a new benchmark-local module — implement the preallocated slot ring and timing loop.
- Internal `idxd-rust` direct-runtime/slot code as needed — introduce a narrow unsafe core to remove per-operation ownership/synchronization overhead from the hot path, while keeping the public API safe.
- `idxd-rust/src/bin/tokio_memmove_bench/hardware.rs` — route hardware throughput suites to the new runner and keep post-run validation.
- `idxd-rust/src/bin/tokio_memmove_bench/artifact.rs` — preserve schema v2 if possible; add row naming only.
- `idxd-rust/scripts/verify_tokio_memmove_bench.sh` — accept/require the new row and keep the GiB/s threshold optional.
- `idxd-rust/scripts/bench_async_throughput_matrix.sh` — extract the new row for CSV.
- `idxd-rust/tests/async_benchmark_cli_contract.rs` and `idxd-rust/tests/async_benchmark_verifier_contract.rs` — minimal schema/row smoke updates.
- `idxd-rust/README.md` — document that this row measures non-batched raw submission, while `raw_async_throughput` measures the public async future path.
- Any new benchmark-local unsafe module/helper — keep raw descriptor/completion/buffer pointers encapsulated behind a tiny safe runner API, with focused `SAFETY:` comments at each unsafe operation.

## TDD / verification stance

Keep tests minimal and performance-oriented:

1. Host-free smoke test: verifier accepts a fake artifact containing `raw_nonbatch_submission_throughput` and still rejects payload dumps/schema errors.
2. Prepared-host integration test: release-mode run on `/dev/dsa/wq0.1`, small messages, concurrency sweep, `completion-only`, post-run validation pass.
3. Acceptance threshold: use `IDXD_RUST_VERIFY_MIN_OPS_PER_SEC` or a similar op-rate threshold, with an initial target near 3 Mops/sec and final target near 5 Mops/sec for small messages once stable.
4. Unsafe review gate: every unsafe block in the new runner or internal hot core must be small and documented; prefer one audited slot/ring type over scattered raw-pointer operations.

Do not add fine-grained unit tests for every ring detail unless the integration benchmark fails and needs diagnosis.

- [x] Add a fake-artifact verifier test for `raw_nonbatch_submission_throughput`.

- [x] If safe abstractions keep the ring below target, introduce the minimal benchmark-local unsafe needed for descriptor/completion/buffer reuse and document each invariant with `SAFETY:` comments.
- [x] Prefault/pre-touch benchmark buffers before timing.
- [x] Run release prepared-host sweeps over small messages and concurrency.
- [x] If still below 3 Mops/sec, profile the ring runner before touching public runtime code. The ring runner exceeded 3 Mops/sec after removing async/ownership overhead, so deep profiling was not required for this pass.
- [x] If the ring runner approaches 5 Mops/sec, keep it as the hardware ceiling row and document the public async-runtime gap separately. Best observed sample is ~5.06 Mops/sec at 64 B/concurrency 16 after final rebuild; repeated samples vary significantly by run.
- [ ] If benchmark-local unsafe proves the ceiling but public async remains slow, move the same shape into internal `idxd-rust` runtime code: safe external API, unsafe preallocated slot/ring internals, and no per-operation `HashMap`/`oneshot`/`Mutex<Option<_>>` in the measured submission/completion path.

## Verification commands

Host-free:

```bash
cargo test --manifest-path ./Cargo.toml -p idxd-rust \
  --test async_benchmark_cli_contract \
  --test async_benchmark_verifier_contract \
  --test async_throughput_matrix_contract \
  -- --nocapture
```

Prepared host:

```bash
IDXD_RUST_VERIFY_PROFILE=release \
IDXD_RUST_VERIFY_DEVICE=/dev/dsa/wq0.1 \
IDXD_RUST_VERIFY_BYTES=64 \
IDXD_RUST_VERIFY_CONCURRENCY=8 \
IDXD_RUST_VERIFY_DURATION_MS=1000 \
IDXD_RUST_VERIFY_MAX_PAGE_FAULT_RETRIES=64 \
IDXD_RUST_VERIFY_VALIDATION=completion-only \
IDXD_RUST_VERIFY_MIN_OPS_PER_SEC=3000000 \
bash idxd-rust/scripts/verify_tokio_memmove_bench.sh
```

Then raise the op-rate threshold toward 5 Mops/sec once the direct ring path is stable.
