# idxd Tokio benchmark suite revision plan

## Context

We have identified that the current `idxd-rust` Tokio benchmark suite reports very poor performance. This follow-up plan targets the benchmark suite and the async runtime validation path that currently pollutes benchmark measurements.

Current code scan findings:

- [`tokio_memmove_bench.rs#L24`](idxd-rust/src/bin/tokio_memmove_bench.rs#L24) uses a current-thread Tokio runtime and delegates parse/execute/emit to `tokio_memmove_bench/{cli,runner,hardware,software,modes,artifact}.rs`.
- Specific hot-path code in `modes.rs`: [`modes.rs#L132`](idxd-rust/src/bin/tokio_memmove_bench/modes.rs#L132) (`concurrent_submissions()`) creates a fresh `JoinSet` inside the iteration loop and calls `tasks.spawn(submit_one(handle.clone(), bytes, seed))`; [`modes.rs#L151`](idxd-rust/src/bin/tokio_memmove_bench/modes.rs#L151) (`fixed_duration_throughput()`) keeps filling a `JoinSet` with per-operation `tasks.spawn(submit_one(...))`; [`modes.rs#L194`](idxd-rust/src/bin/tokio_memmove_bench/modes.rs#L194) and [`modes.rs#L204`](idxd-rust/src/bin/tokio_memmove_bench/modes.rs#L204) (`submit_one()`/`build_request()`) rebuild each request; and [`modes.rs#L210`](idxd-rust/src/bin/tokio_memmove_bench/modes.rs#L210) (`deterministic_source()`) regenerates source bytes before `BytesMut::with_capacity(bytes)` allocates a fresh destination.
- [`operation.rs#L201`](idxd-rust/src/async_direct/operation.rs#L201) (`PendingOperation::finish_success()`) always calls `verify_initialized_destination` on success, so every async operation performs a full byte comparison in the critical path today.
- [`monitor.rs#L16`](idxd-rust/src/async_direct/monitor.rs#L16) (`monitor_completion_records()`) sleeps for `MONITOR_IDLE_BACKOFF` when no operations are pending, while [`async_direct.rs#L268`](idxd-rust/src/async_direct.rs#L268) inserts new pending operations without an explicit monitor wakeup, which can distort low-concurrency/latency measurements.
- [`async_session.rs#L26`](idxd-rust/src/async_session.rs#L26) (`AsyncMemmoveRequest`) consumes `Bytes` and `BytesMut`, and [`async_session.rs#L129`](idxd-rust/src/async_session.rs#L129) currently returns `AsyncMemmoveResult { destination, report: MemmoveValidationReport }`. The revised hot-path result should keep destination ownership for reuse but should not carry a validation result; validation belongs in an explicit out-of-band check.
- [`hardware.rs#L24`](idxd-rust/src/bin/tokio_memmove_bench/hardware.rs#L24) (`hardware_artifact()`) opens one async session/handle, runs all async modes, then runs a sync comparison row for canonical/latency suites. These old comparison semantics may be broken/replaced for the new raw-throughput goal.
- Existing contracts in `idxd-rust/tests/async_benchmark_*`, `idxd-rust/tests/async_throughput_matrix_contract.rs`, and `idxd-rust/scripts/verify_tokio_memmove_bench.sh` protect CLI/schema/verifier semantics; revise them deliberately with minimal tests.
- User decisions for this revision: prioritize raw DSA async throughput, treat Tokio only as the execution engine, do not preserve old row/mode behavior if it blocks a good benchmark, and keep output/correctness checks outside the timed critical path.

## Approach

Recommended direction: revise the benchmark into a raw DSA async throughput benchmark that uses Tokio as the async execution engine, not as the thing under test.

1. Keep the existing benchmark binary and artifact pipeline, but redefine the hardware performance path around one primary `raw_async_throughput` result row.
2. Decouple completion from validation in the async runtime result. The timed hot path should return only what is needed to continue/reuse ownership and collect lightweight completion metadata; it should not build or carry a validation result.
3. Keep TDD minimal and integration-oriented: one host-free contract for the new artifact shape, plus a prepared-host integration benchmark that must demonstrate good raw DSA async throughput. Avoid fine-grained scheduler/unit tests unless needed to debug the integration result.
4. Replace per-operation `tokio::spawn`/`JoinSet` scheduling in the performance-critical throughput path with a fixed worker/slot model: spawn at most `concurrency` long-lived workers, each repeatedly submits one DSA operation at a time until the duration/iteration budget is exhausted.
5. Reuse one prebuilt `Bytes` source and one `BytesMut` destination buffer per slot. After a successful operation, clear the returned destination and reuse its capacity for the next request. This keeps source generation and allocation out of the measured loop.
6. Add a small post-run full-validation check outside the measured interval, recommended as one sample per slot capped at a small constant such as 8. If this check fails, the artifact is not claim-eligible even if the timed throughput row completed.
7. Wake the async monitor when new operations are registered so measurements are not distorted by the idle sleep path.
8. Keep proof controls available outside the hot path: page-fault retry budget, no-payload artifact rule, expected-failure classification, software diagnostic/backend contract coverage, and explicit validation-mode reporting.

## Files to modify

- `idxd-rust/tests/async_benchmark_verifier_contract.rs` — minimal verifier acceptance/regression test for new schema/modes.
- `idxd-rust/tests/async_throughput_matrix_contract.rs` — update the fake benchmark artifact to the new throughput row and optional throughput gate.
- Prepared-host integration script/test path, likely `idxd-rust/scripts/verify_tokio_memmove_bench.sh` or a thin wrapper — run release-mode raw throughput and enforce an optional minimum GiB/s threshold.
- `idxd-rust/README.md` or relevant docs — document how to run the revised benchmark and how to interpret validation/post-run checks.

## TDD focus

Keep tests minimal and centered on the heart of the revision:

- Primary test: a prepared-host integration benchmark that runs the revised `raw_async_throughput` path in release mode and fails when `bytes_per_sec`/GiB/s is below a configured threshold such as `IDXD_RUST_VERIFY_MIN_GIB_PER_SEC`.
- Host-free support tests only where cheap and contract-facing: one CLI/artifact/verifier smoke test proving the new row/schema can be produced and parsed without payload dumps, plus fake-artifact coverage for the optional throughput gate.
- Avoid unit tests for every scheduler detail; if the integration benchmark is fast, claim-eligible, and stable, that is the heart of this revision.

## Post-run verification policy

Use one full-validation sample per concurrency slot, capped at 8 samples, after the timed throughput interval. These samples are not included in the throughput row's `elapsed_ns`, `ops_per_sec`, or `bytes_per_sec`. A sample failure should make the top-level artifact fail/non-claim-eligible while preserving the timed row for diagnosis.
