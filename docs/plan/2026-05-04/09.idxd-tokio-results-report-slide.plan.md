# IDXD Tokio results report deck plan

## Goal

Create a short advisor-facing characteristics report for the new Tokio integration path for Intel IDXD/DSA accelerators. The report should compare Tokio against raw `hw-eval` hardware performance only at matched points: same device/WQ, operation, NUMA policy, thread count, message size, and concurrency. It should use Lilaq plots for the characteristic curves and avoid over-commenting beyond a few highlighted numbers.

## Sources

- `docs/report/benchmarking/016.idxd_tokio_raw_throughput_2026-05-01.md`
  - public async-future row with completion-only timed validation and post-run validation.
  - key value: best point around `1.1 Mops/s` for 256 B to 1 KiB messages at concurrency 8.
- `docs/report/benchmarking/017.idxd_nonbatch_submission_throughput_2026-05-01.md`
  - benchmark-local non-batched slot-ring row.
  - key values: best observed `5,064,290 ops/sec` at 64 B / concurrency 16 in repeated direct-launch samples; earlier best verified-script sample `4,501,936 ops/sec`.
  - interpretation: removing public async-path container overhead exposes a faster hardware submission shape.
- `docs/report/benchmarking/013.tokio_single_numa_shared_wq.md`
  - NUMA-local Tokio submitter sweep on `/dev/dsa/wq0.1` shared WQ.
  - key values: best Tokio point `46.384 Mops/s` at 32 Tokio threads, 128 B messages, concurrency 128; 64 threads dropped to `33.443 Mops/s`.
  - raw `hw-eval` NUMA0 spot-check values: at 32 raw threads, per-size bests were `39.573`, `32.451`, `23.509`, and `7.008 Mops/s` for 128 B, 256 B, 1 KiB, and 4 KiB; at 64 raw threads, the 128 B point was `31.715 Mops/s` and the overall best was `34.483 Mops/s` at 256 B.
  - key caveat: raw/Tokio comparisons need matched repeats with identical NUMA/thread/concurrency settings before making an overhead-ratio claim.
- `docs/report/benchmarking/shared_thread_sweep_numa0/tokio_numa0_summary.csv`
  - exact per-thread best Mops/s values used in the compact scaling table.

## Design goals

- Main idea: characterize Tokio/IDXD against raw hardware with apples-to-apples curves, not a best-row matrix.
- Every plotted comparison must hold device, operation, NUMA policy, thread count, message size, and concurrency fixed.
- Use Lilaq (`@preview/lilaq:0.6.0`) for the plots.
- Use dual-y Lilaq plots: left axis is message rate (`Mops/s`), right axis is bandwidth (`GB/s`).
- Highlight a few useful numbers, but avoid heavy commentary.
- Generate the repeated characteristic slides from a Typst `scenarios` data array and `#for` loop instead of hand-copying slide bodies.
- Separate five slides:
  1. comparison contract / what is held fixed,
  2. 128 B thread sweep at fixed `concurrency=128`,
  3. 256 B thread sweep at fixed `concurrency=128`,
  4. 1 KiB thread sweep at fixed `concurrency=128`,
  5. 4 KiB thread sweep at fixed `concurrency=128`.
- Use caveat styling to avoid overselling: the report should say this is not yet a final speedup claim.

## Story spine

1. Open with the comparison contract: use NUMA-constrained Tokio data, and overlay raw NUMA0 hardware only where raw NUMA0 spot-checks exist.
2. Use a Typst `scenarios` array to generate one slide per message size.
3. Each generated slide fixes message size and concurrency, then sweeps NUMA0 Tokio thread counts: `1, 2, 4, 8, 16, 32, 64`.
4. Raw NUMA0 is overlaid at measured `32` and `64` thread points; do not imply unavailable raw points for 1--16 threads.

## Planned slide sequence

### Slide 1: Comparison contract

Purpose: make the apples-to-apples rule explicit before showing numbers.

Takeaway sentence: `Use NUMA-constrained Tokio data; for each message size, sweep submitter thread count and overlay raw NUMA0 hardware where raw spot-checks exist.`

Visible content components:

1. Main title: `Tokio + IDXD: NUMA0 per-message, per-thread characteristics`
2. Top callout: `Use NUMA-constrained Tokio data. For each message size, sweep submitter thread count and compare against raw NUMA0 hardware where raw spot-checks exist.`
3. Contract cards:
   - `Device/WQ`: `/dev/dsa/wq0.1`, shared WQ
   - `Operation`: direct/no-batch DSA memmove, `batch_n=1`
   - `Placement`: NUMA node 0 CPU + memory
   - `Threads`: Tokio `1, 2, 4, 8, 16, 32, 64`; raw `32, 64`
4. Highlight cards:
   - `128 B, 32T`: Tokio `46.4` vs raw `39.6 Mops/s`, `1.17x`
   - `128 B, 64T`: Tokio `33.4` vs raw `31.7 Mops/s`, `1.05x`
   - `256 B, 64T`: Tokio `24.0` vs raw `34.5 Mops/s`, `0.70x`
5. Minimal caveat: `raw NUMA0 is a 32T/64T spot-check; repeat before claiming overhead.`

### Generated thread-sweep slides

Purpose: include all matched submitter thread counts without copy-pasting slide bodies.

Takeaway sentence: `Each generated slide fixes one message size and c=128, then sweeps NUMA0 Tokio threads 1, 2, 4, 8, 16, 32, and 64.`

Visible content components generated for each scenario:

1. Title from the scenario data:
   - `128 B: NUMA0 per-thread scaling at c=128`
   - `256 B: NUMA0 per-thread scaling at c=128`
   - `1 KiB: NUMA0 per-thread scaling at c=128`
   - `4 KiB: NUMA0 per-thread scaling at c=128`
2. One Lilaq plot per generated slide with x-axis submitter threads, left y-axis `Mops/s`, and right y-axis `GB/s`.
3. The plot contains the NUMA0 Tokio thread-sweep curve and raw NUMA0 32T/64T spot-check points. The right axis is a dependent bandwidth conversion for that fixed message size.
4. Source footnote appears on the final generated slide.

## Visual guidance

- Use the repository presentation template and keep each page readable on 16:9.
- Keep one plot per slide for readability.
- Use Lilaq plots instead of a matrix of best rows.
- Use the right y-axis for bandwidth (`GB/s`) so both operation rate and byte rate are visible without adding more pages.
- Do not compare points that use different concurrency or message size on the same curve.
- Highlight only a few numbers; avoid over-commentary.
