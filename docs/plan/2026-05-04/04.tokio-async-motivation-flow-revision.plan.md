# Tokio tutorial async motivation flow revision plan

## Goal

Revise the opening motivation flow so it starts from a familiar blocking API, then motivates async mechanisms step by step:

1. blocking API is simple;
2. blocking API consumes a thread while waiting;
3. multiplexing one/fewer threads with an event loop is the natural solution;
4. multiplexing creates a new problem: the suspended operation's continuation must be represented explicitly;
5. C callbacks, Go stackful goroutines, and Rust/C++ stackless futures/coroutines are different answers to that continuation problem.

## Scope

In scope:

- Rewrite the first motivation slide after the title.
- Rewrite the C callback slide so it explicitly follows from thread multiplexing.
- Adjust the Go/Rust slide title/body to include Rust/C++ stackless coroutines.
- Preserve the rest of the tutorial flow after this setup.

Out of scope:

- Detailed C++ coroutine semantics.
- Performance claims or benchmark material.
- Full visual redesign beyond keeping slides readable.

## Intended slide sequence changes

- Slide `Blocking APIs are simple until many calls wait`:
  - show blocking `read`/`write` style code;
  - show the problem: while one call waits, the thread cannot run other connections;
  - show the potential solution: one worker/event loop watches many fds and dispatches only the one that can progress.
- Slide `C callbacks make the continuation explicit`:
  - explain that multiplexing removes the blocking stack as the place that stores progress;
  - show context + callback code as the manual continuation representation.
- Slide `Go is stackful; Rust/C++ futures are stackless`:
  - compare Go goroutine as userspace-thread-like stackful coroutine;
  - compare Rust/C++ async as stackless state-machine values.
