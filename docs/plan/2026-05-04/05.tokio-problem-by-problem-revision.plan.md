# Tokio tutorial problem-by-problem revision plan

## Goal

Revise the existing Tokio tutorial deck so the slides advance one problem at a time. Each new term should be introduced only after the deck has created the pressure that requires it.

## Structure principle

Use the chain recorded in `docs/plan/2026-05-02/06.tokio-general-tutorial-deck.plan.md`:

```text
Blocking API is readable
→ but many waits park many OS threads
→ so we multiplex fewer workers with an event loop
→ but each paused operation now needs its own continuation representation
→ C does this manually with context structs and callbacks
→ Go hides it in stackful, userspace-thread-like goroutines
→ Rust/C++ expose it as stackless future/coroutine state machines
→ Tokio schedules and wakes Rust Future values
→ spawn moves futures into runtime-owned tasks
→ ownership, lifetime, Send, and Pin constraints become visible
```

## Scope

In scope:

- Retitle and rewrite visible callouts so each slide follows pressure -> mechanism -> consequence.
- Remove glossary-like framing where possible.
- Preserve the existing deck file and most existing diagrams/code.

Out of scope:

- Full visual redesign.
- Benchmark or hardware material.
