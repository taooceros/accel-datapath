## Goal

Maintain a general advisor-facing tutorial deck that explains Rust async and Tokio from first principles. The deck should teach the execution model clearly enough that a systems reader can reason about:

- why async exists;
- where paused work stores its continuation;
- what a Rust `Future` is;
- how `poll`, `Pending`, `Waker`, and the Tokio executor interact;
- why `tokio::spawn` creates ownership, lifetime, `Send`, and `Pin` constraints.

The deck is intentionally a general Tokio/Rust async tutorial. It is not a DSA/IAX hardware report, not a benchmark report, and not a `stdexec` comparison.

## Core story spine

Preserve this problem-by-problem chain:

```text
Blocking API is readable
→ but many waits park many OS threads
→ so we multiplex fewer workers with an event loop
→ but each paused operation now needs its own continuation representation
→ C does this manually with context structs and callbacks
→ Go hides it in stackful, userspace-thread-like goroutines
→ Rust/C++ expose it as stackless future/coroutine state machines
→ Tokio schedules and wakes Rust Future values
→ spawn moves futures into runtime-owned tasks
→ ownership, lifetime, Send, and Pin constraints become visible
```

Each slide should answer a pressure created by earlier slides. Avoid glossary-like ordering where a term appears before the audience has seen why it is needed.

## Current deck structure

The current deck is chunked with Touying-native section headings:

1. `Introduction to async and Tokio`
2. `Problem 1: Blocking calls do not scale to many waits`
   - Blocking APIs are readable because the stack stores the continuation.
   - Many waits make one-thread-per-wait expensive.
   - Multiplexing fewer workers with an event loop creates a new continuation problem.
3. `Problem 2: Paused work needs a continuation`
   - C callbacks make continuation state explicit with context structs and callback functions.
   - A concrete `read + timeout + CPU-pool parse + event-loop report` example and follow-up glue-code slide show why manual C async APIs require callback/context plumbing for cross-library composition, explicitly noting this as one SG-IOV work challenge.
   - A bridge slide explains why Go goroutines/`select`, Rust/Tokio `Future`/`.await`, and C++ coroutine/sender APIs help: they put continuation state, races, errors, and scheduler hops into reusable async API shapes.
   - Go stackful goroutines preserve call stacks.
   - Rust/C++ stackless futures/coroutines compile suspension points into state-machine objects.
4. Solution slides for Rust futures (not a standalone section-title slide)
   - `async fn` creates a `Future`.
   - Executors drive futures by polling them.
   - `.await` defines state transitions and saved locals.
   - The state-machine slide uses pseudo-Rust `poll` lowering to show how `Pending` keeps the current state and `Ready` advances to the next state.
5. `Problem 4: Futures do not run themselves`
   - Tokio supplies runtime machinery: workers, scheduler, event loop, ready queue, timers, I/O events, and wakers.
   - `Pending` means the future cannot progress now and must save a `Waker`.
   - Wakers requeue tasks when I/O or timer readiness suggests progress may be possible.
6. `Problem 5: Runtime-owned tasks need type guarantees`
   - Keep Problem 5 as a dedicated title slide before the lifetime concept slides.
   - Introduce lifetimes before `spawn`: a borrow is a view with a proof window; annotations name relationships and do not extend storage.
   - Bridge to async lifetimes: an async function with `&Cfg` can produce a future containing that reference across `.await`; local `.await` bounds it, while `spawn` may let it escape.
   - `tokio::spawn` crosses an ownership boundary.
   - Briefly explain `Send` / `Sync` as Rust's compile-time markers for moving owned values or sharing references across threads, and why multi-thread Tokio requires spawned tasks to satisfy them.
   - `Pin` protects future state after polling starts; mention the hardware analogy that accelerators often require submitted descriptors/buffers to remain at stable addresses until completion.
7. `Close: Reason from the saved continuation`
   - Practical rules: own when spawning, keep borrows local, watch cross-await state, avoid locks across await, use channels, plan cancellation.

## Slide wording rules

Use audience-facing mechanism statements. Do not put plan/meta language on visible slides.

Avoid visible phrases such as:

- self-contained tutorial deck;
- no hardware details;
- no stdexec;
- speaker-note readability;
- takeaway prefix labels that read like planning scaffolding.

Prefer direct claims such as:

- `async fn` creates a `Future`; Tokio polls it, parks it when it returns `Pending`, and wakes it when I/O or timers may progress.
- The stack stores continuation state in blocking code.
- Multiplexing moves paused continuation state out of the OS thread stack.
- A future is saved computation plus a `poll` interface.
- A waker is a requeue handle, not the I/O result.
- `static` for spawned tasks means no short-lived borrowed references are stored in the future; it does not mean values leak forever.

## Technical claim boundaries

Keep these boundaries unless a future plan explicitly changes scope:

- Do not add project-specific DSA/IAX hardware material.
- Do not add benchmark or performance-superiority claims.
- Do not reintroduce `stdexec` slides into this tutorial version.
- Do not over-specify Go scheduler internals.
- Keep `Pin` conceptual for application readers; avoid unsafe projection details.
- Keep C++ coroutine mentions comparative and lightweight.
- Keep sender/receiver mentions conceptual and lightweight when explicitly requested; do not turn the tutorial into a `stdexec` comparison.
