# Experiment 2 mechanism trace plan

## Goal

Make `submit-marker-mechanism` emit per-iteration sample traces in the same shape as the Experiment 2 baseline trace so mechanism rows can be plotted and visually compared against `submit-marker-overlap`.

## Scope

- Add `sample_trace` to `SubmitMarkerMechanismResult` using the existing `SubmitMarkerSampleTrace` and `SubmitMarkerSampleTracePoint` JSON shape.
- Record submit latency, poll read order, poll statuses, poll read latency, and visible-prefix frontier for per-read timing rows.
- Preserve aggregate mechanism fields and baseline comparison fields.
- Teach the existing trace plotter to select either a `submit_marker_overlap` row or a `submit_marker_mechanism` row such as `baseline/packed-32b`.
- Regenerate a mechanism baseline trace plot and compare it visually/numerically to the baseline overlap trace.

## Verification

- `cargo test -p hw-eval`
- `cargo build --release -p hw-eval`
- Hardware run through `launch` with `--benchmark submit-marker-mechanism` emits rows with non-empty `sample_trace`.
- Plot script generates a mechanism baseline trace PNG/CSV from the mechanism JSON.
- Validate baseline row has 1000 traces and 160 points per trace for the full check run.

## Completion notes

Completed. `submit-marker-mechanism` now emits per-row `sample_trace` in the same shape as `submit-marker-overlap`, and the trace plotter accepts `--row` for mechanism row selection. The canonical try2 run shows the mechanism baseline reproduces the overlap baseline at the visible-vs-`NONE` level; line-position 0/1 split is run-sensitive rather than stable across all iterations. Details are in `docs/report/benchmarking/037.experiment2_mechanism_trace_try2_2026-05-31.md`.
