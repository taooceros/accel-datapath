# Minimal-code Prost bytes DSA encode plan

Status: draft

## Goal

Try DSA in Prost's `bytes` encoding path with the smallest useful code change set.

This plan deliberately avoids the larger field-transfer design from `01.prost-bytes-dsa-integration.draft.md`. The first question is simpler: when Prost is about to copy a large protobuf `bytes` field into Tonic's encode buffer, can we replace that synchronous CPU copy with a synchronous DSA memmove and still produce identical frames?

## Minimal design

Do not change Prost code generation, `prost::Message`, `prost::encoding::bytes::encode`, or Tonic's encode state machine.

Instead, add a DSA-aware `BufMut` wrapper used only by an experimental Prost codec:

```text
Tonic EncodeBuffer
  -> EncodeBuf
  -> DsaCopyBuf<EncodeBuf>
  -> prost::Message::encode(&mut DsaCopyBuf)
```

Why this works:

- Prost generated code already writes into any `BufMut`.
- `prost::encoding::bytes::encode` writes the key and length on CPU, then calls `BytesAdapter::append_to`.
- For protobuf `bytes`, `append_to` uses `buf.put(...)` for both `bytes::Bytes` and `Vec<u8>` sources.
- A wrapper can override `BufMut::put<T: Buf>` and use DSA only for large contiguous payload copies.
- Strings use `put_slice`, varints use scalar byte writes, and fixed-width fields use scalar writes, so leaving `put_slice` on the CPU keeps this mostly targeted at protobuf bytes payloads.

## Scope

Target the existing experimental crate `tonic-dsa-bytes-sync` instead of creating a new Prost-specific crate for the first slice.

Planned code changes:

1. Add `prost` and `tonic-prost` dependencies to `tonic-dsa-bytes-sync`.
2. Add a new module, for example `prost_codec.rs`, exporting:
   - `DsaSyncProstCodec<T, U>`
   - `DsaSyncProstEncoder<T>`
   - `DsaCopyBuf<'a>` as crate-private implementation detail
3. Reuse `tonic_prost::ProstDecoder<U>` for decode.
4. Reuse the existing sync DSA work-queue configuration from `tonic-dsa-bytes-sync`.
5. Make the existing synchronous slice-copy helper reusable inside the crate, e.g. change `copy_slice_to_uninit_with_dsa` from private to `pub(crate)`.

## Encoder behavior

`DsaSyncProstEncoder<T>` mirrors `tonic_prost::ProstEncoder<T>`:

```rust
impl<T: prost::Message> Encoder for DsaSyncProstEncoder<T> {
    type Item = T;
    type Error = tonic::Status;
    type Encode = Ready<Result<EncodeBuffer, tonic::Status>>;

    fn encode(
        self: Pin<&mut Self>,
        item: T,
        mut buf: EncodeBuffer,
    ) -> Result<Self::Encode, tonic::Status> {
        let mut dst = DsaCopyBuf::new(buf.as_encode_buf(), self.work_queue.clone(), self.threshold);
        item.encode(&mut dst).expect("Message only errors if not enough space");
        dst.finish()?;
        Ok(ready(Ok(buf)))
    }
}
```

The real implementation should avoid the literal `expect` if the wrapper can report a cleaner status, but the shape stays synchronous and ready-returning.

## `DsaCopyBuf` policy

`DsaCopyBuf` wraps `EncodeBuf<'_>` and implements `BufMut` by delegating almost everything to the inner buffer.

Only `put<T: Buf>` is special:

1. If no DSA work queue is configured, delegate to CPU.
2. If `src.remaining() < threshold`, delegate to CPU.
3. If `src.remaining() > u32::MAX`, record an internal error and delegate to CPU so the buffer remains initialized.
4. If `src.chunk().len() != src.remaining()`, delegate to CPU. The first slice only uses one DSA descriptor for one contiguous source chunk.
5. Otherwise, call `EncodeBuf::put_uninit_slice_with(len, |dst| copy_slice_to_uninit_with_dsa(src_ptr, dst, len, work_queue))`.
6. On DSA success, advance the source by `len`.
7. On DSA failure, record the `Status`, then CPU-copy the original source into the buffer. The encoder returns the recorded error after `Message::encode`, so the frame is not emitted. This avoids exposing uninitialized bytes without silently hiding selected hardware failure.

This keeps all DSA work synchronous. There are no pending holes, no async wake path, and no encode-buffer lifetime across `Poll::Pending`.

## What this proves

This slice can answer a narrow question:

> If we keep the existing Prost and Tonic APIs unchanged, does replacing large protobuf `bytes` field copies with synchronous DSA memmove look promising enough to justify a later async field-aware design?

It does not prove that DSA can overlap with Tonic's async body path. It is a low-risk measurement gate before adding those larger abstractions.

## Non-goals

- Do not add a generated `TransferMessage` trait.
- Do not modify Prost derive output.
- Do not add a Tonic private-hole API.
- Do not return `Poll::Pending` from Prost encoding.
- Do not implement real completion waking.
- Do not claim an end-to-end performance win from this slice alone.
- Do not change ordinary `tonic-prost` behavior.

## Test plan

Host-free tests:

- CPU path parity: with no work queue configured, `DsaSyncProstCodec` emits the same bytes as `tonic_prost::ProstCodec`.
- Wrapper selection: a fake copy lane records that large `put<T: Buf>` calls are selected, while `put_slice` calls remain CPU.
- Threshold behavior: below-threshold bytes are CPU, at/above-threshold bytes use the selected lane.
- Contiguity behavior: non-contiguous `Buf` sources fall back to CPU.
- Failure behavior: a fake selected-copy failure records an error, initializes the buffer via CPU copy, and causes the encoder to return `Status::internal` without yielding a frame.
- Message shape: a test message with leading scalar, large bytes field, and trailing scalar round-trips byte-for-byte.

Hardware checks through `launch`:

- Ignored encode test with a large protobuf `bytes` payload and configured `/dev/dsa/wq*`.
- Page-fault retry smoke using the same retry helper already used by `tonic-dsa-bytes-sync`.
- A small benchmark comparing:
  - `tonic_prost::ProstCodec`
  - `DsaSyncProstCodec` with no work queue
  - `DsaSyncProstCodec` with DSA enabled

Suggested commands after implementation:

```bash
rtk cargo test -p tonic-dsa-bytes-sync
rtk cargo check --tests -p tonic-dsa-bytes-sync
rtk launch cargo test --manifest-path accel-rpc/tonic/Cargo.toml -p tonic-dsa-bytes-sync --test hardware_prost_dsa -- --ignored
```

## Completion criteria

The slice is complete when:

- standard Prost and Tonic crates are untouched;
- the DSA Prost codec is opt-in through `tonic-dsa-bytes-sync`;
- default/no-work-queue behavior is byte-for-byte equivalent to normal Prost;
- selected DSA failures are observable as errors, not hidden as successful CPU fallback;
- a hardware smoke test confirms a large protobuf bytes field can be copied through DSA and decoded correctly.
