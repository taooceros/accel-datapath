# Experiment 2 perf profile with release debug symbols, 2026-05-29

## Change

Release builds now emit DWARF debug symbols without changing the release optimization level:

```toml
[profile.release]
debug = 2
```

`readelf -S target/release/hw-eval` confirmed `.debug_info`, `.debug_line`, and `.debug_abbrev` are present.

## Profile command

The profiler must run under `launch` so `perf` and its child inherit the DSA raw-I/O capability:

```bash
launch perf record \
  -F 9999 \
  --call-graph fp \
  -o docs/report/benchmarking/submission_bottleneck_2026-05-27/perf_experiment2_next_unfinished.data \
  -- ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-marker-overlap \
  --device /dev/dsa/wq0.0 \
  --iterations 5000 \
  --marker-bursts 160 \
  --marker-positions first \
  --marker-poll-offsets 0 \
  --dsa-op noop \
  --pin-core 0
```

Perf captured 5481 samples from `hw-eval`, with zero lost samples.

## Findings

This quick profile includes the full benchmark run: submit/poll loop, trace construction, stats conversion, and teardown.

Observed CPU cost:

- `bench_submit_marker_overlap`: 49.67% flat / 84.07% under the DSA benchmark call path.
- `poll_to_next_unfinished`: 41.76% under Experiment 2; inside it:
  - completion-status read/mask path: 25.44%;
  - `rdtscp`: 6.79%;
  - `CompletionPollResult::record_read`: 6.63%, including `Vec` pushes and visible `grow_one`/`malloc` paths.
- `sample_trace_point`: 7.33%, mostly cloning `Vec<usize>`, `Vec<u64>`, and `Vec<u8>` into per-iteration trace points.
- stats conversion/sorting after the run is visible: `core::slice::sort::unstable::quicksort` is 10.24% flat, and trace conversion through `into_point` accounts for 12.81% in the call graph.
- allocator/teardown costs are visible: `_int_malloc` 5.02%, `malloc_consolidate` 3.61%, and `__memmove_avx512_unaligned_erms` 3.27%, mostly tied to trace vectors and sample-trace drops/reallocations.

## Interpretation

The main measurement path is present as expected: status reads and `rdtscp` dominate the actual polling work. The extra overhead introduced by the richer Experiment 2 tracing is also measurable:

1. `CompletionPollResult` uses growable `Vec`s in the per-submit poll path.
2. `sample_trace_point` clones those vectors into the retained per-iteration trace.
3. post-run stats sort many accumulated vectors.

The most direct hot-path cleanup would be to reuse/preallocate the per-poll scratch vectors, or replace them with a bounded inline buffer sized for the maximum frontier burst observed per submit. That would remove the `grow_one`/`malloc` samples from `record_read` without changing the measured status-read latency.
