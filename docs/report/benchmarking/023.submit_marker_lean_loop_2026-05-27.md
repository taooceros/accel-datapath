# Submit-marker lean loop trace, 2026-05-27

## Question

After polling only one request, the offset-1 trace still showed about 1.2k TSC ticks from marker submit start to first observed completion. We simplified the active polling loop to identify which codepath contributes to the cumulative interval.

## Codepath change

The hot loop now follows this order:

1. Read TSC before submit.
2. Submit the descriptor.
3. Read TSC after submit.
4. If polling is enabled at this submit index, read the marker completion status and then read TSC once.
5. Only after the poll-end TSC is captured, update trace accumulators.

This removes the nested timed poll measurement from the hot path and moves trace/accounting writes after the completion observation. Per-poll latency distributions are intentionally absent in this lean mode; cumulative poll-end timing is the primary signal.

## Interpretation

After the lean change, the trace no longer measures per-poll latency inside the hot loop. The codepath to each poll is now close to: submit timestamp, submit, submit timestamp, volatile status load, post-load timestamp, and only then trace bookkeeping. The remaining interval is repeated cheap iterations until hardware completion becomes visible: cheap submit slices, cheap miss polls/status reads, loop transition gaps, then a success-visible status read at index 12.

The row-level marker-visible median (`1952` ticks) is higher than the median cumulative poll-end at index 12 (`1526` ticks) because these medians summarize different distributions. The index-12 success fraction is only `0.567`; samples that complete by index 12 are biased toward slower cumulative loop timings, while faster samples often need later polls. Therefore per-index median cumulative fields are useful for codepath shape, but the row-level first-seen median remains the direct completion-latency statistic.
