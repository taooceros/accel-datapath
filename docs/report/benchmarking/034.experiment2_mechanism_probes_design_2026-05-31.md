# Experiment 2 mechanism probes design

## Context

The no-`black_box` Experiment 2 rerun showed that visible completion-status reads are much slower than `NONE` reads after converting TSC ticks to nanoseconds:

- `NONE` reads: ~10.9 ns median, ~11.8 ns p99
- visible reads: ~104 ns median, ~360 ns p99
- adjacent visible completions often form a two-record/cacheline pattern: the first completion in a 64-byte line is expensive, while the second 32-byte completion record in that line is often near the measurement floor.

Experiment 2 therefore needs mechanism probes, not a new top-level benchmark question. The shared question remains: while the CPU submits descriptors toward the admission wall, what does completion visibility cost and why?

## Interface decision

Use an Experiment 2 Rust submodule with a separate runnable selector:

```text
--benchmark submit-marker-mechanism
```

```text
experiment_2_marker_overlap::mechanism_probes
```

The existing `submit-marker-overlap` selector and `submit_marker_overlap` JSON contract remain unchanged. New rows are serialized under:

```text
submit_marker_mechanism: [ ... ]
```

Each row has:

- `sub_experiment`: stable sub-experiment name
- `variant`: stable variant name within that sub-experiment
- `n`, `marker_poll_offset`, `operation_class`: workload controls
- completion layout facts: stride, alignment, base `%64`, base `%4096`
- latency stats for `NONE`, visible, first-line-position, second-line-position reads
- completion outcome stats
- optional poll-window stats for batch-scan variants
- non-baseline median nanosecond gaps and ratios against `baseline/packed-32b`

This keeps the public selector small, avoids adding many top-level benchmark names, and gives plots/scripts enough stable fields to compare variants.

## Sub-experiments

### 2B. Baseline and completion layout probe

Question: is the every-other visible-read pattern caused by two 32-byte completion records sharing one 64-byte cacheline?

Rows:

- `baseline` / `packed-32b`: current `Vec<DsaCompletionRecord>` layout, reset-only cache state, no prefetch, per-read timing
- `layout` / `padded-64b`: one completion record per 64-byte-aligned slot

Prediction: the baseline keeps the first/second line-position split; `padded-64b` removes cheap second-record hits because each completion is a first touch of its own line. The padded row reports `baseline_comparison` gaps against the single baseline row.

### 2C. Cacheline-pair probe

Question: within a visible poll event, how different are the first and second completion records in the same cacheline?

Implementation: aggregate visible reads by computed line position from the measured completion base alignment. For packed 32-byte storage, position 0 and position 1 correspond to the lower/upper half of the 64-byte line.

Prediction: position 0 is expensive and position 1 is cheap when a cacheline is first observed by CPU after DSA writes.

### 2D. Prefetch probe

Question: can CPU prefetch hide the next DSA-written cacheline visibility cost?

Rows:

- `prefetch-1-lines`
- `prefetch-2-lines`
- `prefetch-4-lines`

Each variant prefetches ahead of the next unfinished completion before the measured status load. The distance is expressed in 64-byte cachelines, not completion records. The no-prefetch case is the single `baseline/packed-32b` row, not a duplicate prefetch row.

Prediction: if prefetch can pull a DSA-written line into the CPU hierarchy before the demand load, visible-read latency drops. If the line is not yet globally visible or demand-load serialization dominates, latency remains similar.

### 2E. Measurement-method probe

Question: does per-read `rdtscp` expose serialized latency that a production-style scan could overlap?

Rows:

- `batch-scan-timing`: one timestamp before and after the whole visible-prefix scan

The per-read timing case is the single `baseline/packed-32b` row.

Prediction: batch scanning may show lower per-read amortized cost if the CPU can overlap line fills or if `rdtscp` fences suppress natural out-of-order/prefetch behavior.

### 2F. Cache-state probe

Question: does the CPU's pre-submit ownership/state of completion cachelines affect first-visible read cost?

Rows:

- `pre-touch`: read completion statuses after reset before submit
- `clflush`: flush completion storage after reset before submit

The reset-only case is the single `baseline/packed-32b` row.

Prediction: if CPU-owned clean lines interact with DSA writes, pre-touch or clflush will shift the first-visible distribution.

## Non-goals

- Do not turn these into a new numbered Experiment 6.
- Do not change the existing `submit_marker_overlap` JSON shape.
- Do not infer NUMA/DDIO policy directly from this probe alone; placement-specific work can build on the same result schema later.

## Completion criteria

A completed implementation provides a real hardware submit/poll loop for each variant, records layout/alignment facts, emits parseable JSON rows, and has tests covering selector parsing, result serialization wiring, and cacheline-position math.
