# Async DSA vs sync DSA vs standard bytes RPC comparison

## Question

Compare the end-to-end Tonic mock bytes RPC throughput of:

- `standard`: CPU `BufMut::put` raw bytes codec.
- `sync-dsa`: `tonic-dsa-bytes-sync` synchronous DSA encode copy.
- `async-dsa`: `tonic-dsa-bytes-async` `poll_encode` DSA encode copy.

The benchmark is `tonic-bytes-bench --bin compare_bytes_rpc_throughput`. It uses the same unary bytes echo shape as the existing sync benchmark, but is generic over the codec encode item so standard/sync can encode `Box<dyn Buf + Send + Sync>` while async encodes `Bytes` directly.

## Environment and command shape

All hardware DSA runs used `/dev/dsa/wq0.0` through `launch`.

Build and checks:

```bash
cd accel-rpc/tonic
rtk cargo fmt -p tonic-bytes-bench -p tonic-dsa-bytes-async -- --check
rtk cargo check -p tonic-bytes-bench --bin compare_bytes_rpc_throughput
rtk cargo test -p tonic-bytes-bench
rtk cargo clippy -p tonic-bytes-bench --all-targets --no-deps -- -D warnings
rtk cargo build --release -p tonic-bytes-bench --bin compare_bytes_rpc_throughput
rtk cargo check --workspace --exclude interop
```

Full `rtk cargo check --workspace` still fails only in `interop/build.rs` because this environment lacks configured `protoc` / `protoc-gen-rust-grpc` binaries.

## Direct EncodeBuf update

The async path was changed after the initial comparison: it now reserves final
`EncodeBuf` storage, assumes the reservation remains stable across `Pending`,
and commits the initialized bytes after DSA completion. This removes the staged
destination and final CPU copy from the async DSA encode path.

## Current interpretation

- Removing the staging buffer materially changes the result. Async DSA now wins the observed 64 KiB row in both reruns and wins the 1 MiB / 2 MiB rows in the broader sweep.
- Sync DSA still wins the observed 4 KiB rows and the 4 MiB broad-sweep row, and it wins the 1 MiB default row.
- Standard CPU is no longer the robust winner after the direct-buffer change; it loses most DSA-eligible rows in the direct-buffer reruns.
- The direct async path is therefore performance-relevant, not just semantically implementable. The remaining question is where the DSA submission/polling overhead crosses over against CPU copy and sync spinning for each payload/concurrency regime.
