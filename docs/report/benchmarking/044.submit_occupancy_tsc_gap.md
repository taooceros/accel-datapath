# Submit occupancy TSC-gap pacing, 2026-06-02

## Question

Can Experiment 1 use a cheaper, more interpretable inter-submit pacing knob than black-box loop iterations?

## Change

Added `--submit-occupancy-gap-tsc <N>`. When nonzero, Experiment 1 waits until about `N` TSC ticks have elapsed after each prefill submission and between traced post-prefill submissions. The wait is outside each recorded `submit_tsc_ticks` sample.

The prior `--submit-occupancy-spin-iters <N>` remains available for the legacy `for n in 0..N { black_box(n); }` loop. The two options are mutually exclusive.

Implementation shape:

```rust
fn wait_tsc_gap(target_tsc_ticks: u64) {
    let start = rdtsc_relaxed();
    while rdtsc_relaxed().wrapping_sub(start) < target_tsc_ticks {}
}
```

`rdtsc_relaxed()` is a non-serializing `rdtsc` inline-asm helper, so the minimum nonzero cost is bounded by two `rdtsc` reads plus loop/control overhead. A target of 1 tick is not a one-cycle delay, but it is cheaper and better-defined than a black-box loop count.

## Cargo-asm evidence

Command:

```text
rtk cargo asm -p hw-eval --bin hw-eval --rust --intel hw_eval::benchmarks::submission_bottleneck::run > target/asm-investigation/submission_bottleneck_run_gap_tsc.asm
```

Dedicated WQ path with TSC gap:

```asm
movdir64b rbx, zmmword ptr [rdi]
rdtsc                         ; start
...
.LBB244_812:
rdtsc                         ; current
...
cmp rax, r14                  ; elapsed < target?
jb .LBB244_812
add rdi, 64
```

There is no `pause` and no black-box stack store in this path. The wait remains non-removable because the loop repeatedly executes inline asm `rdtsc`.

## Cost of the TSC-gap knob

At K=96, where the no-gap prefill loop is not yet in the admission-stall region, the effective added prefill ticks per descriptor were:

| workload | gap=1 | gap=10 | gap=25 | gap=50 | gap=100 |
|---|---:|---:|---:|---:|---:|
| noop | 37.4 | 38.1 | 55.4 | 84.4 | 124.9 |
| 1 MiB memmove | 54.2 | 76.9 | 93.8 | 120.7 | 163.2 |

At K=128, the no-gap baseline already includes submit stalls, so net deltas are partially masked by stall removal:

| workload | gap=1 | gap=10 | gap=25 | gap=50 | gap=100 |
|---|---:|---:|---:|---:|---:|
| noop | 4.4 | 3.0 | 22.7 | 47.0 | 104.6 |
| 1 MiB memmove | 46.0 | 46.3 | 59.9 | 87.9 | 129.5 |

The important calibration point is K=96: even a target gap of 1 tick costs tens of ticks because the implementation needs at least two `rdtsc` reads. But it is materially cheaper than the simple `black_box(n)` loop, which was about 102-103 ticks/descriptor at K=128 for one iteration.

## Interpretation

The TSC-gap knob gives a smoother pacing axis than the black-box loop:

- gap=0: knee at K=114 for both workloads.
- gap=1 or 10: knee moves later, to K=128 for `noop` and K=160 for 1 MiB memmove.
- gap=25: `noop` knee moves to K=144; 1 MiB memmove still bends at K=160.
- gap=50: no median knee through K=160 for either workload.

This preserves the earlier conclusion but with a more interpretable delay unit. The submit-latency knee is highly sensitive to modest inter-submit pacing. A roughly 50-tick target TSC gap is enough to remove the measured admission stall through K=160, while the 1 MiB memmove rows still show only about 27-30 of 128 completions visible at K=128 and still need about 2.24M post-submit completion ticks. That means the knee disappearance is still not payload completion; it is the WQ/device admission path catching up with the descriptor stream.
