# Submit-occupancy huge-memmove probe, 2026-06-01

## Question

If Experiment 1 uses very large memmove descriptors, does the submit-occupancy knee move in a way that points to payload processing / PCIe pressure, or does it stay near the prior admission threshold?

## Setup

- Binary: `./target/release/hw-eval`
- Runner: `--benchmark submit-occupancy`
- Device: `/dev/dsa/wq0.0`
- WQ mode: dedicated
- CPU pin: core 0
- Artifacts: `docs/report/benchmarking/submit_occupancy_huge_memmove_2026-06-01/`

A CLI override was added for this probe:

```bash
--dsa-op memmove64 --dsa-memmove-bytes <N>
```

The operation stays on the memmove descriptor path, while the byte count is overridden for submission-bottleneck experiments.

## Size calibration

The original proposed size, 16 MiB, was too large for this path on the tested WQ: every descriptor completed with an error. Calibration showed:

| Bytes | Result |
|---:|---|
| 64 KiB | completed, no errors |
| 256 KiB | completed, no errors |
| 1 MiB | completed, no errors |
| 2 MiB | accepted at K=0, but high-occupancy sweep had descriptor errors |
| 4 MiB | descriptor error |
| 16 MiB | descriptor error |

The primary clean run therefore used **1 MiB**. This is still large enough for the intended separation: using the prior local dedicated DSA 4 KiB throughput result of about 29,973 MB/s, 1 MiB is roughly 35 us of payload work, far above the ~100--200 ns submit plateau and prior ~2 us first-completion window.

## Commands

Clean large-payload run:

```bash
launch ./target/release/hw-eval \
  --accel dsa \
```

The submit knee stayed around K=115--116 for every tested size. The high-occupancy plateau stayed near 170--209 ns even while first-old-completion latency scaled from sub-microsecond NOOP completions to hundreds of microseconds for large memmoves.

## Interpretation

The 1 MiB run delayed the first old completion from about 2 us to roughly 140--270 us, so payload processing was definitely much longer than the submit path. Despite that, the submit-occupancy knee stayed in the same region:

- cheap/low-submit-cost region through about K=112,
- transition at K=114--115,
- high/backpressured plateau by K=116.

The high plateau also matched the same-build 4 KiB rerun closely: about 432--440 TSC ticks for 1 MiB versus about 454--456 TSC ticks for 4 KiB.

This argues against the knee being caused by PCIe or payload-processing throughput. If payload processing were the controlling mechanism, making each descriptor take hundreds of microseconds should have shifted the submit knee substantially. Instead, payload latency changed dramatically while the admission knee did not.

The current evidence points to a DSA work-queue admission / submit-side threshold rather than a consumer-side completion-drain bottleneck or payload-processing bottleneck. The completion consumer was not the limiting factor in this particular probe because completions were delayed by large payload DMA, yet the submit knee still appeared at the same outstanding count.

## Caveats

- 16 MiB is not a valid clean memmove size on this tested path; those rows are retained only as failed calibration evidence.
- 2 MiB was not used as primary evidence because the high-occupancy sweep reported descriptor errors.
- The 1 MiB run is valid for the tested WQ and command shape: median missing completions were zero and median descriptor errors were zero at every checked occupancy.
