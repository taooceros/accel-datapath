# Submit-marker next-unfinished frontier trace, 2026-05-28

## Question

Instead of repeatedly reading one completion record, what happens if each traced poll walks the completion frontier until it reaches the next unfinished request, while still timing each individual status read?

## Change

Experiment 2 now keeps a per-iteration frontier. At each traced submit index it polls completion records starting at the first not-yet-observed request. It records one latency per status read, advances the frontier for every non-`NONE` status, and stops at the first `NONE` status or the end of the burst.

Each per-iteration sample point now carries:

- `polled_request_indices`
- `poll_latency_tsc_ticks`
- `polled_statuses`
- `first_polled_request_index`
- `last_polled_request_index`
- `visible_prefix_len`

## Visualization

The plot uses three synchronized panels for one sampled iteration:

1. submit latency by submit index;
2. per-status-read latency, colored by `NONE` versus visible completion;
3. frontier movement, with step lines for the last probed request and visible prefix after the read.

Thin purple guide lines mark every submit index where at least one status read observed a visible completion.

## Hardware run

```bash
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-marker-overlap \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 1000 \
  --marker-bursts 160 \
  --marker-positions first \
  --marker-poll-offsets 1 \
  --dsa-op noop \
  --pin-core 0
```
