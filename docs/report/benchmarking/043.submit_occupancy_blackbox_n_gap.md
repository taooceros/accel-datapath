# Submit occupancy cheaper black_box(n) gap

## Question

Can the artificial Experiment 1 inter-submit delay be cheaper than the accumulator-based black-box loop while still preventing LLVM from optimizing the loop away?

## Change

The helper now uses one `std::hint::black_box` call per loop counter and discards the result:

```rust
fn manual_submit_gap(iterations: u64) {
    for n in 0..iterations {
        black_box(n);
    }
}
```

This replaces the heavier accumulator form:

```rust
accumulator = black_box(accumulator.wrapping_add(black_box(i)));
black_box(accumulator);
```

## Cargo-asm evidence

Command:

```text
rtk cargo asm -p hw-eval --bin hw-eval --rust --intel hw_eval::benchmarks::submission_bottleneck::run > target/asm-investigation/submission_bottleneck_run_black_box_n.asm
```

Experiment 1 helpers are still inlined into `hw_eval::benchmarks::submission_bottleneck::run`.

Dedicated WQ prefill path with `spin_loop_iters == 0` remains the tight `movdir64b` burst:

```asm
movdir64b rdx, zmmword ptr [rcx]
add rcx, 64
add rax, -64
jne .LBB242_819
```

With `spin_loop_iters != 0`, each descriptor gets the simple `black_box(n)` loop:

```asm
movdir64b rdx, zmmword ptr [rcx]
xor edx, edx
lea rsi, [rsp + 576]
.LBB242_810:
mov qword ptr [rsp + 576], rdx   ; black_box(n)
inc rdx
#APP
#NO_APP                          ; black_box inline-asm barrier
cmp rbx, rdx
jne .LBB242_810
add rcx, 64
```

The traced-post-prefill gap compiles similarly:

```asm
xor ecx, ecx
.LBB242_876:
mov qword ptr [rsp + 576], rcx   ; black_box(n)
inc rcx
#APP
#NO_APP
cmp rdx, rcx
jne .LBB242_876
```

This is not optimized out: each iteration contains a stack store plus the `black_box` empty inline-asm barrier. It is cheaper than the accumulator form because it removes accumulator memory updates, the inner `black_box(i)` reload/use path, and the final accumulator `black_box`.

## Focused hardware verification

Built release and ran a focused hardware check on `/dev/dsa/wq0.0`, pinned to core 0, 200 iterations per row:

```text
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-occupancy \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 200 \
  --submit-occupancies 96,114,128,160 \
  --submit-occupancy-spin-iters <0|1|2|10> \
  --pin-core 0
```

Raw JSON: `hw-eval/results/2026-06-02-blackbox-n-gap/`.

At K=128:

| workload | iters=0 avg prefill ticks | iters=1 avg prefill ticks | delta per descriptor | iters=2 delta per descriptor | iters=10 delta per descriptor |
|---|---:|---:|---:|---:|---:|
| noop | 3,387 | 16,486 | 102 ticks | 137 ticks | 187 ticks |
| 1 MiB memmove | 3,660 | 16,881 | 103 ticks | 139 ticks | 186 ticks |

Compared with the accumulator loop's earlier ~162 ticks/descriptor for iters=1, the simple `black_box(n)` form is materially cheaper, but still large enough to pace the submit train.

## Conclusion

`for n in 0..iterations { black_box(n); }` is better than the accumulator loop: it is simpler, safe Rust, still non-removable, and reduces the iters=1 K=128 gap from about 162 ticks/descriptor to about 102-103 ticks/descriptor.

It is still not a one-cycle delay. One iteration still forces an observable stack store and compiler barrier. For a cycle-calibrated delay knob, use a TSC-targeted wait instead of any `black_box` loop-count proxy.
