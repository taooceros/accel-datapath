# Submission bottleneck experiment results, 2026-05-27

## Question

Following `docs/report/benchmarking/019.submit_occupancy_one_extra_2026-05-26.md`, run the remaining DSA submission-bottleneck experiment setup and answer:

1. whether marker completions become visible while later descriptors are still being submitted;
2. which traffic class first changes the curve;
3. whether completion discovery/reuse policy materially changes sustained batch-size-1 throughput;
4. whether no-tracking over-depth submission loses descriptors.

## Setup

- Binary: `./target/release/hw-eval`
- Device: `/dev/dsa/wq0.0`
- WQ mode: dedicated
- WQ size: 128
- DSA NUMA node: 0
- CPU pin: core 0
- TSC frequency from run metadata: 2202375041 Hz
- Artifacts: `docs/report/benchmarking/submission_bottleneck_2026-05-27/`

Interpretation:

- The submit phase bends in the same place for submit-only, NOOP+completion, 64 B memmove, and 4 KiB memmove: the jump begins at window 120 and is large by 128.
- Adding completion writes lowers end-to-end ops/sec to about 9.1 Mops/s at high window, but it does not move the submit-admission knee.
- 64 B memmove is close to NOOP+completion at high window, so tiny payload DMA is not the first differentiator.
- 4 KiB memmove lowers throughput further, about 6.4 Mops/s at window 256, but its submit phase still bends with the same admission curve.

| packed-scan | 1000000 | 8468433 | 1.00 | 11 | 10 | 0 | 0 |

| batch-harvest | 1000000 | 8526471 | 1.70 | 9 | 3 | 0 | 0 |

Interpretation:

- NOOP window-128 policies are all in the same rough band except `poll-only` and `delayed-reset`, which are slower rather than faster.
- Padding/round-robin does not materially improve NOOP throughput over packed scan.
- `batch-harvest` is similar to packed scan for NOOP and slightly best for memmove64, but not by enough to explain the earlier 116--117 outstanding-operation knee.
- Completion reuse policy is therefore not the first bottleneck named by this run; admission/backpressure remains the controlling effect.

## Attribution

The current bottleneck is DSA WQ/admission backpressure, not raw `movdir64b`, not missing/lost descriptors, and not 64 B payload DMA. The prior submit-occupancy run located the first expensive extra submit at about 116--117 outstanding operations. This run adds that DSA can complete early descriptors while the CPU is still submitting the tail, and that traffic-class/policy changes do not move the submit-phase knee. The practical bound for batch-size-1/no-batch loops on this dedicated WQ should stay below the observed admission threshold rather than the nominal WQ size of 128.
