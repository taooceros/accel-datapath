# Submit occupancy TSC-gap sweep to K=320, 2026-06-02

## Question

When the Experiment 1 TSC-gap pacing removed the submit-latency knee through K=160, was the knee gone or merely shifted beyond the previous occupancy cap?

## Method

Built release `hw-eval` and ran `submit-occupancy` on `/dev/dsa/wq0.0`, pinned to core 0, 200 iterations per row.

Common command shape:

```text
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-occupancy \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 200 \
  --submit-occupancies 96,114,128,160,192,224,256,288,320 \
  --submit-occupancy-gap-tsc <gap> \
  --pin-core 0
```

Workloads:

- `noop`
- `memmove64 --dsa-memmove-bytes 1048576`

Gaps: `0,1,10,25,50,100,150,200,300`.

Artifacts:

- Raw JSON: `hw-eval/results/2026-06-02-tsc-gap-cap320/`
- Summary CSV: `docs/report/benchmarking/045.submit_occupancy_tsc_gap_cap320.summary.csv`

## Finding

The TSC gap shifts the knee right; it does not make the admission limit disappear.

- `gap_tsc=0`: both workloads bend at K=114.
- `gap_tsc=1/10/25`: both workloads bend at K=160 in this coarser extended sweep.
- `gap_tsc=50`: both workloads bend at K=192.
- `gap_tsc=100`: `noop` bends at K=224; 1 MiB `memmove` bends at K=256.
- `gap_tsc>=150`: no median knee through K=320 for either workload.

The high-latency plateau remains about 105-110 ns. Larger pacing gaps mainly delay where the plateau starts.

## Completion/probe notes

For `noop`, the companion prefill completion probe reported all K completions visible at K=320 with zero errors across all gaps.

For 1 MiB `memmove`, the K=320 companion probe usually saw only about 28-35 completions visible immediately after prefill, and some rows reported 3 completion errors in that companion probe. That completion-side behavior does not change the submit-latency observation: the extra-submit knee still shifts with submit pacing while the large payload work remains mostly unfinished.

## Interpretation

This strengthens the admission-pressure interpretation. The knee is a paced-stream threshold: if software submits a raw burst, the extra submit stalls around K=114; if software inserts small TSC gaps, the WQ/device admission path consumes descriptors during the prefill train, so the same measured extra submit stalls only at a larger K. By K=320, a target gap of about 150 TSC ticks is enough to keep both `noop` and 1 MiB `memmove` under the median-latency knee.
