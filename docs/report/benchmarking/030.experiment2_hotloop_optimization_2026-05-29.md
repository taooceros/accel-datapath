# Experiment 2 hot-loop optimization, 2026-05-29

## Change

Experiment 2 (`submit-marker-overlap`) now keeps the submit/poll path allocation-free for the retained trace data:

- `CompletionPollResult` is reused with capacity `n` instead of allocating fresh vectors per poll.
- Per-iteration poll reads are copied into preallocated flat scratch buffers sized by the bounded maximum poll reads for the iteration.
- Per-iteration sample trace points are materialized after the submit loop from those flat buffers, so vector ownership for the JSON shape is not created inside the submit/poll loop.
- Request-completion accumulator updates are deferred until after submit and completion observation; the hot poll path records only observed TSC, status, observed-after-submit index, and marker-relative TSC.
- `TraceAccumulator` vectors for fixed one-sample-per-iteration fields are preallocated with `iterations` capacity.

The JSON field shape is unchanged. Experiment 2 indices remain zero-based.

## Profile command

```bash
launch perf record \
  -F 9999 \

  -o docs/report/benchmarking/submission_bottleneck_2026-05-27/perf_experiment2_next_unfinished_optimized.data \
  -- ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-marker-overlap \
  --device /dev/dsa/wq0.0 \
  --iterations 5000 \
  --marker-bursts 160 \
  --marker-positions first \
  --marker-poll-offsets 0 \
  --dsa-op noop \
  --pin-core 0
```

Perf captured 4951 samples from `hw-eval`, with zero lost samples.

## Before/after findings

Compared with report 029:

- `poll_to_next_unfinished` fell from 41.76% under Experiment 2 to 32.57%.
- `CompletionPollResult::record_read` fell from 6.63% to 0.78%.
- `Vec::grow_one` no longer appears in the optimized Experiment 2 path; the only remaining `grow_one` samples are 0.01% clap startup entries.
- The completion status read/mask path remains the dominant actual poll work: 22.17% in the optimized run.
- `rdtscp` remains visible at 8.71% in the optimized poll path.
- `sample_trace_point` still appears in the full-run profile because the benchmark still materializes the owned JSON-shaped per-iteration vectors after the submit loop; that cost is no longer in the submit/poll hot loop.
- `record_request_completion` is no longer called from `poll_to_next_unfinished`; its accumulator writes happen after the submit loop from the recorded scratch arrays.
