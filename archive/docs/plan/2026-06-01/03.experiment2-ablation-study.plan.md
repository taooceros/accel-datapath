# Experiment 2 ablation-study plan

## Goal

Design the next Experiment 2 run as a controlled ablation study. The goal is to explain why early completions become visible after a small number of traced submit/poll iterations while Experiment 1 reaches submit-admission backpressure around 116--117 outstanding operations.

The study should distinguish three effects that are easy to conflate:

1. elapsed CPU time during the traced submit/poll loop,
2. DSA admission/backpressure depth,
3. completion-record cacheline visibility cost when the CPU first reads DSA-written completion memory.

## Principle

Do not run an uncontrolled full factorial matrix. Use one-factor-at-a-time ablations around a single baseline, then add a small number of targeted two-factor interaction checks only where the first-pass results justify them.

Every non-baseline row should have a sibling baseline with the same `n`, poll offset, operation class, device, core pinning, iteration count, and run block. This keeps comparisons local and reduces drift from hardware state, scheduler noise, or WQ state.

## Experiment picture

Experiment 2 interleaves submit work with completion-frontier observation:

```text
CPU submit order, one logical op per MMIO:

time / submit index  ───────────────────────────────────────────────────▶

                  poll_offset
                      │
                      ▼
req:     [0] [1] [2] ... [K] [K+1] [K+2] ............... [N-1]
submit:   │   │   │       │     │     │                     │
          ▼   ▼   ▼       ▼     ▼     ▼                     ▼
DSA WQ:  enqueue descriptors while CPU continues toward admission wall

poll:                    read next unfinished completion after each submit
                         │
                         ▼
completion frontier:  [done?][done?][done?][none?]...
                         ▲
                         │
                  visible_prefix_len

Question at each K:
  when the CPU first sees completion #j, how many earlier/later
  completions are already visible, and what did the status read cost?
```

The ablation plan keeps this loop shape fixed and changes one variable at a time:

```text
                          baseline loop
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
  frontier timing        marker position        mechanism probes
  n, poll_offset         first / half / last     layout / prefetch /
                                                timing / cache state
        │                      │                      │
        └──────────────────────┼──────────────────────┘
                               │
                        operation control
                         noop vs memmove64
```

Each branch must answer against a nearby sibling baseline, not against an old run.

## Baseline configuration

Use this as the anchor unless a stage explicitly changes one variable:

- selector: `--benchmark submit-marker-overlap`
- operation: `--dsa-op noop`
- burst length: `--marker-bursts 160`
- marker position: `--marker-positions first`
- poll offset: start with `--marker-poll-offsets 1`, then sweep offsets in the frontier stage
- completion layout: packed 32-byte records
- cache state: reset-only
- prefetch: none
- timing mode: per-read timing
- iterations: at least 1000 for exploratory traces; raise only for final confirmation rows
- execution: release binary through `launch`, explicit DSA device, explicit `--pin-core`

The current default `submit-marker-overlap` suite emits both `submit_marker_overlap` and `submit_marker_mechanism` rows. Use `submit-marker-mechanism` only for surgical mechanism-only reruns.

## Poll-offset design

`marker_poll_offset` is the zero-based submit index where the loop starts polling after each subsequent submit. Use a mostly geometric ladder so the scan is standard, compact, and easy to compare across runs:

```text
early/frontier ladder: 1, 2, 4, 8, 16, 32, 64
near-wall sentinels:  96, 112, 115
post-wall sentinel:  128, only for n >= 160
```

Rationale:

- `1,2,4,8,16,32,64` gives a power-of-two view of the early completion frontier without hand-picking around the previous result.
- `96,112,115` are not powers of two; they are hardware-knee controls around the Experiment 1 submit-admission wall at about 116--117 outstanding operations.
- `128` is a clean post-wall power-of-two control, but only for bursts larger than 128. Do not include `128` in an `n = 128` run because polling would start after the submit loop is already complete.
- Keep `0` out of the default matrix. It is useful only as an immediate-poll stress case because it perturbs every submit after request 0.

Use representative offsets `1,16,112` for smaller cross-variable checks: early, mid-ladder, and near-wall.

The only acceptable non-ladder offsets are hypothesis-driven sentinels tied to the known admission wall.


## Stage 1: completion-frontier sweep

Question: does completion visibility track elapsed traced-loop time, or does it track proximity to the Experiment 1 admission wall?

Vary only:

- burst length `n`: `128,160,256`
- poll offset: `1,2,4,8,16,32,64,96,112,115` for all burst lengths; add `128` only for `n = 160,256`

Keep fixed:

- marker position: `first`
- operation: `noop`
- packed layout, reset-only cache state, no prefetch, per-read timing
- same device and pin core

Primary metrics:

- first visible completion submit index
- `first_seen_tsc_from_start`
- `visible_count`
- `visible_prefix_len`
- visible vs `NONE` poll latency
- submit-tail latency near the wall

Expected interpretation:

- If visibility appears after similar elapsed TSC time across offsets and burst lengths, Experiment 2 is mostly measuring elapsed loop time.
- If near-wall offsets change visibility sharply even at similar elapsed time, the admission/backpressure state is interacting with completion visibility.
- If `visible_count` grows while `visible_prefix_len` does not, completions are visible out of prefix order and the analysis should not treat the marker alone as the frontier.

## Stage 2: marker-position controls

Question: is the observation tied to the first submitted descriptor, or to elapsed time and queue progress?

Vary only:

- marker position: `first,half,last`

Run at:

- `n = 160`
- poll offsets: `1,16,112`

Keep all mechanism variables at baseline.

Expected interpretation:

- If `first` becomes visible early but `last` does not, visibility follows submit order.
- If `last` also becomes visible soon after sufficient elapsed time, the poll timing may be observing a bulk completion frontier rather than a marker-specific event.
- `half` is the sanity check between those extremes.

## Stage 3: mechanism ablations

Question: what causes the expensive visible-status read: first CPU touch of a DSA-written cacheline, measurement fencing, prefetchability, or CPU cache state?

Run at:

- `n = 160`
- marker position: `first`
- poll offsets: `1,16,112`
- operation: `noop`

Use the existing mechanism rows:

| Variable | Baseline | Ablation rows | What it tests |
|---|---|---|---|
| completion layout | `baseline/packed-32b` | `layout/padded-64b` | Whether the every-other visible-read pattern is caused by two 32-byte completion records sharing a 64-byte line. |
| prefetch | no prefetch | `prefetch-1-lines`, `prefetch-2-lines`, `prefetch-4-lines` | Whether software prefetch can hide DSA-written line visibility cost. |
| measurement method | per-read `rdtscp` timing | `measurement/batch-scan-timing` | Whether per-read serialization exaggerates production-style scan cost. |
| cache state | reset-only | `cache-state/pre-touch`, `cache-state/clflush` | Whether CPU pre-submit cacheline ownership changes first-visible read latency. |

Primary metrics:

- `visible_poll_ns` median/p90/p99
- `none_poll_ns` median/p90/p99
- `line_position_0_visible_ns`
- `line_position_1_visible_ns`
- `same_line_first_visible_ns`
- `same_line_second_visible_ns`
- `poll_window_ns` and `poll_window_reads` for batch-scan timing
- `baseline_comparison` deltas and ratios

Expected interpretation:

- If `padded-64b` removes the cheap second-record effect, the pair pattern is cacheline sharing.
- If prefetch rows do not move visible latency, the bottleneck is not trivially hidden by CPU prefetch at these distances.
- If batch-scan timing is much cheaper per visible read, the per-read measurement fence is part of the observed cost.
- If `pre-touch` or `clflush` shifts the visible distribution, CPU cacheline state before DSA writes matters.

## Stage 4: operation-class control

Question: does payload work change the visibility frontier, or is this a submission/completion-memory effect?

Vary only:

- operation: `noop`, then `memmove64`

Run at:

- `n = 160`
- marker position: `first`
- poll offsets: `1,16,112`

Use `memmove4k` only if `memmove64` changes the conclusion; otherwise it adds payload/cache effects before the submit/completion question is settled.

Expected interpretation:

- If `noop` and `memmove64` have the same frontier and visible-read cost, the behavior is dominated by submission/completion mechanics.
- If `memmove64` shifts first-visible timing or visible-count growth, payload execution time is part of the effect and should be separated from pure admission depth.

## Stage 5: targeted interaction checks

Run these only after Stages 1--4 identify a main effect. Do not expand to all combinations.

Recommended interaction checks:

1. `layout x poll_offset`: packed vs padded at offsets `1,16,112`.
2. `cache_state x layout`: reset-only vs clflush for packed and padded at offset `16`.
3. `operation x poll_offset`: noop vs memmove64 at offsets `1,16,112`.

Skip interactions whose main effect was flat in Stage 3.

## Run-block discipline

Use blocked runs so every comparison has a nearby baseline:

1. run baseline block,
2. run one ablation block,
3. rerun baseline block,
4. compare ablation against the average or bracketing baseline, not against an old trace from a different day.

Keep command metadata with every artifact:

- git revision or working-tree diff summary,
- release build command,
- full `launch` command,
- device path,
- pin core,
- iterations,
- `tsc_freq_hz`,
- result JSON path,
- plot/CSV paths.

## Acceptance criteria

The study is complete when the report can answer these questions with artifact-backed tables and plots:

1. At each poll offset, how much elapsed TSC time has passed before the first visible completion?
2. Near the 116--117 submit-admission wall, are early completions already visible, and how many are visible?
3. Does the visible-read cost come from first CPU touch of DSA-written completion cachelines?
4. Do layout, prefetch, cache state, or measurement method materially change the visible-read distribution?
5. Does `memmove64` preserve or change the `noop` conclusion?
