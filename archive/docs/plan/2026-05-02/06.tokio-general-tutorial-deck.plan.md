# Tokio general tutorial deck plan

## Goal

Create a general advisor-facing tutorial deck for Rust Tokio async. This revision intentionally avoids hardware-integration framing and skips `stdexec` for now. The deck should explain the Tokio mental model clearly enough that a systems advisor can understand what a future is, how polling/wakers work, why tasks have lifetime constraints, and why Rust async design often feels harder than simply writing sequential code.

## Scope

In scope:

- A standalone Typst prototype deck under `presentation/2026-05-02/`.
- Focus on Tokio / Rust async fundamentals.
- Include the lifetime challenge as a first-class teaching point.
- Use simple diagrams, pseudo-code, and plain language.
- Use Tinymist live preview plus browser screenshots for layout iteration.

Out of scope:

- No `stdexec` slides in this first tutorial version.
- No project-specific DSA/IAX hardware integration details.
- No performance claims or benchmark results.
- No exhaustive Rust async reference.


## Tutorial structure principle

The deck should be organized as a chain of necessity, not as a glossary of Tokio terms. Every concept should answer a concrete pressure created by the previous slide.

Story spine to preserve:

```text
Blocking API is readable
→ but many waits park many OS threads
→ so we multiplex fewer workers with an event loop
→ but each paused operation now needs its own continuation representation
→ C does this manually with context structs and callbacks
→ Go hides it in stackful, userspace-thread-like goroutines
→ Rust/C++ expose it as stackless future/coroutine state machines
→ Tokio schedules and wakes Rust Future values
→ spawn moves futures into runtime-owned tasks
→ ownership, lifetime, Send, and Pin constraints become visible
```

Per-slide template:

1. **Pressure**: what problem forces this idea to exist?
2. **Mechanism**: what concrete thing stores state, moves control, or wakes work?
3. **Consequence**: what rule should the audience remember?

Do not introduce Tokio terminology before the audience has seen why it is needed. Start with blocking calls and the cost of many waiting threads; introduce Future, poll, Waker, task, lifetime, Send, and Pin only as answers to the continuation/scheduling problems already established.

## Slide design

### Slide 1: Title and audience contract

Takeaway: this is a tutorial for understanding Tokio's execution model, not a performance or hardware report.

Visual: title plus a compact roadmap: `async fn` → `Future` → `poll` → `Waker` → `Task` → `lifetime constraints`.

### Slide 2: The sequential illusion

Takeaway: `async fn` looks sequential, but it returns a future that can pause and resume.

Visual: left side pseudo-code with two `.await` points; right side timeline showing `run`, `yield Pending`, `resume`, `complete`.

### Slide 3: Future as a state machine

Takeaway: a Rust future is a value that stores its own progress and local state between polls.

Visual: state machine boxes: `Start` → `Waiting for read` → `Waiting for write` → `Done`. Add a small note: locals used after `.await` become part of the future state.

### Slide 4: Poll, Waker, and executor

Takeaway: Tokio does not magically run async code; the runtime polls futures, and wakers tell it when polling might make progress.

Visual: loop diagram: `Tokio executor` → `poll future` → `Pending + store Waker` → `I/O ready / timer fires` → `wake task` → `poll again`.

### Slide 5: Tokio tasks and `spawn`

Takeaway: a Tokio task is the runtime's unit of scheduling; spawned tasks can outlive the caller and can move between worker threads.

Visual: task cards moving between worker threads. Bullets: lightweight task, scheduler-managed, `JoinHandle`, cancellation on runtime shutdown. Emphasize `tokio::spawn` requires `Future + Send + 'static` in common multi-threaded use.

### Slide 6: The lifetime challenge

Takeaway: Rust async lifetimes are hard because references may be captured inside a future across suspension points.

Visual: `.await` gap with borrowed `&config` or `&mut buffer` spanning across it. Contrast two cases:

- awaited in the same scope: borrowed future can be okay;
- spawned task: must usually own data or use `Arc`, because `spawn` requires `'static`.

### Slide 7: `Send` and data held across `.await`

Takeaway: what matters is not every temporary variable, but the state that remains live across `.await`.

Visual: before/after `.await` split; mark `Rc` dropped before `.await` as okay, `Rc` used after `.await` as not `Send`. Include practical rule: keep non-`Send` values out of cross-await state, or use `LocalSet` when appropriate.

### Slide 8: `Pin` in one slide

Takeaway: `Pin` exists because async state machines can become address-sensitive after polling.

Visual: future object before poll can move; after poll, internal references may point into its own state, so movement is constrained. Keep this conceptual; do not dive into unsafe projection details.

### Slide 9: Practical design rules

Takeaway: good Tokio code makes ownership and wakeup boundaries explicit.

Visual: checklist card:

- own data when spawning;
- prefer `Arc` for shared long-lived state;
- keep borrows within one awaited scope when possible;
- avoid holding locks across `.await`;
- use channels for task communication;
- make cancellation/drop behavior explicit.

### Optional slide 10: How this differs from C++ coroutine syntax

Only include if useful after the Tokio tutorial is clear. Takeaway: both preserve continuation state, but Rust adds explicit ownership, lifetime, `Send`, and `Pin` constraints at the type level.
