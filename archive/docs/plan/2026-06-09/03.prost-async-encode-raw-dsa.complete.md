# Async encode_raw Prost DSA plan

Status: complete

## Goal

Add an opt-in async Prost encoding path that lets generated messages encode `string` and `bytes` payload copies through an async sink, while preserving ordinary Prost and Tonic behavior.

The implemented path keeps protobuf structure on the CPU: field keys, length varints, scalars, map entry structure, message/group delimiters, and field order are still written synchronously by generated code. Only the payload bytes of `string` and `bytes` fields are routed through the async payload-copy hook.

## Implemented shape

```text
Tonic Encoder owns message + EncodeBuffer
  -> DsaAsyncProstEncoder returns Tonic's owned encode future
      -> prost::transfer::encode_message_to_sink performs Prost capacity/framing checks
      -> generated Message::encode_raw_async preserves encode_raw field order
          -> CPU writes protobuf keys, lengths, scalars, maps, groups, and nesting
          -> string/bytes helpers call AsyncEncodeSink::put_payload(payload)
              -> CPU copy for no-DSA or below-policy-threshold cases
              -> async DSA memmove for selected large payloads
          -> generated code resumes after DSA completion before later fields
  -> Tonic emits the completed frame through its existing body state
```

There are no reserved middle holes and no Tonic framing/body-state changes.

## Prost changes

- Added `prost::transfer::AsyncEncodeSink` as the hardware-neutral sink used by generated async encoding.
- Added `prost::transfer::BufMutEncodeSink` for CPU-backed async encoding against an existing `BufMut`.
- Added `prost::transfer::encode_message_to_sink`, preserving Prost capacity checks and optional length delimiter handling before delegating to `Message::encode_raw_async`.
- Added `Message::encode_raw_async` beside the existing hidden `encode_raw` method. The default implementation delegates to `encode_raw`, so existing manual `Message` implementations keep CPU behavior.
- Kept `Message::encode`, `Message::encode_raw`, `CpuEngine`, and `AsyncEncodeExt` behavior unchanged.

## Generated code changes

`prost-derive` now emits an `encode_raw_async` override for derived messages. The generated body mirrors the synchronous field order.

- Numeric scalar fields call the existing synchronous encoding helpers through `AsyncEncodeSink::buf_mut`.
- Messages and map/oneof variants with no accelerator-eligible payloads delegate async encoding back to the existing synchronous encode path.
- `string` and `bytes` fields call `encoding::string::encode_async` and `encoding::bytes::encode_async`.
- Repeated `string` and `bytes` fields call async repeated helpers.
- Oneof, nested message, group, and map codegen all participates in the async path; map entry structure remains CPU-written while string/bytes map key/value payload copies can use the async payload hook.
- Wrapper `Message` implementations for `String`, `Vec<u8>`, and `bytes::Bytes` override `encode_raw_async` to use the async string/bytes helpers.

## DSA integration

DSA-specific code is contained in `tonic-dsa-bytes-async/src/prost_codec.rs`.

Added:

- `DsaAsyncProstCodec<T, U>`
- `DsaAsyncProstEncoder<T>`
- `DsaAsyncProstEncode`
- `DsaAsyncProstDecoder<U>`

`DsaAsyncProstEncoder<T>` uses Tonic's existing owned encode future boundary. The future owns the message, the `EncodeBuffer`, and the selected work-queue policy. Its sink implementation uses CPU writes for protobuf structure and routes only payload slices through DSA when the configured policy selects hardware.

If no work queue is selected, or the policy threshold does not select DSA for a payload, the payload is copied on the CPU. If DSA is selected, submission/completion failures are returned as encode errors; the encoder does not silently fall back to CPU after selection.

## Completion criteria

- Derived messages expose both synchronous `encode_raw` and async `encode_raw_async`.
- CPU async encoding is byte-for-byte equivalent to existing Prost encoding for generated string/bytes, nested, oneof, repeated, and map cases covered by the targeted test.
- Large string/bytes fields can return `Poll::Pending` through Tonic's existing owned encode future and resume after completion.
- Selected DSA copies complete into Tonic's encode buffer without exposing uninitialized bytes on the successful smoke path.
- Hardware smoke confirms large protobuf string/bytes fields encode and decode correctly through the DSA async path.

No performance claim is made here; this is correctness and hardware-smoke completion only.
