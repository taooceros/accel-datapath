# Tokio tutorial deck — C async composition slide plan

## Goal

Add one advisor-facing slide to `presentation/2026-05-02/tokio_general_tutorial.typ` that uses Eric Niebler's “What are senders good for anyway?” motivation to sharpen the transition from manual C callback APIs to higher-level async abstractions.

## Scope

- Insert the slide after `C callbacks make the continuation explicit` and before `Go is stackful; Rust/C++ futures are stackless`.
- Keep the deck a general Rust/Tokio async tutorial.
- Mention C++ sender/receiver only as a lightweight example of making async operations composable; do not add a `stdexec` comparison section.
- Preserve the problem-by-problem spine: blocking calls → event-loop multiplexing → explicit continuations → higher-level continuation representations → Rust futures → Tokio runtime.

## Intended content

The new slide should explain:

- The concrete example is `read file + timeout + CPU-pool parse + event-loop report`.
- A single C callback API is acceptable locally; the pain appears when several async APIs must be combined.
- The example should show that the context object must preserve buffers, winner state, late-callback safety, scheduler handoffs, error propagation, and cleanup.
- Async/await and sender/receiver address the same pressure by giving async operations a uniform shape for reusable composition steps such as `timeout`, `then`, `when_all`, and scheduler hops.
