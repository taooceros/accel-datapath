# Tokio tutorial Go/Rust motivation revision plan

## Goal

Revise the early motivation slides so they do not imply that Rust async is merely about avoiding blocked OS threads. The audience should see the deeper motivation: when work suspends, its continuation must live somewhere; Go and Rust make different choices about where that suspended state lives and who checks it.

## Scope

In scope:

- Revise the first motivation slide around continuation placement rather than blocked-thread avoidance alone.
- Add an explicit Go vs Rust comparison to the saved-continuation slide.
- Preserve the existing slide count and overall tutorial flow.

Out of scope:

- Detailed Go scheduler internals.
- Claims about performance superiority.
- Hardware or benchmark material.

## Intended slide changes

- Replace the first motivation slide title with `Waiting work needs a place to put its continuation`.
- Reframe the slide text around the continuation: when operation A waits, its locals and next instruction must remain somewhere while the worker runs B/C.
- Replace the three bottom cards with `OS thread per wait`, `Go goroutine`, and `Rust async Future`.
- Replace the `Rust checks the saved continuation` slide with a direct comparison:
  - Go: goroutine stack holds the continuation; runtime parks/resumes it; code can look blocking.
  - Rust: `Future` value holds the continuation; `.await` marks suspension; compiler checks ownership, lifetimes, `Send`, and `Pin`.
