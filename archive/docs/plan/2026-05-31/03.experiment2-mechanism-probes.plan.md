# Experiment 2 mechanism probes implementation plan

## Goal

Turn the follow-up Experiment 2 cacheline/coherence questions into runnable sub-experiments under the submission-bottleneck benchmark code, with design documentation that explains the probe set and expected interpretation.

## Scope

- Add an Experiment 2 mechanism-probe module under `hw-eval/src/benchmarks/submission_bottleneck/`.
- Keep the probes framed as Experiment 2 sub-experiments rather than a new top-level research question.
- Add a focused CLI selector for the probe runner so existing `submit-marker-overlap` JSON remains stable.
- Add result types for the probe rows without changing existing `submit_marker_overlap` rows.
- Cover the locally actionable probes: completion layout, cacheline pair behavior, CPU prefetch, measurement method, and completion cache state.
- Write a durable design report in `docs/report/benchmarking/` and a local module design note beside the implementation.

## Intended implementation

- Add `BenchmarkKind::SubmitMarkerMechanism` with selector `submit-marker-mechanism`.
- Add `SubmitMarkerMechanismResult` rows serialized as `submit_marker_mechanism`.
- Implement variants as rows with a `sub_experiment` and `variant` string:
  - baseline: one packed 32-byte, reset-only, no-prefetch, per-read timing row
  - layout: 64-byte padded records compared against baseline
  - cacheline pair: first vs second completion record within a 64-byte line, recorded in baseline and comparable rows
  - prefetch: one/two/four cachelines ahead compared against baseline
  - measurement: batch-scan timing compared against baseline
  - cache state: pre-touch and clflush compared against baseline
- Record completion base alignment (`%64`, `%4096`), stride, line-position stats, visible/none read latency, poll-window stats where applicable, completion outcome counts, and median nanosecond gaps/ratios against baseline for non-baseline rows.

## Verification

- Rust unit tests for the new probe metadata and layout math.
- CLI contract tests for the selector and DSA-only validation.
- `cargo test -p hw-eval submit_marker_mechanism`
- `cargo test -p hw-eval cli_contract`
- `cargo build --release -p hw-eval`
- A small hardware smoke run through `launch` if the build and tests pass.
