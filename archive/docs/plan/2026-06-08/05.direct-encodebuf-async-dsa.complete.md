# Direct EncodeBuf async DSA copy

## Goal

Remove the staged destination buffer from `tonic-dsa-bytes-async` and submit async DSA directly into Tonic's encode buffer, under the explicit experiment assumption that the reserved buffer memory remains stable while `poll_encode` returns `Pending`.

## Scope

- Target crates: `tonic` and `tonic-dsa-bytes-async`.
- Add a low-level delayed initialization API to `EncodeBuf` for experiments that reserve capacity, return `Pending`, and commit initialized bytes later.
- Change async DSA encode state to hold a raw destination pointer and length instead of a staged `BytesMut`.
- Keep drop-time completion draining before any buffer storage can be released.
- Update benchmark/report notes to remove the staged-copy caveat.

## Intended changes

- Add doc-hidden `EncodeBuf` methods for reserving uninitialized capacity and later advancing initialized length.
- Rewrite `PendingDsaCopy` to own source bytes, descriptor, completion, destination pointer, and length.
- On first poll, reserve/touch the final encode buffer and submit DSA; on completion, advance the buffer length exactly once.
- Keep CPU fallback unchanged.

## Verification plan

- Format affected crates.
- Run async crate check/tests/clippy, including the ignored hardware smoke test through `launch`.
- Run neutral benchmark crate check/clippy/release build.
- Run a short hardware comparison through `launch` to confirm the direct path completes.

## Completed changes

- Added doc-hidden `EncodeBuf::reserve_uninit_slice_for_pending` and `EncodeBuf::advance_reserved_uninit_slice`.
- Threaded a stable-buffer flag through Tonic's in-flight encode state so buffered prefixes are not split while an encoder holds a direct pending reservation.
- Rewrote `tonic-dsa-bytes-async` pending DSA state to hold a raw destination pointer and length instead of a staged `BytesMut`.
- Kept drop-time DSA completion draining before pending state release.
- Updated the comparison report with direct-buffer hardware results.
