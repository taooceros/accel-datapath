# Tokio shared-WQ sweep constrained to one NUMA node

## Scope

Device: `/dev/dsa/wq0.1` shared WQ, direct/no-batch DSA memmove (`batch_n = 1`). Tokio was run through:

```bash
launch numactl --cpunodebind=0 --membind=0 ./target/release/tokio_memmove_bench ...
```

NUMA node 0 CPUs: `0-31,64-95` (64 logical CPUs).

Thread counts swept: `1,2,4,8,16,32`, plus `64` as the full single-node CPU count.

## Raw hw-eval NUMA0 spot-check

To avoid comparing NUMA-local Tokio against unconstrained raw, `hw-eval` was also spot-checked under the same NUMA binding for the high thread counts:

| raw threads | 128B | 256B | 1024B | 4096B | overall best |
|---:|---:|---:|---:|---:|---:|
| 32 | 39.573 | 32.451 | 23.509 | 7.008 | 39.573 Mops/s |
| 64 | 31.715 | 34.483 | 22.130 | 6.732 | 34.483 Mops/s |

Under single-NUMA binding, Tokio at 32 threads reaches 46.384 Mops/s on 128B, which is higher than the 32-thread raw spot-check for that size. This should be treated as a prompt for repeat runs and deeper methodology inspection, not as a final overhead claim.

## Takeaways

- Constraining Tokio to one NUMA node fixes the severe high-thread collapse seen in unrestricted runs.
- Best Tokio point observed: **46.384 Mops/s** at 32 threads, 128B messages, concurrency 128.
- Increasing Tokio from 32 to 64 threads did **not** improve peak throughput; it dropped to 33.443 Mops/s for 128B.
- NUMA locality matters substantially for shared-WQ ENQCMD multi-thread submission.
- For a final claim, rerun key points with repeats and run hw-eval/Tokio under identical NUMA and thread/concurrency settings.
