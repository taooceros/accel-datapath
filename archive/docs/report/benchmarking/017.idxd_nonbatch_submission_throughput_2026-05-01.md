# idxd-rust non-batched submission throughput update — 2026-05-01

## Summary

Implemented a hardware benchmark row for raw non-batched DSA submission throughput:

- Row name: `raw_nonbatch_submission_throughput`
- Backend: hardware
- Critical path: preallocated descriptor/completion/source/destination slot ring
- Validation in timed loop: completion status only
- Full byte validation: post-run samples outside timing
- Submission style: one ENQCMD per operation; no MMIO batching and no DSA batch descriptors

This removes the public async future path (`HashMap`, `Arc<PendingOperation>`, `oneshot`, and per-operation ownership/container overhead) from the measured hardware row.

## Critical-path changes

- Added a benchmark-local slot ring in `idxd-rust/src/bin/tokio_memmove_bench/nonbatch.rs`.
- Reuses per-slot descriptor, completion record, source buffer, and destination buffer.
- Prefaults source and destination buffers before timing.
- Reuses descriptors on the success path and only clears the completion status byte before resubmission.
- Uses DSA cache-control flags unset for the benchmark path so the destination write is directed to memory rather than allocating destination cache lines in the hot loop.
- Keeps unsafe limited to low-level descriptor submission and completion-record reset helpers with `SAFETY:` comments.

## Tooling/schema changes

- Hardware artifacts now emit `raw_nonbatch_submission_throughput`.
- Software diagnostic artifacts still emit `raw_async_throughput`.
- `verify_tokio_memmove_bench.sh` and `bench_async_throughput_matrix.sh` now understand the hardware row.
- Added `IDXD_RUST_VERIFY_MIN_OPS_PER_SEC` / `IDXD_RUST_BENCH_MIN_OPS_PER_SEC` for message-rate thresholds.

## Measurements

Prepared host/device:

- Device: `/dev/dsa/wq0.1`
- Binary: `target/release/tokio_memmove_bench`
- Launcher: `tools/build/dsa_launcher`
- Validation: `completion-only`
- Max page-fault retries: `64`
- Duration: `1000 ms`

For comparison, the earlier public async-future row peaked around `1.1M ops/sec`, so the non-batched slot-ring row improves small-message throughput by roughly 4.6x on the best current sample and about 2.2–4.6x across repeated 64-byte runs.

## Caveats

- Results vary substantially between consecutive runs, likely due to scheduling/core placement and host load. The current implementation can reach the expected ~5M ops/sec non-batched ceiling, but it does not yet hold that rate stably on every sample.
- The public async API is not yet rebuilt around this slot-ring core. This report proves the overhead gap and establishes a faster hardware-ceiling benchmark row; moving the same shape into the public runtime remains a follow-up design slice.
- A later attempt to rerun the matrix through `devenv shell -- launch` hit a host `devenv.nix` evaluation failure unrelated to the benchmark binary. Direct `tools/build/dsa_launcher ... tokio_memmove_bench` runs continued to work.

## Next steps

1. Stabilize CPU placement for the benchmark runner or launcher before using a hard 5M ops/sec threshold.
2. If 5M remains out of reach after pinning/noise control, profile the slot-ring path directly.
3. Move the ring/slab completion model into internal `idxd-rust` direct runtime code so the safe public async API can avoid per-operation `HashMap`/`oneshot`/`Mutex<Option<_>>` overhead.
