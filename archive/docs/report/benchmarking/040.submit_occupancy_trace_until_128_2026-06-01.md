# Submit-occupancy trace-until-128 probe, 2026-06-01

## Question

Instead of timing only one additional descriptor after a K-prefill, time every post-prefill submit until total submitted reaches 128.

## Code path

Added `--submit-occupancy-trace-until <N>` for `--benchmark submit-occupancy`. When set, each JSON `submit_occupancy` row includes `extra_submit_trace`, a single-iteration list of `{ submit_index, submit_tsc_ticks, submit_ns }` for every measured submit from `k_prefill` through `N - 1`.

The existing `extra_submit_ns` field remains the first post-prefill submit, preserving the old one-extra meaning.

## Command shape

Each measured run was warmed first, then captured with one iteration:

```bash
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-occupancy \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 1 \
  --submit-occupancies 0,32,64,96,112 \
  --submit-occupancy-trace-until 128 \
  --dsa-op <noop|memmove64> [--dsa-memmove-bytes N] \
  --pin-core 0
```

Artifacts are in `docs/report/benchmarking/submit_occupancy_huge_memmove_2026-06-01/trace_until_128_*.json`.

## Interpretation

The trace-until-128 mode does **not** show every submit after the known knee staying on the ~200 ns plateau. Instead, most submits remain near 9--13 ns, with localized stalls near the initial submit after prefill or around submit indexes 112--116 depending on payload and prefill.

This changes the interpretation of the original one-extra plateau: it is not simply “all later submits are slow once occupancy exceeds 116.” The slow event is localized and sensitive to where the timed submit lands relative to hardware admission/completion progress. Once the loop keeps submitting, completions/admission state can advance and later submits often become cheap again.

The result still supports an admission/front-end threshold rather than payload-throughput control, because NOOP, 64 KiB, 256 KiB, and 1 MiB all show the same localized submit-index region while payload completion cost differs substantially.
