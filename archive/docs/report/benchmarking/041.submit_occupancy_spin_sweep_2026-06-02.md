# Submit occupancy black-box loop sweep, 2026-06-02

## Question

Does manually slowing Experiment 1's submit loop change the first submit-latency knee differently for `noop` and a large `memmove` workload?

## Method

Built `hw-eval` release and ran `submit-occupancy` on `/dev/dsa/wq0.0`, pinned to core 0, 200 iterations per row. The inter-submit delay is now a `std::hint::black_box` CPU loop, not `spin_loop()`/`pause`.

Common command shape:

```text
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-occupancy \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 200 \
  --submit-occupancies 96,108,112,114,115,116,120,124,128,136,144,160 \
  --submit-occupancy-spin-iters <iters> \
  --pin-core 0
```

Workloads:

- `noop`
- `memmove64 --dsa-memmove-bytes 1048576` (1 MiB per descriptor)

Iteration values: `0,1,2,5,10,20,50,100,1000,10000`.

Artifacts:

## Finding

With a black-box loop, the no-delay row still bends at K=114 for both workloads. Adding even one black-box iteration between submits removes the median submit-latency knee through K=160 for both `noop` and 1 MiB `memmove`.

This is a stronger version of the earlier pause-loop result: a very small amount of non-`pause` CPU work between MMIO submissions gives the WQ/device admission path enough time to consume descriptors and avoid the measured submit stall. The large-memmove row behaves the same at the submit-admission level, so the Experiment 1 knee remains best explained as admission/descriptor-consumption pressure rather than payload completion.
