# Submit-marker all request completion times, 2026-05-27

## Question

The marker-specific `first_marker_seen` path was too narrow. We now record the observed completion time for every request in the burst, so the marker is just request 1 in the same per-request table rather than a special hot-loop case.

## Change

Experiment 2 now keeps per-iteration first-observed completion timestamps for every submitted request:

- `request_completions[].completion_tsc_ticks`: first observed completion time minus that request's submit-start TSC.
- `request_completions[].observed_after_submit_index`: submit index at which the request was first observed complete.
- `request_completions[].observed_from_marker_tsc`: first observed completion time minus the marker submit-start TSC.
- `request_completions[].success_count/error_count`: completion status classification over iterations.

The hot loop polls submitted requests that have not yet been observed. The old marker-visible row field is retained for compatibility, but it is derived from request 1's recorded completion observation rather than from a separate first-marker path.

## Interpretation

The per-request table separates two concepts that the marker-only path conflated:

1. request-local completion latency, measured from that request's own submit start; and
2. absolute progress through the burst, measured from the marker submit start.

Later NOOP requests complete in roughly the same sub-microsecond range from their own submit start, but their `observed_from_marker_tsc` grows because their submit happens later in the CPU burst.
