# Tonic mock bytes RPC throughput — 2026-06-08

## Benchmark shape

Standalone executable: `accel-rpc/tonic/tonic-dsa-bytes-sync/src/bin/mock_bytes_rpc_throughput.rs`.

The benchmark starts a real Tonic TCP server and client on localhost. The service is a unary mock bytes RPC:

```text
client Bytes payload -> tonic request encode -> HTTP/2 -> server raw Bytes decode
server echoes the Bytes -> tonic response encode -> HTTP/2 -> client raw Bytes decode
```

The application body does not do protobuf work or business logic. The standard codec uses CPU `BufMut::put` for encode. The DSA codec uses `DsaBufCodec` with `/dev/dsa/wq0.0`. Both paths use the same raw bytes decoder.

The executable validates echoed payload bytes before timing and checks echoed length during the timed loop. Throughput uses concurrent unary RPCs over Tonic `Channel` clones. The server accepts sockets with `TCP_NODELAY` and shuts each per-row server down after measurement.

## Command

Built from `accel-rpc/tonic`:

```bash
cargo build --release -p tonic-dsa-bytes-sync --bin mock_bytes_rpc_throughput
```

Ran from repo root through the DSA launcher so the process has `CAP_SYS_RAWIO`:

```bash
launch accel-rpc/tonic/target/release/mock_bytes_rpc_throughput \
  --codec both \
  --requests 5000 \
  --concurrency 64 \
  --warmup 256 \
  --dsa-wq /dev/dsa/wq0.0
```

## Crossover follow-up

Forced-DSA (`--dsa-min-message-bytes 1`) sweeps were noisy below 1 MiB. Single runs alternated between DSA wins and losses at 16 KiB through 512 KiB, so there is no stable crossover in that range from this end-to-end benchmark.

Larger payloads were more consistent. Average of two 2k-request runs:

| payload bytes | standard one-way MiB/s | dsa one-way MiB/s | dsa / standard |
|---:|---:|---:|---:|
| 1048576 | 1212.00 | 1226.22 | 1.01x |
| 2097152 | 1017.84 | 1151.62 | 1.13x |
| 4194304 | 1083.27 | 1302.37 | 1.20x |

A threshold-policy run with `--dsa-min-message-bytes 1048576` preserved CPU fallback below 1 MiB and showed DSA wins at 1 MiB, 2 MiB, and 4 MiB in that run. Because the below-threshold rows still showed ordinary run-to-run variance, this should be treated as policy validation, not as a precise crossover measurement.

## Isolated encoder check

The isolated encoder benchmark confirms the expected hardware-copy behavior: DSA is slower than CPU copy for small and medium messages when measuring only the encode copy path.

Command:

```bash
TONIC_DSA_WQ=/dev/dsa/wq0.0 launch bash -lc 'cd accel-rpc/tonic && cargo bench -p tonic-dsa-bytes-sync --bench buf_codec'
```

Observed:

| payload | software ns/iter | DSA ns/iter | DSA / software |
|---:|---:|---:|---:|
| 4 KiB | 123 | 1402 | 11.40x slower |
| 64 KiB | 1483 | 3523 | 2.38x slower |
| 1 MiB | 33340 | 37470 | 1.12x slower |

This means the small-message e2e rows must not be interpreted as DSA hardware being faster for tiny copies. The copy itself is slower; framework scheduling, h2/Tonic overhead, allocator behavior, and run-to-run variance dominate the small-message e2e measurements.

## Profiling follow-up

Profiles were collected with `perf record -F 199 -g` through `launch`.

Small payload, 64 B:

| codec | req/s under perf | dominant flat samples |
|---|---:|---|
| standard | 39165.36 | `std::sys::sync::mutex::futex::Mutex::lock_contended` 30.80%, Tokio scheduler ~6.4%, `__memmove_avx512_unaligned_erms` 1.73% |
| dsa | 29787.36 | `std::sys::sync::mutex::futex::Mutex::lock_contended` 29.92%, Tokio scheduler ~6.3%, `DsaOperation::poll` 1.21%, DSA encode closure 0.91%, `__memmove_avx512_unaligned_erms` 1.88% |

For 64 B, the profile is dominated by RPC/runtime synchronization, not copying. DSA-specific work appears but is small relative to Tonic/h2/Tokio overhead; under profiling, forced DSA was slower.

Large payload, 4 MiB:

| codec | req/s under perf | dominant flat samples |
|---|---:|---|
| standard | 314.37 | `__memmove_avx512_unaligned_erms` 49.66%, `bytes::bytes_mut::shared_v_drop` 5.72%, `realloc` 3.50% |
| dsa | 277.37 | `__memmove_avx512_unaligned_erms` 29.66%, DSA encode closure 10.59%, `DsaOperation::poll` 2.53%, `bytes::bytes_mut::shared_v_drop` 7.31% |

For 4 MiB, the profile shifts from CPU memcpy toward DSA encode/poll work, but `memmove` remains significant because not every copy in the RPC path is replaced by DSA.

## Takeaway

At concurrency 64 in this mock bytes RPC benchmark, DSA is not meaningfully beneficial for small payloads. The isolated copy path is slower through at least 1 MiB, and the e2e small-message results are dominated by framework overhead and variance. In the e2e mock RPC, benefits become more plausible around 1 MiB and are more consistent in the 2–4 MiB range. A defensible policy from the current evidence is to leave small payloads on CPU and only try DSA at roughly 1 MiB or larger until a broader, lower-variance sweep says otherwise.
