# Tokio async memmove vs fixed hw-eval batch-size-1 baseline

## Scope

This comparison uses only direct/no-MMIO-batch DSA memmove rows:

- Raw baseline: fixed `hw-eval`, `benchmark == "memmove"`, conceptual `batch_n = 1`.
- Async wrapper: `tokio_naive_direct_descriptor`, `batch_n = 1`.
- Device: `/dev/dsa/wq0.0`.
- Raw command used `--iterations 5000 --sizes 128,256,1024,4096 --max-concurrency 128 --pin-core 2`.

The fixed `hw-eval` run includes the initial sliding-window submissions in the timed interval, so it avoids the earlier short-run overcount artifact.

## Best comparable points

- 128B: async best 6.225 Mops/s at concurrency 128; raw same point 9.384 Mops/s; async keeps 66.3%.
- 256B: async best 7.310 Mops/s at concurrency 64; raw same point 9.374 Mops/s; async keeps 78.0%.
- 1024B: async best 5.255 Mops/s at concurrency 64; raw same point 9.395 Mops/s; async keeps 55.9%.
- 4096B: async best 4.725 Mops/s at concurrency 64; raw same point 7.218 Mops/s; async keeps 65.5%.

## Takeaway

With the corrected raw batch-size-1 baseline, the no-batch direct MMIO ceiling is about 9.4 Mops/s for 128B-1024B warm-cache messages and about 7.3 Mops/s for 4096B. The naive Tokio wrapper peaks at 7.31 Mops/s for 256B and loses about 22% at its best small-message point. More typical high-concurrency losses are about 34%-54%, and the worst common point here is 68% loss at 1024B/concurrency 128.
