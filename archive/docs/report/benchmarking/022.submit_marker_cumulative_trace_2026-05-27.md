# Submit-marker cumulative trace, 2026-05-27

## Question

With Experiment 2 polling only one completion record, the offset-1 run still reported roughly 1.2k TSC ticks from marker submit start to first observed marker completion. The question was what contributes to that interval when individual submit slices are around 20--30 ticks and the first successful poll is around 200--240 ticks.

## Change

Experiment 2 now records cumulative TSC offsets from the marker submit start for each trace point:

- `submit_start_from_marker_tsc`
- `submit_end_from_marker_tsc`
- `poll_end_from_marker_tsc`

The benchmark still records per-slice submit and poll latency, records submit latency at every submit index, and polls only the marker completion record.

## Hardware run

```bash
launch ./target/release/hw-eval \
  --accel dsa \
  --benchmark submit-marker-overlap \
  --device /dev/dsa/wq0.0 \
  --json \
  --iterations 1000 \
  --marker-bursts 160 \
  --marker-positions first \
  --marker-poll-offsets 1 \
  --dsa-op noop \
  --pin-core 0
```

Artifacts:

- `docs/report/benchmarking/submission_bottleneck_2026-05-27/marker_trace_poll1_offset1_cumulative_noop.raw`
- `docs/report/benchmarking/submission_bottleneck_2026-05-27/marker_trace_poll1_offset1_cumulative_noop.json`

## Result

The rerun reported marker-visible median `1230` TSC ticks (`558 ns`). First median-visible trace point was submit index 8. Median cumulative timing at index 8:

| segment | median TSC ticks |
|---|---:|
| submit #1 start | 0 |
| submit #8 start | 930 |
| submit #8 end | 958 |
| poll #8 end / first visible point | 1202 |

Approximate decomposition to index 8 using median trace values:

| component | median-derived ticks |
|---|---:|
| measured submit slices, index 1--8 | 228 |
| measured poll slices, miss polls then first success poll | 386 |
| inter-iteration gap after poll before next submit | 286 |
| remaining submit-end-to-poll-end overhead captured by cumulative trace | about 302 |
| cumulative poll-end at first median-visible point | 1202 |

The remaining overhead is not DSA execution alone; it includes benchmark loop work around the measured slices: trace vector updates, branch/accounting work, address setup, status masking, and the rdtscp/measurement envelope not represented by simply adding the per-slice submit and poll medians.
