# Shared WQ submit-thread sweep: hw-eval vs Tokio async

## Scope

Device: `/dev/dsa/wq0.1` shared work queue. Submission path is ENQCMD. All rows are direct/no-batch DSA memmove (`batch_n = 1`).

Thread counts swept: `1,2,4,8,16,32`.

Important correction: the first raw multi-thread attempt was invalid because `hw-eval` pinned the process before spawning worker threads, causing all submitter threads to inherit one-core affinity. `hw-eval` was fixed to avoid implicit pinning when `--threads > 1` unless `--pin-core` is explicitly provided. The numbers below use the corrected unpinned multi-thread raw run.

## Interpretation

- Shared-WQ ENQCMD does scale with multiple submitter threads once `hw-eval` is not accidentally pinned to one CPU.
- Raw `hw-eval` reaches about 31 Mops/s at 32 submitter threads for 128B direct memmove.
- Tokio async is competitive at 2-4 threads and has one high 8-thread 256B point, but it does not scale as cleanly at 16-32 threads in this sweep.
- Several low-concurrency Tokio points failed with DSA page-fault completions and are absent from the CSV; best-rate comparisons only use successful points.
