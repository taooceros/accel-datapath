# Tokio async memmove vs raw direct memmove

## Scope

This comparison uses only direct descriptor submission: one logical memmove per MMIO submission. There is no DSA `BATCH` descriptor in either side of the comparison (`batch_n = 1` conceptually).

- Async wrapper: `idxd-rust` `tokio_naive_direct_descriptor`, `/dev/dsa/wq0.0`, `docs/report/benchmarking/tokio_memmove_sweep_latest.clean.jsonl`.
- Raw baseline: `hw-eval` direct sliding-window `memmove` rows from `hw-eval/results_dedicated.json`.
- Device mode: `/sys/bus/dsa/devices/wq0.0/mode` reports `dedicated`.

The raw baseline is from the existing hw-eval artifact because the current `hw-eval` source no longer builds after the `idxd-sys` raw-boundary cleanup, and a stale release-binary full-suite run timed out before producing JSON. Do not compare against `pipelined_batch_*`, `burst_batch_*`, or `batch_memmove` for this async wrapper; those use DSA hardware batch descriptors and are not implemented in the wrapper yet.

## Common direct/no-batch points

Only 4096-byte rows overlap between the fresh async sweep and the dedicated raw direct `memmove` artifact at the same concurrency levels.

| message bytes | concurrency | raw Mops/s | async Mops/s | async/raw | loss | raw GB/s | async GB/s |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 4096 | 1 | 0.855 | 0.544 | 0.636 | 36.4% | 3.502 | 2.228 |
| 4096 | 8 | 5.506 | 2.484 | 0.451 | 54.9% | 22.551 | 10.173 |
| 4096 | 32 | 7.318 | 2.417 | 0.330 | 67.0% | 29.973 | 9.899 |
| 4096 | 64 | 7.171 | 4.725 | 0.659 | 34.1% | 29.373 | 19.352 |
| 4096 | 128 | 7.058 | 3.289 | 0.466 | 53.4% | 28.911 | 13.472 |

Best common point by message rate:

- Raw direct memmove: 7.318 Mops/s at concurrency 32.
- Tokio async wrapper: 4.725 Mops/s at concurrency 64.
- Async retains 64.6% of raw message rate, losing 35.4%.

## Interpretation

The async wrapper is not using hardware batching; it is still one descriptor and one MMIO submission per message. The gap is therefore attributable to wrapper/runtime overhead around the same direct hardware submission model:

- Tokio task scheduling and wake/re-poll overhead.
- The naive future calls `wake_by_ref()` every pending poll, so it busy-reschedules instead of integrating with an event source.
- Per-operation future construction and descriptor/completion ownership movement.
- Worker-task structure and shared `Arc<DsaEngine>` dispatch.

At 4096 bytes, the raw direct path reaches about 7.3 Mops/s while the naive Tokio path peaks around 4.7 Mops/s. That is a substantial but not catastrophic loss for a first naive async binding. The next optimization target should be reducing poll/wake overhead and reusing operation slots, not adding hardware batch descriptors yet.

## Notes

The async sweep also measured sizes not present in the dedicated raw direct artifact:

- Peak async message rate: 7.310 Mops/s at 256 bytes, concurrency 64.
- Peak async bandwidth: 29.323 GB/s at 65536 bytes, concurrency 32.

These are useful for async characterization but are not used for raw-vs-async loss calculations until matching raw direct/no-batch points are regenerated.
