# DSA submit-only workload study, 2026-05-24

## Question

Intel's claim was that one DSA engine submission can cost roughly 20 cycles. The benchmark question here is narrower than DSA operation latency: measure the CPU-visible MMIO submission path (`movdir64b` for the dedicated WQ used here), not descriptor completion or data movement.

`Understanding the Host Network` is the right lens: host paths are credit-limited domains. A posted write can look cheap while it is merely admitted into a queue; once credits or downstream queues are exhausted, the same instruction stream can observe much larger admission/backpressure latency.

## Code changes

`hw-eval` now has an explicit submit-only workload family:

```bash
--benchmark submit-only
--submit-mode all|unloaded|sustained|mfence
```

Benchmark rows are separated by name:

- `submit_only_empty`: calibration row using the same timer wrapper with no `wq.submit`.
- `submit_only_unloaded`: timed NOOP submit burst, then an out-of-region completion-bearing sentinel drains the queue before the next sample.
- `submit_only_pressure_ramp`: timed NOOP submit burst with no per-sample drain; selected by `--submit-mode sustained` and intentionally stateful.
- `submit_only_mfence`: timed NOOP submit burst with `mfence` between adjacent submissions, then an out-of-region sentinel drain.

The default burst points are:

```text
1, 2, 4, 8, 16, 32, 64, 128, 256, 512
```

They can now be overridden with `--submit-bursts`, including a single burst size for cleaner pressure-ramp and PMU attribution experiments.

The implementation does not put `rdtscp` around every `movdir64b`; it times the whole burst and reports median cycles per batch plus derived cycles per submit. Per-submit `rdtscp` would dominate the thing being measured.

## Gradual experiment path

1. Added the CLI/workload controls and preserved the existing no-drain behavior now labeled `submit_only_pressure_ramp`.
2. Ran `submit_only_unloaded` by itself. It showed the expected cheap issue regime through moderate bursts and a clear knee at 128 submissions.
3. Ran the no-drain workload by itself. It showed hundreds of cycles per submit under sustained pressure, confirming it is a backpressure workload rather than a clean MMIO issue-cost workload.
4. Ran `submit_only_mfence` by itself. It showed about 650 cycles per submit for larger bursts, confirming that the cheap unloaded result depends on asynchronous/posting behavior.
5. Refined the combined `--submit-mode all` path so clean workloads run first and the sustained workload drains once at the end, preventing it from contaminating later modes.

## Interpretation

### The Intel 20-cycle claim is plausible, but only in the unloaded/admitted regime

The cleanest comparison is `submit_only_unloaded` at burst size 2: median 40 cycles per batch, exactly 20 cycles per submit. For bursts 4 through 64, the amortized median is even lower, around 6–12 cycles per submit. That does not mean the device completed work in 6 cycles; it means the CPU was able to issue/admit a stream of posted submissions cheaply.

This matches the Host Network interpretation: the CPU-visible operation is cheap while the write path has available credits and downstream admission capacity.

### The knee is around 64–128 submissions on this setup

`submit_only_unloaded` stays cheap through 64 submissions:

- burst 32: 268 cycles/batch, 8.4 cycles/submit
- burst 64: 526 cycles/batch, 8.2 cycles/submit

At 128 submissions the median jumps to 7692 cycles/batch, 60.1 cycles/submit. Larger bursts are dominated by admission/backpressure:

- burst 256: 297.0 cycles/submit
- burst 512: 415.4 cycles/submit

Even with a sentinel drain between samples, one large burst can exceed the cheap-credit regime internally. That is the useful credit-depth signal.

### Sustained no-drain is a backpressure benchmark, not an MMIO issue benchmark

`submit_only_pressure_ramp` converges to roughly 500 cycles per submit for larger bursts. That is not the cost of an isolated `movdir64b`; it is the cost of continuously submitting when queue/device credits are already under pressure.

This workload is still valuable because it tells us the cost of ignoring completion/credit pacing. It should not be used as the answer to “how much does one submission cost?”

### `mfence` makes submission look synchronous/serialized

`submit_only_mfence` converges to about 650 cycles per submit for larger bursts, or about 295–298 ns per submit. The burst-1 row is unchanged because no fence is inserted when there is no adjacent submission; the cost appears once there is a fence between submissions.

This strongly supports the asynchronous-posted-write interpretation. Cheap submit costs come from issuing/admitting stores without waiting for the downstream device path to fully resolve each one.

## Research conclusion

We should report three different costs, not one:

1. **Unloaded MMIO issue/admission cost**: about 20 cycles for a two-submit burst, and about 8 cycles/submit amortized through 64-submit bursts on this machine.
2. **Credit-depth knee**: between 64 and 128 same-descriptor NOOP submissions in one drained sample.
3. **Backpressured or serialized cost**: hundreds of cycles per submit; about 500 cycles sustained no-drain and about 650 cycles with `mfence` between submissions.

For the paper/story, the strongest statement is:

> DSA submission is cheap and asynchronous only while the host/device submission path has credits. In that regime, our measured dedicated-WQ `movdir64b` path reaches the 20-cycle claim and amortizes below it. Once we exceed the submission-path credit regime or force ordering with `mfence`, the apparent cost rises to hundreds of cycles, matching the Host Network view of credit-limited domains and backpressure.

## Timer-source and RDPMC follow-up

After switching the CPU governor to performance, `hw-eval` was extended to measure every submit-only workload with independent timer passes in one command:

- TSC ticks from `rdtscp`;
- wall-clock nanoseconds from `Instant`;
- unhalted thread cycles from an in-process `perf_event_open` PMU counter using per-sample ioctl/reset/enable/disable/read;
- unhalted thread cycles from the same PMU event class using the perf mmap page plus `rdpmc`.

The first timer-source attempt measured several sources in one hot path. That was rejected because it made PMU results include `rdtscp` and wall-clock overhead. The current DSA submit loop receives the timer as a generic type parameter at the innermost measurement boundary, and each timer gets a separate pass. JSON rows now include an explicit `timer` field, so rows no longer have to be identified by optional-field presence.

The current `rdpmc` implementation is in `hw-eval/src/timing.rs`. It opens a current-thread `PERF_COUNT_HW_CPU_CYCLES` event, maps the perf metadata page, checks `cap_user_rdpmc`, enables the event once, and samples `offset + rdpmc(index - 1)` inside the seqlock protocol documented by `linux/perf_event.h`. This keeps PMU setup and unsafe perf/assembly details out of the DSA benchmark loop.

Verification command used after adding `rdpmc`, explicit timer labels, empty calibration rows, `--submit-bursts`, and pressure-ramp naming:

### Timer-source interpretation

The explicit calibration rows make the main artifact visible:

- `tsc` empty rows are about 20-22 TSC ticks, so TSC remains the lowest-overhead stable source for short burst-shape studies.
- `wall` empty rows are about 15 ns and too coarse to interpret tiny bursts alone, but useful as a real-time sanity check.
- `pmu` ioctl/read empty rows are about 125-127 core cycles, so tiny-burst PMU medians mostly report measurement machinery.
- `rdpmc` empty rows are about 9 core cycles in this run, making it the useful PMU path for core-cycle attribution.
- The burst-64 unloaded `rdpmc` row was 534 core cycles/batch versus a 9-cycle empty median, which is consistent with the older TSC-only result that unloaded same-descriptor submission is cheap until queue/admission pressure appears.

`submit_only_pressure_ramp` is still not an independent per-burst cost table. It intentionally carries queue state across samples in a timer pass and should be read as a pressure trajectory. Use `--submit-bursts <N>` for single-burst pressure-ramp experiments.

## Dedicated-WQ admission probe

To test whether `movdir64b` over a full dedicated WQ behaves like blocking admission or like silent loss, `hw-eval` now includes:

```bash
--benchmark submit-admission
```

The probe prepares `N` distinct completion-bearing NOOP descriptors, submits them as a tight `movdir64b` burst without software inflight tracking, then counts how many completion records become non-empty. This is intentionally different from `submit_only_unloaded`, which reuses one no-completion descriptor and drains with a sentinel.

Dense run around the current WQ depth:


### Admission interpretation

On this machine and WQ, the distinct-descriptor admission probe supports the blocking/admission-paced interpretation: `movdir64b` did not produce missing completions up to 1024 submitted descriptors, even though the WQ depth is 128. Instead, the submit loop slowed as the WQ approached and exceeded its depth.

This does not eliminate the need to track inflight operations in production code:

- descriptors, completion records, and data buffers must remain alive until completion;
- software still needs completion tracking to reclaim resources and bound latency;
- other WQ modes, devices, or kernels may not expose the same behavior;
- shared WQs remain different because `enqcmd` has explicit retry feedback.

It does refine the claim for this platform: for the tested dedicated WQ, over-depth `movdir64b` submissions were backpressured rather than silently lost.
