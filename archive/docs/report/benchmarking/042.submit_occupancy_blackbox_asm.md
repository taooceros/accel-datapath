# Submit occupancy black-box loop assembly investigation

Note: this report describes the earlier accumulator-based black-box helper. The current cheaper `black_box(n)` helper and focused verification are documented in `docs/report/benchmarking/043.submit_occupancy_blackbox_n_gap.md`.

## Question

Why does `--submit-occupancy-spin-iters 1` remove the Experiment 1 submit-latency knee, even though it sounds like only one loop iteration?

## Commands

```text
rtk cargo asm -p hw-eval --bin hw-eval --json --this-workspace --intel
rtk cargo asm -p hw-eval --bin hw-eval --rust --intel hw_eval::benchmarks::submission_bottleneck::run > target/asm-investigation/submission_bottleneck_run.asm
```

`cargo asm` did not show a standalone Experiment 1 symbol; the Experiment 1 helpers are inlined into `hw_eval::benchmarks::submission_bottleneck::run`.

## Relevant source

```rust
fn submit_prefill(wq: &WqPortal, descriptors: &[DsaHwDesc], spin_loop_iters: u64) {
    for desc in descriptors {
        unsafe { wq.submit(desc) };
        if spin_loop_iters != 0 {
            manual_submit_gap(spin_loop_iters);
        }
    }
}

fn manual_submit_gap(iterations: u64) {
    let mut accumulator = 0_u64;
    for i in 0..iterations {
        accumulator = black_box(accumulator.wrapping_add(black_box(i)));
    }
    black_box(accumulator);
}
```

## Cargo-asm finding

For the dedicated WQ path, submit is a `movdir64b` followed by either the next descriptor or the black-box loop. With `spin_loop_iters == 0`, the prefill loop is essentially:

```asm
movdir64b (%rcx), %rdx
addq $64, %rcx
addq $-64, %rax
jne .LBB242_822
```

With `spin_loop_iters != 0`, each descriptor pays the black-box loop machinery:

```asm
movdir64b (%rcx), %rdx
movq $0, 576(%rsp)       ; accumulator stack slot
xorl %edx, %edx          ; i = 0
movq 56(%rsp), %rdi      ; iterations
leaq 576(%rsp), %r8
.LBB242_813:
movq %rdx, 768(%rsp)     ; black_box(i): force a stack observable value
incq %rdx
#APP
#NO_APP                  ; empty asm barrier from black_box
movq 768(%rsp), %rsi
addq %rsi, 576(%rsp)     ; accumulator += i, in memory
#APP
#NO_APP                  ; empty asm barrier from black_box(accumulator update)
cmpq %rdx, %rdi
jne .LBB242_813
movq 576(%rsp), %rdx
movq %rdx, 768(%rsp)
#APP
#NO_APP                  ; final black_box(accumulator)
```

`black_box` does not emit a useful hardware instruction here. The `#APP/#NO_APP` blocks are empty inline-asm compiler barriers. The cost comes from forcing stack stores/loads, memory accumulator traffic, branch/control setup, and preventing LLVM from deleting or simplifying the loop.

The active path for `/dev/dsa/wq0.0` is dedicated (`wq_dedicated: true` in JSON), so the submit path uses `movdir64b`. The `enqcmd` retry path contains `pause`, but it is not the path used for these runs.

## Measured size of one black-box iteration

From the current black-box-loop sweep summary CSV, at K=128:

| workload | iters=0 avg prefill ticks | iters=1 avg prefill ticks | delta | delta per descriptor |
|---|---:|---:|---:|---:|
| noop | 3,440 | 24,448 | 21,008 | 164 ticks |
| 1 MiB memmove | 4,245 | 24,910 | 20,665 | 162 ticks |

The TSC frequency in the JSON is `2,204,206,114 Hz`, so 21k ticks is about 9.5 us. The per-descriptor added delay is about 73-75 ns.

Additional iterations are much cheaper than turning the path on: for K=128, going from iters=1 to iters=2 adds only about 9-11 ticks per descriptor. The first iteration includes the fixed setup/finalization cost of the black-box machinery; the second and later iterations mostly pay the loop body incrementally.

## Interpretation

The label `iters=1` is misleading if read as one cheap arithmetic operation. It means: after every submitted descriptor, execute a non-optimizable black-box sequence with stack traffic and compiler barriers. Across K=128, this stretches the prefill submit train from about 1.6 us to about 11.1 us.

That extra time is enough for the DSA WQ/device admission path to consume descriptors and avoid the next measured submit stall. It is not because large payload work completed: at K=128 with iters=1, the 1 MiB memmove run still had only about 30-33 of 128 prefill completions visible and still needed about 2.23M TSC ticks of post-submit completion time.

Therefore the massive behavior change is explained by submit pacing: the no-delay loop drives `movdir64b` submissions in a very tight burst; one black-box iteration converts that burst into a paced stream with roughly 160 extra TSC ticks between descriptors. That pacing is enough to remove the admission/descriptor-consumption pressure observed as the K=114 knee.
