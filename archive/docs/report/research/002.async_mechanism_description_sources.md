# Async mechanism description source notes

## Purpose

Collect a small set of public-source phrasing cues for an advisor-facing slide comparing `stdexec`, Rust Tokio, and C++ coroutines. These notes are for slide wording only; they do not add any project performance or hardware claims.

## Sources checked

- Tokio tutorial, “Spawning”: <https://tokio.rs/tokio/tutorial/spawning>
- Rust Async Book, “async/.await”: <https://rust-lang.github.io/async-book/03_async_await/01_chapter.html>
- Rust standard library `Future`: <https://doc.rust-lang.org/std/future/trait.Future.html>
- Rust standard library `Pin`: <https://doc.rust-lang.org/std/pin/index.html>
- NVIDIA `stdexec` README: <https://github.com/NVIDIA/stdexec>
- Lewis Baker, “Coroutine Theory”: <https://lewissbaker.github.io/2017/09/25/coroutine-theory>

## Wording cues

### `stdexec`

The NVIDIA `stdexec` README describes `stdexec` as an experimental reference implementation of the Senders model for C++ asynchronous execution, proposed by P2300 and accepted for C++26 `std::execution`. Its example language is useful for a slide: the programmer “describes some work,” builds sender pipelines with scheduling and continuation adaptors, and “no work actually happens” until the lazy graph is started.

Slide phrasing:

- “Build a lazy operation graph.”
- “Connect to a receiver, start an operation state.”
- “Scheduler/pipeline policy is explicit and swappable.”

### Tokio / Rust futures

The Rust `Future` docs define a future as an asynchronous computation and put `poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>` at the center. `poll` does not block; if the value is not ready, the current task is scheduled to be woken and polled again through a `Waker`.

The Tokio tutorial describes tasks as scheduler-managed units. `tokio::spawn` submits a task to the scheduler; the runtime executes it when it has work, may move it between runtime threads, and resumes it after it yielded at `.await`.

Important lifetime challenge for the slide:

- The Rust Async Book says an `async fn` that takes references returns a `Future` bounded by those references' lifetimes; that future must be awaited while borrowed data remains valid.
- Tokio `spawn` requires the task future to be `'static`: the spawned task must not contain references to data owned outside the task.
- Tokio also requires spawned tasks to be `Send`; all state held across `.await` must be `Send` because the runtime may move suspended tasks between threads.
- The Rust `Pin` docs explain why async state machines can become address-sensitive/self-referential once polled; pinning keeps the future's address stable across suspension/resumption.

Slide phrasing:

- “Runtime polls a pinned future; pending registers a waker.”
- “Hard part for our hardware path: buffers/completion records may live across `.await`, so lifetimes, ownership, `Send`, and pinning are part of the interface—not just implementation details.”
- “Tokio makes wakeup integration natural, but Rust forces us to prove that outstanding hardware operations do not outlive their buffers.”

### C++ coroutine

Lewis Baker’s coroutine explanation frames a coroutine as a generalized function that can be suspended and later resumed. Suspension points are identified by `co_await`/`co_yield`; the coroutine prepares a coroutine frame so a later resume can continue from the suspension point.

Slide phrasing:

- “Sequential-looking code; `co_await` marks suspension.”
- “Coroutine frame stores continuation state.”
- “Language provides suspension mechanics; library/runtime decides scheduling and I/O policy.”

## Slide implication

The slide should not present these as three unrelated technologies. A better advisor-facing frame is:

```text
submit async work -> save continuation state -> return pending/suspend -> completion wakes scheduler/awaiter -> resume continuation
```

Then distinguish the mechanisms by what they make explicit:

- `stdexec`: explicit operation graph and scheduler composition.
- Tokio: polling/waker runtime plus Rust ownership/lifetime constraints.
- C++ coroutine: syntax-level suspension and coroutine frame, with policy supplied elsewhere.
