# Tonic + DSA integration notes

## Progress

The direction is clearer now. We are not trying to optimize Tonic/Prost for its own sake, and we are not treating zero-copy as the only correct answer. The research question is simpler: can we expose real copy work in the RPC byte path, then compare normal Tonic, CPU copy, and DSA copy on the same bytes?

The codec/body boundary still looks like the right place to work because that is where payload bytes become visible. But I think we learned an important nuance: "codec boundary" does not automatically mean "good async boundary." `tonic::codec::Encoder::encode` is synchronous. Putting real DSA completion there would either block, spin, or fight Tonic's async backpressure model.

So the current design split is:

- use the sync codec path only as a controlled experiment;
- keep the real async DSA design for Tonic's body/state-machine polling path;
- avoid changing generated services until the low-level path is better understood.

## Design choices from the gradual plan

The first slice was intentionally conservative. Prost encodes into a staging buffer, then DSA copies the encoded bytes into Tonic's output buffer. This gives us a clean comparison point, even if it is not the final design.

Moving this into a separate crate, `tonic-prost-dsa-sync`, was the right cleanup. `tonic-prost` stays as the normal CPU baseline. The DSA path is explicit and experimental through `tonic_prost_dsa_sync::DsaSyncProstCodec`.

A few small choices matter for measurement quality:

- install the DSA work queue once instead of taking a global lock on every encode;
- do not silently fall back to CPU copy after DSA is selected;
- keep the default Tonic/Prost path boring and unchanged.

This makes the experiments easier to trust.

## What we learned

DSA is copy, not zero-copy. It only helps if there is real byte-copy work to replace or overlap. If Tonic already writes directly into the final buffer, adding DSA can just add extra work.

The async API shape also matters. A borrowed async API like `async fn encode(&mut self, item, dst: &mut EncodeBuf<'_>)` sounds nice, but it quickly becomes self-referential inside Tonic. The safer direction is for the pending operation to own the buffers, wait for completion, and then return the buffers back to the state machine.

The DSA future also cannot just wake itself repeatedly. That would create poll/wake churn inside Tokio. We need a real completion path: submit, return `Pending`, wake on completion, then finish the gRPC frame.

## Current evidence

The mock bytes RPC benchmark is useful because it runs through a real Tonic TCP client/server path. It validates the echoed bytes, then compares the standard CPU codec against the DSA codec.

The current result is not "DSA makes Tonic faster." It is more limited:

- small payloads are dominated by Tonic/h2/Tokio overhead;
- isolated DSA copy is slower than CPU copy through at least 1 MiB;
- end-to-end results become more interesting around 1 MiB;
- 2-4 MiB payloads look more consistently favorable to DSA, but still need more careful sweeps.

So I would treat the current numbers as directional, not final.

## Next steps

The next useful step is the async binding layer: submit work, hold owned buffers while the operation is pending, wake on completion, and avoid blocking inside sync codec APIs.

After that, the narrow Tonic integration should happen at the body/codec polling boundary. The rough shape is:

```text
Prost prepares bytes
-> Tonic submits DSA copy
-> body returns Pending
-> completion wakes the task
-> Tonic emits the finished frame
```

For policy, small payloads should stay on CPU for now. Current evidence only supports trying DSA around 1 MiB or larger.

Intel DTO is also worth comparing against. It uses an async-over-sync split model where CPU and DSA each handle part of the copy and overlap. That is different from a Tonic-native async design, but it is a useful baseline for transparent offload.

## Some thoughts

I think the main process lesson is that small, named slices worked better than broad integration requests. The useful pattern was: keep the CPU baseline untouched, isolate the DSA path, make failure visible, run one concrete benchmark, and interpret noisy results carefully.

For future profiling/report work, I should probably ask the agent to analyze one workload or one profile at a time, with symbols and configuration checked first. Asking for a big synthesis too early tends to produce a polished story before the evidence is solid.
