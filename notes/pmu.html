P10: performance counters as second evidence (group pmu)

Probe: dsa-lab/src/bin/p10_pmu.rs (one binary, --mode calib|knee). All runs are under dsa-lab-runs/P10/<dir> (below: <dir> only). Config dsa-config/{1,2,3,4}-engine.conf (dedicated WQ, size 128). Heaters on (8 threads); uncore 2.05-2.20 GHz at start, 2.20 at end in every run. Core 3.6-3.9 GHz, except q1-rdpmc-r1/r2, which ran at 2.2 GHz. All noop runs: every status 0x01, SWERROR unchanged. 1 MiB runs: an unmeasured warm-up runs each slot alone until it returns 0x01. All buffers are prefaulted, including the partial last page, and set_mempolicy(MPOL_PREFERRED) is set. In the measured runs the only non-0x01 status is 0x00, which is the dropped descriptors. SWERROR records 0x53 plus overflow, as expected for drops.

How the counters are read

  • DSA PMU (dsa0, dsa2; perf type from sysfs; counted on the cpumask CPU 0): config = category | events << 4; config1 = wq | tc << 32 | pgsz << 40 | sz << 44 | eng << 52 (bit positions from format/). The idxd driver writes a filter register only when the field is non-zero (drivers/dma/idxd/perfmon.c, perfmon_pmu_event_start), so a zero field would keep a stale filter. The probe therefore always writes every filter: WQ = the leased WQ only, all others all-ones. 8 hardware counters: with 16 events open, only 8 count (021810Z-A-calib-n16), so never open more than 8.

  • IIO: UNC_IIO_TXN_REQ_BY_CPU.MEM_WRITE (event 0xC1, umask 0x01, ch_mask 0xFF, fc_mask 7; intel/perfmon SPR/events/sapphirerapids_uncore.json) opened on all 7 uncore_iio_* PMUs. On both sockets only uncore_iio_0 counts the DSA portal writes. The other 6 read 0.

  • Core (user mode, this thread; intel/perfmon SPR/events/sapphirerapids_core.json V1.40, repo commit 2ba60f6). There are two read methods:

    • --core-read syscall: PerfCounter::raw plus read(2).
    • --core-read rdpmc: same codes, but read with RDPMC through the perf mmap page. LFENCE and then 4 RDPMCs into registers, so there is no store or syscall inside the bracket. A sample is dropped if the mmap-page seqlock or index changed. That happened in 0 iterations.

    The syscall bracket is biased. The user-mode stores in the read() path after the timed submit wait for SB entries. That stall is counted, so SB stalls appear from K≈90 (q1-syscall-sb_stall-r1..3). This is why the Q1 verdicts use RDPMC.

P10-a. Calibration (exact K, no Drain inside the window)

The probe submits K noops, polls every completion record, and only then reads the counters. The Drain is bracketed separately. Runs: 021734Z-B-calib-ncounters (K = 1, 10, 100, 5 iters each), 021810Z-A-calib-n16, 022015Z-A-calib-cyc-1m-warm (1 MiB, K = 1, 8). Every count-type event above reads K in every iteration (exact, not ±1). 021846Z-B-calib-cyc-1m is invalid: all descriptors faulted (0x03) at the unwritten last partial page of dst. That was a prefault bug, fixed afterwards.

P10-b. Q1: is the ~114 stall the core store buffer? (X1 sweep with heaters)

Predictions (model.js P10, before running): Q1-b says RESOURCE_STALLS.SB ≈ 0 below the knee and ≈ the extra time above it. Q1-c (device or IIO backpressure) says no SB stalls; the stall would show as something else.

Runs (RDPMC bracket around prefill + timed submit):

  • 022346Z-B-q1-rdpmc-r1, 022347Z-B-q1-rdpmc-r2 (core 2.2 GHz)
  • 022348Z-B-q1-rdpmc-r3 (3.9 GHz)
  • 022355Z-A-q1-rdpmc-fence-control (side A, ~3.9 GHz effective; its main bracket is the same as the others)

"Extra" = cycles − a linear fit of cycles over K ≤ 108.

  • Above the knee, the SB stall grows by 376 cycles per extra descriptor at 3.9 GHz (96.5 ns), and the prefill time grows by 97.3 ns per descriptor. At 2.2 GHz the numbers are 217 cycles = 98.7 ns vs 100.4 ns. So one SB-full stall equals one cadence period.
  • BOUND_ON_STORES agrees with RESOURCE_STALLS.SB to 1-2%.
  • ALL_STORES = K+10, so every MOVDIR64B is a retired store.
  • No device drops: DWQ_SUCCESS = K+1 and DWQ_FULL = 0 at every K.
  • The knee moves with core speed: SB stalls first appear at K = 114 at 3.9 GHz and at K = 116 at 2.2 GHz, because a slower prefill lets more stores drain first.

Verdict: Q1-b survives with two evidence types (timing, and a count that matches the timing within 1-5%). Q1-c is contradicted: the extra time is store-buffer allocation stall in the core.

Controls and caveats:

  • --mid runs (022348Z..022350Z-B-q1-rdpmc-mid-r1..3) add an RDPMC snapshot between prefill and the timed submit. The compiler spills the snapshot to the stack, and those stores themselves stall in the full SB: about 2540-2660 cycles, roughly 7 stores, inside the "timed" segment. That segment is perturbed and should not be used. The prefill segment there gives the same picture: 0 below K≈116, then (K−117)×~390 cycles. The timed submit stays at ~100 ns even after the spills, which fits in-order SB drain with the spills queued behind the MOVDIR64Bs [INFERENCE].
  • The fence control (SFENCE after the timed submit) is labeled a control only and its result is inconclusive. The fence window saturates at ~850 ns for K ≥ 114, and SB stalls in that window are ~2450 cycles, which coincide with 5 spill stores. Nothing here measures how many stores are still outstanding at the SFENCE, so what SFENCE+RDTSCP waits for is not established, and the run says nothing about drain depth.
  • The submit+1 cost of ~40-80 ns at K = 32/64 (seen in several runs) has SB stall = 0, so it is not a store-buffer effect. The cause is still open.

P10-c. Do descriptors past the CPU knee reach the device late, or drop? (noop)

Runs:

  • 022048Z..022049Z-A-knee-noop-r1..3: DSA counters per K block. The core counters in these runs were read serially with read(), so they are not used.
  • 022744Z-A-arr-noop-r1, 022745Z-A-arr-noop-r2: a sampler thread on CPU 0 reads DWQ_SUCCESS / DISPATCH / IIO back to back (~1.5 µs per read, 3.5-4.6 µs per sample) while the submitter never enters the kernel.

Results:

  • No drops. DWQ_SUCCESS = K+1 and the IIO count = K+2 (with the Drain), DWQ_FULL = 0, and completions = K+1 at every K up to 160, in 3 runs.
  • The device WQ never queues noops. EV_CYC_NON_BATCH_DESC_RDY is exactly 1 cycle per descriptor, and DISPATCH = DWQ_SUCCESS.
  • They arrive late, at the cadence. Descriptors reach the WQ at 105-110 ns each (fit over 22 traces). The CPU retires the timed submit at 0.3-1.1 µs (K=96) or 5.6 µs (K=160), but the WQ count reaches its final value only at 12-16 µs (K=96) or 19-21 µs (K=160). So ~K−50 (K=160) or ~K (K=96) descriptors are still in the core when the CPU moves on, both below and above the knee. That matches P10-b.
  • No queue between the IIO and the WQ. The IIO TXN count runs ahead of DWQ_SUCCESS by about the number of descriptors that arrive during the ~2.5 µs read skew between the two columns, i.e. 0 buffered within resolution. [INFERENCE] The pacing is set at or before the IIO's request ingress, not at the device's WQ. This is Q5 evidence against a slow device-side acceptance stage (Q5-b), though credit backpressure from the IIO itself is not excluded.

Caveats: the sampler perturbs the run. The K=160 timed submit takes ~320 ns with the sampler (~105 without), and prefill is about 5% slower. Columns of one sample are read ~1.5 µs apart, so only the first column (DWQ_SUCCESS) has a clean baseline.

P10-d. Q4: where do the extra 1 MiB descriptors sit?

Predictions (model.js, before running):

  • Q4-a: capacity = 128 + E·m, and EV_PIPEFULL_NO_DISPATCH is large for 1 MiB.
  • Q4-b: 128 + a constant.
  • Q4-c: a counting artifact.

Runs (memmove 1 MiB, K = 64/128/200, 5 iters, 4 engines):

  • 022640Z..022645Z-A-ovf-wqeng-r1..3
  • 022646Z/022648Z-A-ovf-pereng-r1..2: per-engine dispatch + PIPEFULL
  • 022650Z/022652Z-A-ovf-xlat-r1..2: translation
  • 022740Z/022742Z-A-arr-1m-r1..2: sampler time series
  • 022906Z-A-arr-1m-pereng: sampler, per-engine dispatch
  • 022908Z-B-arr-1m-e1, 022909Z-A-arr-1m-e2, 022910Z-B-arr-1m-e3: engine sweep with the sampler

Results:

  • Accepted = 140 per iteration at K=200, in every run, and identical in the device counter and the completion records: DWQ_SUCCESS 141 = 140 + 1 Drain, DWQ_FULL 62 = 61 + 1 Drain, completed 140, missing 61. At K=128 nothing drops (DWQ_FULL 0). Q4-c is dead.

  • Engine sweep (time series while full, before any completion):

    E accepted plateau dispatched (simultaneous) accepted − 128 − dispatched
    1 131 2 1
    2 134 4 2
    3 137 6 3
    4 140 8 (2/2/2/2 per engine) 4

    So C(E) = 128 + 3E exactly. Q4-a survives with m = 3, and Q4-b is dead. Each engine holds 2 descriptors that the PMU counts as dispatched into its work pipeline. The third is accepted but not counted as dispatched. It scales with E, so it is per engine. Its exact location is not directly counted [INFERENCE]: it fits "one descriptor staged in the engine waiting for a pipeline slot", which is what EV_PIPEFULL_NO_DISPATCH describes, but it could be any per-engine one-entry stage.

  • EV_PIPEFULL_NO_DISPATCH ≈ 4.6-4.85 M cycles per engine per iteration. That is the whole ~4.6 ms busy period at ~1 GHz, so the 1 MiB pipelines are always full with a descriptor waiting. Noop: 2 cycles/desc. Prediction "Q4-a: PIPEFULL large for 1 MiB" survives. EV_CYC_NON_BATCH_DESC_RDY ≈ 4.5 M: the WQ holds ready descriptors for the whole run.

  • Translation: one ATS translation per 4 KiB page, no page-fault/PRS responses, and ~5 ATC-no-alloc per descriptor. Translation is not where descriptors wait.

  • Arrival into the WQ during 1 MiB runs is 107-115 ns/desc (sampler on). The WQ fills at 17-20 µs, and the CPU finishes at ~10 µs.

  • Core side, 1 MiB K=200: SB stall ≈ 31-32 k cycles (3.9 GHz) of a ~9.5 µs prefill. The timed submit takes ~320 ns, not ~100 ns (also at K=128). That 1 MiB timed-submit cost is not explained here (Q6/Q8).

Suggested model.js updates (the lead integrates)

  • Q1-b: supported → confirmed by count: RESOURCE_STALLS.SB = 1.01-1.05 × the extra cycles, 0 below the knee, slope = one cadence per extra descriptor. Mark Q1-c ruled out by P10.
  • Q2: DWQ_FULL counts every drop (= missing completions). SWERROR shows 0x53 + overflow.
  • Q4: a → supported, m = 3 per engine: C(E) = 128 + 3E measured for E = 1-4. Per engine, 2 are counted as dispatched and 1 is per-engine but not counted. b and c → ruled out. engine_slots = 3/engine, and the animation fill should be 12 (8 in pipelines + 4 staged), not 11.
  • Q5: add evidence. Arrivals at the IIO and at the WQ are both paced at ~105-110 ns with no queue between them, so the cadence is upstream of the device WQ [INFERENCE: at or before IIO ingress].
  • Components: the DSA cycle events count ~1.0 per ns while busy and are inactive when idle (a conditional event, not a free-running clock). A Drain completes as 4 completions (one per engine [INFERENCE]) and is dispatched to every engine.
  • P10 status: done. The DSA PMU has 8 counters, and the driver's zero-filter-means-stale rule must be avoided.
