coreside: is the ~114–116 knee the core store buffer? (P0, P2, P3, Q8, the mid-K anomaly)

Machine: Xeon Gold 6438M (SPR / Golden Cove), side A = cpu 2 (SMT sibling 66) + dsa0, side B = cpu 34 (sibling 98) + dsa2. All device runs use dsa-config/4-engine.conf, noop descriptors, and Drain. The heaters ran (8 threads, mesh ~2.2 GHz) unless noted. Every device run had errors_total = 0 and missing = 0. Run directories are relative to dsa-lab-runs/.

Probes (committed in this workspace):

  • src/bin/p0_sb_size.rs: CPU only. A JIT-generated loop runs two pointer-chase chains that miss to DRAM through one random cycle in a 512 MiB huge-page buffer, with chain heads carried across calls: [SERIALIZE]; mov (%rdi),%rdi; N fillers; mov (%rsi),%rsi. Fillers can be store, store64, nop, load or movdir64b. It reads RESOURCE_STALLS.SB and EXE_ACTIVITY.BOUND_ON_STORES. --sib compute|store puts a loop on the SMT sibling.
  • src/bin/cs_knee.rs: X1 with knobs. --m adds plain stores after each prefill MOVDIR64B. --sib loads the SMT sibling. --timed-stores j adds plain stores inside the timed window. --timed-op swaps in a control op. --gap-ns, --clear all|used|status, --pre zmm|ymm|spin|wb64:<ms>, --row-pause-us, --freq (per-iteration core GHz and time), --pmu and --trace are also there. The timed submit is one asm block (rdtscp; movdir64b; [j stores]; rdtscp) with no stores in between. The binary maps the portal and drains it itself, because a dedicated WQ can only be opened once. prefill_ns (t0 − t_start) works as a trace without stores: its increment at K is what the K-th prefill submit cost.

Event codes come from Intel perfmon SPR/events/sapphirerapids_core.json V1.40 (https://github.com/intel/perfmon/blob/main/SPR/events/sapphirerapids_core.json): RESOURCE_STALLS.SB = event 0xA2 umask 0x08, "Cycles stalled due to no store buffers available (not including draining form sync)". EXE_ACTIVITY.BOUND_ON_STORES = 0xA6 / 0x40 / cmask 2.

P0: how big is this core's store buffer (no device)?

Question. How many plain stores fit behind a long-latency blocker before allocation stalls?

Predictions (model.js P0). The Golden Cove public value is 114. If the result is not ~114, the coincidence behind Q1 falls apart.

Method and validation. Each iteration runs a DRAM miss, then N fillers, then a second, independent DRAM miss, with SERIALIZE at the top of the iteration. If the N fillers fit in the resource, the two misses overlap and an iteration costs about one miss latency plus the SERIALIZE cost. If they don't fit, the second miss can't be allocated until the first one retires, which adds about one more miss latency (~+95 ns). SERIALIZE stops run-ahead into the next iteration, so RESOURCE_STALLS.SB is exactly 0 until N stores themselves overflow the SB. That makes the counter an independent signal, not a background level.

Two earlier designs were dropped and are not used in this note:

  • P0/…021443Z-A-store-v1: a bug made both chains re-walk the same 20k lines, so they hit in the LLC.
  • P0/…021621Z-A-store-v2: no fence. Run-ahead fills the SB at every N, so the counter reads about 240 cycles per iteration everywhere and the step is only +20 ns.

At the plain-store knee the step is +91…+106 ns, one extra DRAM latency (for example 183.7 → 278.3 ns at 112 → 113 in r0). Below the knee the counter reads exactly 0.

Result. In this serialized sequence, 112 plain stores fit behind an outstanding miss and 113 do not. The SB-full event first fires at N = 112, and for MOVDIR64B at N = 114 (two runs). That gives a store buffer of ~112–114 entries, and one MOVDIR64B takes one SB entry: 114 MOVDIR64B fit before the counter fires, where 2 entries per MOVDIR64B would have made it fire at ~57. The 2-entry difference between plain stores (112) and MOVDIR64B (114) is unresolved; nothing measured here attributes it.

Validation: the same loop finds the load buffer at 191 (public 192), a structure of known size. The store64 filler (64 distinct lines) gives the same knee and counter onset as stores to one line. The SB counter is 0 for the load filler at every N, and 0 below the knee for the store fillers. In the two-block layout the counter fires at 2N ≈ 112, so it tracks total SB occupancy. The timing knee moves only to N ≈ 111 (not ~56), which means the second block barely delays the second miss here. Why it moves by 1–2 rather than 0 is not explained, so this layout shows the counter's meaning but does not by itself validate the timing method. The nop sweep (meant to check the ROB) is inconclusive: it has a step near 500, but its timing is not monotonic above that (see table), most likely because the front end can't keep up with loop bodies of ~500 one-byte nops [INFERENCE]. I don't use it as validation.

Survives: prediction "≈114". Evidence: timing signature, an independent PMU count, and one known-size control (the load buffer) plus the store64 cross-check. Caveats: the core clock moved between 2.2 and 3.9 GHz from run to run (other agents' load). The knee position did not change, but the latency did.

P2: m plain stores after each prefill MOVDIR64B

Question. Do plain stores, which never reach the device, move the knee?

Predictions (model.js P2). Q1-b (SB) predicts a knee ≈ 114/(1+m): 114, 57, 38, 23, 13. Q1-c (device ingress) predicts no earlier knee.

Runs. The final binary, with --clear status (see the anomaly section) and K = 0..130 at every K, 30 iterations each: P2/…023206Z-B-final-m{0,1}-r0, P2/…02320{7,8,9}Z-A-final-m{2,4,8}-r0, P2/…02321{2,3,4}Z-A-final-m*-r1, P2/…0232{17,18,19,20}Z-A-final-m*-r2. An earlier binary (also clean in the timed window, checked in its disassembly) was run 3× on side B and A: P2/…022130Z-B-m0 … P2/…022239Z-A-m8-r2. The PMU runs are P2/…02234{6,7,8,9}Z-A-m{0,1,4}-pmu2-r* and P2/…022350Z-A-m4-pmu2-r1.

A least-squares fit of K* = C/(1+m) + D over the 15 final runs gives C = 114.6 entries and D = 2.45 MOVDIR64B written out during the prefill. It predicts 117.0 / 59.7 / 40.6 / 25.4 / 15.2. cs_knee --trace (exactly one store per submit, but the prefill is slower at ~19 ns per submit) stalls first at submit 70 (ANOM/…023502Z-A-trace-status-clear). That fits the same model with D ≈ 12.7: 1.33 µs of prefill at ~105 ns per write-out. It also explains X3's knee of 21 (about 5–6 entries per traced submit).

Survives: Q1-b. Q1-c is killed, because stores that never reach the device move the knee exactly as entry counting predicts. Evidence: timing (prefill increments, timed submit), counts (RESOURCE_STALLS.SB onset at K = 114 / 58 / 24, and ~410 stall cycles at 3.9 GHz ≈ 105 ns per extra K, which is one write-out), and a manipulation (m).

Note on m ≥ 2. "Timed K+1 > 55 ns" never fires for m ≥ 2, even though the prefill slows to one write-out per submit. A write-out frees 1+m entries at once (the plain stores behind the MOVDIR64B commit right after it). The stall lands on a plain store in the prefill, and the timed MOVDIR64B then finds a free entry. The pressure point has to be read from prefill_ns, not from the timed submit.

Caveats. D depends on how fast the prefill runs. C rests on the assumption that the write-out of the first MOVDIR64B starts right away.

P3: SMT sibling idle or busy

Question. Does the knee halve when the hyperthread sibling is active?

Predictions (model.js P3). If the SB is statically partitioned (Q1-b), the knee drops to ~57. If the limit is in the device (Q1-c), nothing changes. Both CPUs are kept out of the heaters (the lib excludes siblings).

Device runs: P3/…0232{09,10,11}Z-A-final-sib-{none,compute,store}-r0, …02321{5,6}Z-…-r1, …0232{21,22}Z-…-r2, and the earlier P3/…02223{2,3}Z-B-dev-sib-*. The write-out cadence above the knee did not change (106–107 ns).

Survives: Q1-b with static partitioning: a sibling that only computes, with no stores, is enough to halve it. Q1-c is killed again. Evidence: timing on the device, plus a CPU-only timing and PMU count that give the same halving, plus a manipulation (the sibling). [INFERENCE] The knee halves to the same 56/60 whether the sibling stores or not, so the effect comes from partitioning, not from competition for shared entries.

Q1 verdict

The ~114–116 X1 knee is the core store buffer filling with MOVDIR64B (Q1-b). Each MOVDIR64B holds one SB entry until it is written out, about every 100 ns (mesh-dependent). The evidence comes in three independent kinds:

  1. Timing signatures: the CPU-only SB is ~114 (P0). The device knee follows 114.6/(1+m) + 2.5 for m = 0…8 (P2) and halves with an active sibling (P3), and the CPU-only knee halves the same way.
  2. Counts: RESOURCE_STALLS.SB is exactly 0 below the knee in both the CPU-only and device runs. It turns on at the predicted entry count (P0: 112 stores / 114 MOVDIR64B; device: K = 114 / 58 / 24 for m = 0/1/4) and grows by one write-out (~410 cycles) per extra descriptor.
  3. Manipulations: adding plain stores (P2, and --timed-stores in Q8), an SMT sibling (P3), and AVX-512/clear controls (anomaly) each move the result the way the SB model predicts and the device-ingress model does not.

Q1-c (device or IIO ingress buffer) is killed: plain stores can't reach the device, yet they move the knee. Q1-a stays ruled out.

Q8: why the timed submit costs a full ~105 ns

Runs: Q8/…02323{7,8,9}Z-B-timed-stores{0..3}-r0, Q8/…0232{40,41,42}Z-B-timed-stores*-r1, and the gap sweep Q8/…02325{3,4,5,7,8}Z-B-gap{0,25,50,75,100,150}.

plain stores inside the timed window (after the MOVDIR64B) timed plateau, K ≥ 118 (2 runs)
0 92 / 93 ns
1 189 / 189 ns
2 288 / 286 ns
3 383 / 386 ns

Each store costs one more write-out (~96 ns): once the SB is full, entries free one at a time, one per write-out. Before I fixed it, my own probe did this by accident. Rust spilled t0 to the stack between the MOVDIR64B and the second rdtscp (mov %rax,-0x288(%rbp) in the disassembly), and the plateau became 204–209 ns while the prefill slope stayed at 107 ns (ANOM/…022407Z-A-cs-x1ks-r{0,1}). The final binary times inside a single asm block.

Gap sweep with clean timing: gap 0 gives a timed plateau of 96 ns. Gap 25 ns gives 63 ns (cadence − gap − ~8 ns loop overhead), with the knee pushed to K ≈ 192. Gap ≥ 50 ns leaves the SB nearly or entirely unfilled (with gap 50 the mesh was at 1.74 GHz and only K = 384 showed 27 ns). So Q8-a holds in a clean measurement: the timed submit waits only for the next write-out, minus the gap. The old X2 result (~105 ns no matter the gap) fits Q8-b: one extra store inside the timed window adds exactly one write-out. [INFERENCE] hw-eval's measured_call(|| wq.submit(desc)) may spill like this. Its assembly was not inspected. Q8-c also holds: release is discrete, one entry per write-out.

Mid-K anomaly (X1 with heaters: submit K+1 ≈ 40 ns for K = 32..96)

Question. Why is the timed submit ~40 ns at K = 32..96 but ~10 ns at K = 0 and K ≥ 104 (X1/…020842Z-AB-heaters8-v2, X1/…020843Z-AB-heaters8-v2)?

Hypotheses written down before running:

  • (h1) Older stores (the completion-record clear, which misses because the device wrote those lines) sit in the SB ahead of the prefill.
  • (h2) It depends on mesh clock and gap through how many descriptors have already left the SB.
  • (h3) Something that depends on time, not on K.

Findings.

  1. It depends on time, not K. It reproduces with unmodified x1_knee (ANOM/…02240{5,6}Z-A-x1-repro-r{0,1,2}). With the row order reversed it goes away (ANOM/…022443Z-A-x1-rev: K = 96, 64, 32 all at 17 ns). With 16 rows at K = 64, only the first ~85–100 iterations (≈ 0.6–1.5 ms) are slow (33–47 ns) and the rest are a flat 17 ns (ANOM/…022440Z-A-cs-rep64, ANOM/…022442Z-A-x1-rep64, ANOM/…022532Z-A-cs-rep64-freq). X1's default K list simply puts K = 32/64/96 in the first ~1 ms after warm-up.

  2. It is not tied to K or to SB occupancy. Inside the window every K in 1..64 costs +23 ns, and so does K = 0 when it isn't the first row (ANOM/…02331{1,2}Z-A-kgran-h8-r*, ANOM/…022622Z-A-cs-cycleK-freq). (h1) and (h2) are killed.

  3. It does not depend on the mesh clock. At an idle mesh (heaters 0, --side both, uncore 0.24–0.88 GHz) the excess is the same +23 ns (ANOM/…02331{2,3}Z-AB-kgran-h0-r*). With gap 200 ns the window looks shorter (ANOM/…02331{4,5}Z-A-kgran-h8-gap200-r*).

  4. It slows the timing instrument, not MOVDIR64B. An empty rdtscp; rdtscp window, a plain store, and a zmm store all take +23 ns in the same rows (ANOM/…02340{0..5}Z-A-ctl-*). Per-iteration user-mode core GHz is 13–15% low during the window (e.g. 1.82 vs 2.12, 3.25 vs 3.8).

  5. Trigger: the AVX-512 memset in Slots::clear. glibc 2.35 runs here with Prefer_No_AVX512=0, so memset takes the AVX-512 variant.

    Scalar pauses before each row: 0.3 and 1 ms pauses do not bring it back, while 3 ms and 10 ms pauses bring it back at every row, with or without zmm pre-warm (ANOM/…0228{23..31}Z-A-pause*).

Explanation [INFERENCE]. The pattern matches an AVX-512 frequency-license or power transition. 512-bit instructions trigger it (ymm do not), it lasts ~0.5–1.5 ms, and it decays after somewhere between 1 and 3 ms without 512-bit work. During the transition the core is partly stalled, and any TSC-timed window inflates by about +23 ns. The exact trigger inside the clear (zmm stores vs. something else in the AVX-512 string path) is not pinned down. Rows of K = 0 at the very start sometimes did not trigger it (ANOM/…02340{0..5}Z-A-ctl-*, rows 0–1), which suggests it depends on the zmm store density or on the device-written lines. There is no SPR perfmon event for licenses (CORE_POWER.* is absent in V1.40), so this rests on manipulation, not a count.

Consequences. Earlier X1 numbers at K ≤ 96 (heaters runs) carry this artifact. The knee and plateau rows come later and are unaffected. Probes should avoid AVX-512 clears (scalar status clear, or GLIBC_TUNABLES=glibc.cpu.hwcaps=Prefer_No_AVX512) or pre-warm with zmm. The zmm pre-warm also lowers the core clock a little (10.9 vs 10.0 ns baseline). All final P2/P3/Q8 runs use --clear status.

Suggested corrections to model.js

  • store_buffer: badge "114 项（实测）". P0 measured ~114 entries: 112 plain stores fit, and the SB-full event fires at 114 MOVDIR64B. One MOVDIR64B = one entry. Entries are statically split in half when the SMT sibling is active (P3: 56 CPU-only, 60 device).
  • Q1: b → confirmed, with P0/P2/P3 as evidence (timing + RESOURCE_STALLS.SB + manipulations). c → ruled_out (P2: plain stores move the knee as C/(1+m) + D with C = 114.6; P3 halves it).
  • Knee arithmetic: knee K ≈ C/(1+m) + D, where D = descriptors written out during the prefill (≈2.5 at ~3–5 ns per submit; ≈12.7 in trace mode at ~19 ns per submit). This replaces "114 ÷ 6.5 ≈ 18–21" in the X3 animation with the same formula (C/(1+s) + D).
  • Q8: a → supported (clean timing: with a gap, timed = cadence − gap, e.g. 63 ns at gap 25 ns). b → likely for the old X2 numbers (each store in the window adds one write-out: 93/189/288/ 383 ns for 0–3 stores). c → supported as discrete release (one entry per write-out).
  • Animation fact for the full SB: "每写出一个 descriptor，store buffer 只空出一项（加上它后面的 普通 store）；被计时的 submit 等下一次写出".
  • X1 note: the "mid-K ~40 ns" values are a start-up AVX-512 transient (~1 ms after the first zmm memset), not a pipeline effect.
