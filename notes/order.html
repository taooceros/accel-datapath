order: keeping submission order while using parallel portal lines

Probe: dsa-lab/src/bin/ord_mech.rs. Run directories are relative to dsa-lab-runs/.

Question

One core is fast only when it rotates over several portal lines (one write per (core, line) at a time, ~110 ns; 16 lines reach the device cap of 143 M/s). Writes to different lines go through different CHAs and reach the device out of order (P21: 2 adjacent lines, displacement ≤ 1; 4 lines ≤ 3). Spec 3.9 guarantees execution order only for one portal address, one WQ, a one-engine group. Which mechanisms give an order guarantee and how much of the parallel speed do they keep?

"Order" here = arrival order at the WQ, which on a one-engine group is the execution order (spec 3.9; P12: one engine completes in order). Measured as in P21: 64 KiB memmoves (~2 µs each) on 1-engine.conf, completion record first-seen sweep; an inversion = i < j but j seen first.

Mechanisms and predictions (written before running)

id mechanism order prediction submit-side rate prediction
M0 one line ordered ~9 M/s (one write per ~110 ns)
M1 rotate L lines, no fence inversions (P21) min(143, L × 9) M/s
M2 rotate L lines, SFENCE after every k writes ("epochs") no inversion across epochs; inversions only inside an epoch ≈ k / (L0 + 7 ns × k), L0 ≈ 130 ns (one acknowledgement per epoch, device stage 7 ns/write): k = 1 → ~7, 4 → ~25, 16 → ~66, 32 → ~87 M/s
M2' SFENCE before every write (Linux idxd wmb() + iosubmit_cmds512) ordered same as k = 1: ~7 M/s, parallel lines give nothing
M3 lines that hash to the same CHA, no fence H-sameCHA: ordered (one CHA forwards in arrival order) / H-indep: inversions like M1 ≈ L × 9 M/s for those lines
M4 Batch: k descriptors written to memory with normal stores, SFENCE, one MOVDIR64B to one line the batches are ordered (one line); inside a batch spec 3.9 gives no guarantee: H-engine-order: no inversions on one engine (in practice) / H-batch-reorder: inversions one write per k descriptors: limited by the single engine's batch throughput, not by the write path
M5 no ordering at submit; the consumer delivers completions in sequence (reorder at the poller) completion delivery is ordered by construction; execution order is not full M1 rate; cost = extra latency until the predecessor completes

Steps:

  1. chamap: which CHA each of the 64 lines of the wq0.0 portal page maps to (CHA TOR WCiLF inserts per CHA box for 2000 writes to one line).
  2. order: M0, M1, M2 (k = 1, 2, 4, 16), M3 (same-CHA pairs vs. different-CHA pairs), M4.
  3. rate: submit-side rate for M0, M1, M2 (k sweep), M2' (fenced time and DSA PMU arrivals).
  4. brate: one-engine throughput for direct noops and for batches (M4 end to end).

  • M0, M1: supported. M2 (epochs): supported for order: 0 witnessed inversions across a fence in every run; inside an epoch the order is arbitrary. M2': ordered.
  • M3 (H-sameCHA): ruled out. Two lines on one CHA still swap (fewer than adjacent lines). Whether a pair swaps tracks the two lines' latencies [INFERENCE], not the CHA.
  • M4: H-engine-order supported in practice (0 in 200 trials at 64 KiB, 4 KiB and with a 2 MiB head). Spec 3.9 does not guarantee order inside a batch without the Fence flag; this is an observation, not a guarantee.

  • M2' (SFENCE before every write, as the Linux idxd path does): 7.6 M/s whatever the number of lines.

Device side under an order requirement

Execution order needs a one-engine group (spec 3.9). One engine:

  • direct noops without record: ≥ 142.7 M/s accepted, no drops; with record 90.5 M/s (…093044Z-A-rate-1e, …093122Z-A-rate-1e-rcr2; the first rate-1e-rcr run is invalid: completion records on untouched calloc pages).
  • Batches on one line (ordered batches), window 16, noops (…093001Z-A-brate-1-engine, core 3.9 GHz; …093313Z-A-brate-1e-noop-r2, core 2.2 GHz): B = 4: 32; 8: 57–64; 16: 57–77; 32: 64–78; 64: 81–84; 128: 87 M descriptors/s. Small B is core-bound (one batch per ~125 ns: SFENCE + one line), large B device-bound (core waits 75–90 % of the time). Four engines reach ~199 M/s but spread batches over engines (no order between batches).
  • Fence flag on work descriptors (…093309Z-A-brate-1e-mv256, …093312Z-A-brate-1e-mv4096, B = 32, window 16): noops 63–66 vs 64–78 M/s; 256 B memmoves 2.1–3.0 vs 6.1 M/s; 4 KiB 1.6 vs 5.4 M/s. Fence every 16: 5.1–6.0 (little cost).
  • Small copies on one engine are slow and depend on depth: 256 B, B = 32, window 64: 13.1 M/s; B = 8, window 64: 19.0 M/s (…093345Z-A-brate-1e-mv256-w); direct one line keeps up at 9.1 M/s; 4 KiB direct one line 5.6–5.7 M/s (23 GB/s) vs 7.0 on four engines. Direct 16-line runs overflowed the WQ, so the one-engine ceiling for small direct copies is not measured cleanly.
