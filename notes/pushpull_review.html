1. PPO calibration

  • Encodings. Every config matches SPR V1.40:
    • CHA, M2PCIe and IRP: config = UMaskExt << 32 | UMask << 8 | EventCode.
    • IIO: ch_mask 0xff (bits 36–47) and fc_mask 7 (bits 48–50).
    • The CHA TOR_OCCUPANCY events can only use counter 0. IRP boxes have 2 counters.
  • Multiplexing. In cal1 passes 1 and 2, two occupancy events share each box. The kernel rotates them every 4 ms (perf_event_mux_interval_ms = 4), so windows hold partial counts:
    • p1r0: occ_IA counted only on cha_0.
    • p1r1: occ_IA and occ_MMIO are both partial (mux = true).
    • p2r0: occ_WCILF was not scheduled on cha_12 (count 0).
  • CHA-0 clock dropouts. The rotation also descheduled the fixed CHA-0 clock: p1r0 idle mesh 0.063, p1r1 burst mesh 0.000, p2r0 idle mesh 1.251. Fixed::read compares cumulative time_enabled with time_running, so fixed_mux stays true for the rest of the run and cannot identify the affected windows.
  • Impact. The notes use only clean windows: p0 inserts, p2r1 occ_WCILF (mux false), p3 and p4. No number is affected.
  • Unloaded residency. Converting each burst with its own CHA clock gives a residency 3.4–4.8 ns shorter than the per-line step. The notes' 101–106 ns divides every burst by about 2.205 GHz.

2. PPO load runs

Window alignment, load1 (old binary). The DSA and CHA-0 counters were read outside the uncore snapshots but divided by win_ns. arrival_mps / IIO rate is 1.026–1.032, and mesh_ghz (2.255–2.267) carries the same error.

  • Every load1 TOR ns and average-occupancy value in the notes was converted with these inflated mesh values. Those values are biased low by about 3 %, and outside-TOR is biased high by about 3 % of the TOR residency.

  • The per-window mesh cannot be recovered from the raw data, so load1 ns and occupancy values cannot be corrected exactly. They are listed below as cycles only.

  • In CHA cycles load1 and load2 agree to ≤ 1 % on the shared cases:

    case load1 cycles load2 cycles
    1×16 233.9–234.1 233.9–236.0
    64 lines 962.6–970.5 963.0–969.2
    16×16, 1 WQ 3287–3317 3298–3314

  • The ranges that mix the two runs are widened by this artefact alone: 4×16 "427–440" and "8–21"; 16×16 "1454–1505", "287–339" and "208–215".

Window alignment, load2. The fixed counters are bracketed by their own TSC reads. The uncore snapshot itself takes 82–92 µs (73 reads), and the first snapshot is 5–8 µs slower than the second.

  • Events read last (the IIO events) therefore get a window about 0.2 % shorter than win_ns.
  • IIO-window rate: 142.67–142.89 M/s. The TSC-bracketed DSA counter gives 142.94–143.00 M/s for the same cases.
  • Ratios of counts read together (occ/ins, iio_clk/iio_txn_wr) are not affected.
  • No event was multiplexed or unscheduled in any load or far-calibration window.

Little's law. occ/ins summed over the 32 boxes, in CHA cycles, then divided by the measured CHA-0 GHz: the method is correct. Average occupancy = occ / (mesh × window): also correct. Only load1's mesh value is wrong.

3. Downstream: IRP, M2PCIe, IIO (claims b and c)

(b) IRP clock. In the load passes irp_clk was on uncore_irp_1, an idle stack gated at 0.023–0.027 GHz. It says nothing about irp_0, and irp_0's 2 counters were already taken by TxS occupancy and inserts. The cal2 burst count (2 229 269 irp_0 ticks over a 2.21 ms write phase) was consistent with 1 GHz but was not a same-window comparison.

Re-run R1 measured irp_clk on irp_0 in its own passes:

  • irp_0 / iio_0 clockticks = 1.000 at 1×1, 1×16, 1×32, 4×16 and 16×16.
  • IRP cycles per write = IIO cycles per write (7.000 when saturated).
  • TxS_NCS inserts / IIO writes = 1.000.
  • TxS average occupancy on the IRP's own clock: 0.172–0.176 (1×1), 2.93–3.12 (1×16), 3.35–3.65 (1×32), 7.711–7.714 (≥ 4 cores).

The notes' IRP numbers stand. "At most ~8" remains an inference from the 7.71 plateau.

M2PCIe non-empty. At 1×1 every insert adds exactly 2.000 to the not-empty count. R1 adds thresholds:

With thresh = 1 the event fires in every M2P clock, so by Intel's description the CHA_NCB ingress was never empty with ≥ 4 cores. Why the plain count is exactly 2 per clock is not explained by the event description, so the column is not a fraction and its normalization is unresolved.

  • The rate and clock in the notes come from the window-biased IIO counts.

4. PPA (claim d and push vs pull)

Arithmetic. Every table entry matches the raw data:

  • medians 389.5 … 434.0;
  • skews −1.4 … 16.8;
  • cadences 97.8 … 177.4;
  • write + MFENCE 164.3 … 242.4.

The derived values Δc = 63.97, Δ(write + MFENCE) = 66.28, Δarrival = 35.41 and 22.70 / 36.02 / 29.36 after correction all check out.

Method findings:

  • Stamp placement is sound. Both sides use lfence; rdtsc; lfence, and the submitter has MFENCE'd before MOVDIR64B, so its store buffer is empty. The poller's detection latency is common to near and far submitters.

  • The submitter's core clock enters the arrival time. About 100 core cycles lie between the stamp and the write leaving the core. In re-run R2, far blocks where the submitter ran at 2.8–3.4 GHz arrived 11–15 ns earlier than the same core's 2.2 GHz blocks:

    • cpu 44: 410–414 vs 424.8 ns;
    • cpu 54: 420–425 vs 435.7 ns.

    PPA records only the warm-up clock, which was 2.19–2.20 GHz for every block, so the clocks were probably matched but this was not verified during the trials.

  • The clock effect is large. A first pp_chk version kept all 8 submitter threads alive (run R2a). Its near cores ran at 2.2 GHz and its far cores at 3.9 GHz, and it gave raw Δarrival = 18.1 ns. It is superseded; it only shows the size of this effect.

  • Block order. pp_arrival's blocks always run near cores 4/12/20 before far cores 34/44/54 (subs = near ++ far), so any within-block drift would bias Δarrival. R2 reversed the order every other round: near-first rounds give 37.4 ns and far-first rounds 37.3 ns, so the order has no measurable effect.

  • Homes. PPA placed pages by first touch and did not verify them. R2 bound pages with mbind and read them back with move_pages: ping-pong pages on node 0 and node 1, completion record and control lines on node 0.

  • Skew. Ping-pong with both lines on one node is asymmetric for a cross-socket pair, and the bias depends on the line layout.

    • PPA put x, y and the record in adjacent lines of one page. Far-core skews (P − S): +12.7…+16.8 (both lines on node 0) and −3.2…+2.3 (both on node 1).
    • R2 placed x and y 2 KiB apart. Same-home skews: +23.1…+26.8 (node 0) and −10.9…−12.3 (node 1).
    • In the two split arrangements each direction mirrors the other. Far pairs gave +2.3…+8.2 (each line homed at its reader) and −0.5…+4.5 (each line homed at its writer).
    • Near pairs share one socket, so their true skew is 0. They gave −1.4…+5.4 across all four arrangements.
    • Conclusion: the inter-socket TSC offset (P − S) is about +2…+6 ns, with about ±5 ns method noise.

Results of R2 (20 blocks × 300 trials per core, block order reversed every other round, mesh 2.20 / 2.10 GHz as in PPA):

With the symmetric split-home skew, the corrected Δarrival is 30.6–38.6 ns, a ratio of 0.48–0.60. With the same-home skews it would be 12.0–49.6 ns, a ratio of 0.19–0.77. The per-core-pair raw ratio is 0.45–0.74 (PPA: 0.37–0.66).

Verdict. H-push is CONFIRMED (timing evidence): the ratio sits at the push prediction (0.5) and far from pull (1.5). Reaching pull needs a −60 ns skew, which every estimate excludes.

The robustness claim is OVERSTATED. PPA's 0.35–0.56 range comes from biased same-home skews. In R2 the node-1-homed estimate alone would give 0.74–0.77, which is the undecided boundary.

Model caveat [INFERENCE]. Consider a pull variant in which the far CHA also waits for an acknowledgement of the data. It predicts Δc ≈ 2 cross-socket round trips and a ratio of about 0.75. The ratio rule does not exclude it.

It is excluded because Δc (64 ns) and Δ(write + MFENCE) (66 ns) are about one round trip. Far-minus-near ping-pong round trips are about 270 ns, roughly 8 socket crossings, so one crossing is about 34 ns.

H-cap16 ruled out: CONFIRMED.

  • Rate evidence: 16 lines give 78 M/s at a 1.0 GHz mesh, and 32 or 64 lines reach the device cap even at 0.8–1.2 GHz.
  • Count evidence: one core holds ≥ 30 WCiLF in the TORs at 1×32. That value is from load1 and biased low.

The prose "the burst lifts the mesh to 0.8–1.2 GHz" misses one 1-line burst at 2.0 GHz.

6. Evidence labels

  • Warranted labels. H-recv and H-send are count evidence; H-push is timing evidence; H-cap16 rests on rate plus count evidence. The 256-line admission limit is marked [INFERENCE].
  • Inferences that should be marked:
    • "the CHA retires the entry … only after the write has gone downstream" (from residency ≈ cycle − 4…11 ns);
    • "~8-entry" IRP queue;
    • "Pushed" for the local CHA→IIO leg, which rests only on the message class;
    • "from the node-1 CHA straight to the DSA's M2PCIe" (remote-source TOR inserts at node-0 CHAs were not counted);
    • "earlier estimates were artefacts" (untested).
