pushpull: where the submit write waits, and when its data leaves the core

Probes: dsa-lab/src/bin/pp_occ.rs (PPO), dsa-lab/src/bin/pp_arrival.rs (PPA); PPM reuses arb_sat_chk. Run directories are relative to dsa-lab-runs/.

Background (arb_sat, arb_sat_review): one device accepts at most ~141 M writes/s (~7 ns/write), independent of cores, WQs, core clock and mesh clock. One (core, 64 B line) has one write in its serial step at a time; a step takes ~110 ns at a 2.2 GHz mesh, +55–67 ns from the other socket. Under saturation every line's cycle grows by a common wait (near/far shares fit W ≈ 92 ns at 16+16 lines). Throughput, shares and counts cannot tell whether the hop from core to IIO is receiver-pulled or sender-pushed with credits: both are lossless, FIFO and rate-limited by the slowest stage. Two observables differ:

  1. where waiting writes sit (at the receiver, as requests it has already seen, or at the sender);
  2. when the data leaves the core relative to a reply from the far end.

PPO: where does the extra wait sit? (written before running)

Method (as in Vuppalapati et al., SIGCOMM'24): uncore occupancy and insert counters, mean residency = occupancy / inserts (Little). Steady-state windows inside long timed bursts on dsa0 (side A, heaters, mesh ~2.2 GHz), L1-resident noop descriptors without completion records.

Step 0, calibration: K known MOVDIR64B from one core to one line; find which CHA TOR filter (IA, IA_WCIL, IA_WCILF, MMIO), which M2PCIe ingress class (CHA_IDI / CHA_NCB / CHA_NCS) and which IIO / IRP events count exactly K (idle window subtracted). Only events that count K are used.

Load points: 1 core × 1 line (unloaded), 1 × 4, 1 × 8 (below the cap), 1 × 16 (at the cap), 4 × 16 (64 lines), 16 × 16 (256 lines). At the cap, the per-line cycle is lines / 141 M/s: 113, 454 and 1815 ns, so the extra wait W ≈ 3, 344 and 1700 ns.

  • H-recv (requests reach the CHA and wait there): TOR residency of the MOVDIR64B filter grows by about W (≈ +340 ns at 4 × 16, ≈ +1.7 µs at 16 × 16). TOR occupancy (summed over the 32 CHAs) ≈ the number of outstanding lines (≈ 64, ≈ 256) unless a TOR cap is hit.
  • H-send (writes wait in the core until it may send): TOR residency stays at its unloaded value at every load; TOR occupancy ≈ 141 M/s × unloaded residency, independent of core count.
  • H-cap (both): TOR occupancy grows to a fixed cap and then stops; residency grows only up to cap / 141 M/s; the rest waits in the cores.
  • Message class: if each write enters M2PCIe as exactly one CHA_NCB insert (and ~0 CHA_NCS), the data travels with the request on the CHA → IIO leg (pushed). Anything else is reported as is.

PPA: does the data leave before or after a reply from the far side? (written before running)

Submitter S on the near socket (node 0) or the far socket (node 1) writes one noop with a completion record to dsa0, stamped with rdtsc just before MOVDIR64B (store buffer empty). A poller P on node 0 spins on the record (node-0 memory) and stamps when it changes. The device and the record path are the same for both submitters, so far − near of (P stamp − S stamp) is the extra time for the write to reach the device. Same run: per-line cadence (long same-line bursts) and single-write MFENCE time for both submitters, as the yardstick. TSC skew between the two sockets is measured by ping-pong on lines homed on each node and must be small against the effect.

With Δc = far − near per-line cadence (expected 55–67 ns, about one cross-socket round trip):

  • H-push (data leaves with the request, before any far-side reply): Δarrival ≈ Δc / 2 (~28–34 ns).
  • H-pull (data waits for a reply from the far side): Δarrival ≈ 1.5 Δc (~83–100 ns).
  • Decision: Δarrival / Δc < 0.75 → push; > 1.25 → pull; between → undecided.

PPM: does one core cap its outstanding MOVDIR64B? (written before running)

Idle mesh (--heaters 0, side both), one core, 1 / 16 / 32 / 64 lines, mesh measured per burst. With c1 = the one-line cadence at that mesh:

  • H-cap16 (a core holds at most ~16, like the LFB): rate ≈ min(141, 16 / c1) for 16, 32 and 64 lines (no gain beyond 16).
  • H-nocap: rate ≈ min(141, L / c1): 32 and 64 lines faster than 16 until the 141 cap.

  • H-recv: supported (count evidence). Up to 64 outstanding lines the growth of the per-line cycle (111 → 224 → 448 ns) appears as TOR residency (106 → ~2× → 437–440 ns, 4.5–11 ns short of the cycle), and the TOR holds one entry per outstanding line (62.5–62.9 of 64). The core's request reaches its CHA at once and waits there; the core does not hold it back.
  • H-send: ruled out (TOR residency would have stayed at ~106 ns).
  • H-cap: not shown. At 256 lines (one load point) the TOR holds 214 of 256 and ~290 ns of the 1.79 µs cycle is spent before the TOR insert, unevenly across CHAs (≈ 5 to ≈ 470 ns). Same with 256 distinct addresses, so not a same-address conflict. Mechanism open.
  • Message class: the write enters M2PCIe only as CHA_NCB (local) or UPI_NCB (remote), the data-carrying class, one per write.
  • Downstream of the CHA: the IRP's outbound request queue (towards the device) plateaus at an average of 7.71 entries under saturation [INFERENCE: ~8 slots; the maximum is not measured]. With one core at the cap (1 × 32) the IRP holds 3.6, M2PCIe is mostly empty, yet the TOR holds ~30: the CHA keeps most waiting writes itself.
  • The cap is exactly 7.000 IIO clock cycles per write (count ratio 6.999–7.003) in every saturated case, 1–16 cores, 1 or 8 WQs: 143.0 M/s at a 1.001 GHz IIO clock (TSC-bracketed DSA counter 142.94–143.00; PPM slope 143.05). The service stage is at or after the IRP's outbound queue [INFERENCE: IIO-to-device port or device ingress; IIO and device clocks are both ~1 GHz]. The 141.4–142.1 M/s measured earlier with completion records was not re-tested.

  • Δc (far − near cadence) = 64.0 ns (re-run 64.1); Δ(write + MFENCE) = 66.3 ns (66.7).
  • Raw Δarrival = 35.4 ns (re-run 36.0 for the same cores, 37.3 / 37.4 with either block order).

  • Corrected Δarrival = 30.6–38.6 ns; Δarrival / Δc = 0.48–0.60.
  • H-push: supported (timing evidence). The far core's write reaches the device about half a round trip later (push predicts 0.5), not 1.5 round trips (~96 ns). Reaching the pull prediction would need a −60 ns skew. A variant where the far CHA also waits for an ack of the data would give Δc ≈ 2 round trips; Δc and Δ(write + MFENCE) are about one, which excludes it. With the PPO far calibration: the far core hands the write to its own node-1 CHA, which sends it across UPI as one data message without waiting for node 0; the reply (and the core's next same-line write) comes about one round trip later.
  • Caveat: the submitter's core clock enters the arrival time (~100 core cycles between stamp and departure; 2.8–3.4 GHz blocks arrive 11–15 ns earlier than 2.2 GHz ones in the re-run). PPA's warm-up clocks were 2.19–2.20 GHz on every block.

What this says about push vs pull

  • Core → own CHA: the request is delivered and accepted at once; all queueing (up to 64 outstanding lines) is TOR residency at the CHA. The TOR entry lives until 4–11 ns before the core's next write to that line [INFERENCE: the CHA retires it, and the core may send again, only after the write has gone downstream]. The receiver holds the queue. Whether the 64 B data still sits in the core while the request waits is not observable with these counters.
  • CHA → IIO: one data-carrying message per write. Across sockets the data arrives ~half a round trip after issue: pushed (timing evidence). Locally the same message class is used [INFERENCE: pushed as well].
  • IIO → device: one write per 7.000 IIO cycles; the IRP's outbound queue fills in front of it under load.
