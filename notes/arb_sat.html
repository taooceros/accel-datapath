arb_sat: Hardware Arbitration on the CPU-to-DSA Write Datapath

Probe: dsa-lab/src/bin/arb_sat.rs. Run directories are relative to dsa-lab-runs/.

Target

Reverse-engineer the hardware arbitration on the path from CPU cores to an Intel DSA dedicated work queue (WQ), using outside measurements only:

  • E1: Where does the write path saturate?
  • E2: How is bandwidth shared under saturation?

Background and Prior Findings

  • Single core writing a single portal offset (64 B): serialized at ~110 ns/write (~9.1 M writes/s) at a 2.2 GHz mesh.
  • Single core rotating across multiple 64 B portal offsets of the same WQ portal page: achieves concurrent store buffer chains down to ~5.0-6.5 ns/write (~150-200 M writes/s) at 16-32 offsets. The device ignores portal address bits 11:6 (DSA spec 9.3).
  • 8 cores with 1 offset reached 77 M writes/s with each core at its solo rate (~110 ns/write); no arbitration was visible because offered load was below path capacity. Losses only ever came from WQ-FULL.
  • Hardware topology: Dual-socket Xeon Gold 6438M (Sapphire Rapids). dsa0 and iax1 are on NUMA node 0 (same root bus / IO stop 0000:75); dsa2 and iax3 are on NUMA node 1 (root bus 0000:f2). Each DSA device has 4 engines and 128 total WQ entries.
  • Posted MOVDIR64B writes are never lost in flight: EV_DWQ_SUCCESS + EV_DWQ_FULL on the DSA PMU counts every arriving write at the device. The uncore IIO counter UNC_IIO_TXN_REQ_BY_CPU.MEM_WRITE on uncore_iio_0 counts every CPU write to device memory.

E1: Saturate the Path

Question

Can the CPU-to-DSA write datapath be saturated by scaling offered load via core count (1, 2, 4, 8, 16 physical cores on node 0) and portal offsets per core (1, 4, 16)? If so, where does saturation occur, what is the maximum arrival rate, and what is the back-pressure mechanism?

Competing Hypotheses (Written Before Running)

  1. H-nosat (No saturation reachable):
    • Arrival rate keeps rising linearly with offered load across all configurations up to 16 cores × 16 offsets (~2.4 G writes/s offered).
    • Core ns/write remains at the solo rate (~110 ns for 1 offset, ~28 ns for 4 offsets, ~6.5 ns for 16 offsets).
  2. H-credit (Upstream credit back-pressure):
    • Arrival rate plateaus at a path/device bottleneck capacity $C$.
    • Cores experience upstream back-pressure: store buffer fills, causing MOVDIR64B to stall; core ns/write rises proportionally ($ns/write \propto N_{cores} / C$).
    • Device arrival counts (SUCCESS + FULL) and IIO write counts (uncore_iio_0.txn_wr) both match the actual writes sent by the cores (zero in-flight loss).
  3. H-loss (In-flight loss before arrival):
    • Device arrival rate plateaus, but core ns/write remains flat at the solo rate.
    • Writes issued by cores exceed arriving writes: either IIO < core_writes (lost in mesh/IIO ingress) or DSA_arrivals < IIO (lost between IIO and device).
  4. H-limit500 (Specific device ingress limiter):
    • Ingress bottleneck at device clock: e.g. ~500 M writes/s = 2 × 32 B transfers per ~1 GHz device clock cycle [INFERENCE].
    • Alternatively, bus ceiling at PCIe Gen5 x16 write bandwidth (~64 GB/s = 1.0 G 64B writes/s) or mesh stop ceiling.

Predictions (Written Before Running)

  • For 1 offset per core: offered load per core is ~9.1 M/s. 16 cores offer ~145 M/s, which may reach or approach saturation.
  • For 4 offsets per core: offered load per core is ~35.7 M/s. 16 cores offer ~570 M/s.
  • For 16 offsets per core: offered load per core is ~153.8 M/s. 4 cores offer ~615 M/s; 8 cores offer ~1.23 G/s; 16 cores offer ~2.46 G/s.
  • If $C \approx 500$ M writes/s, saturation will be reached at $\ge 4$ cores rotating 16 offsets.
  • Under H-credit, core write rate will be the first metric to deviate from offered load, while IIO and DSA counts will stay strictly equal to issued writes.

Comparison with Single Dedicated WQ (4-engine.conf)

Run dir: arb_sat/20261101T201042Z-A-e1-4eng.

  • Saturated arrival rate on 1 DWQ: 141.1 – 141.6 M writes/s, identical to the 8 DWQ configuration.
  • Mean ns/write under saturation: 14.2 ns (2 cores × 16 off), 28.4 ns (4 cores × 16 off), 56.5 ns (8 cores × 16 off), 113.1 ns (16 cores × 16 off).
  • In-flight loss: 0 in all 30 runs.

E1 Verdict

  1. Saturation Ceiling:
    • The write datapath saturates at 141.8 ± 0.7 M writes/s (max observed 142.5 M/s).
    • This rate is equivalent to 7.05 ns per 64 B write ($9.08 \text{ GB/s}$).
    • At a 2.20 GHz mesh clock, 7.05 ns equals 15.5 mesh cycles per 64 B write [INFERENCE].
    • The bottleneck is common to both 1 DWQ and 8 DWQ configs, pointing to the device portal MMIO ingress interface / IIO write buffer boundary rather than individual WQ logic [INFERENCE].
  2. Back-Pressure Mechanism:
    • Strongly confirms H-credit (upstream credit back-pressure).
    • When offered load exceeds ~142 M/s, device arrival rate plateaus while core-side latency scales linearly with core count: $$\text{Latency per write} \approx N_{\text{cores}} \times 7.05 \text{ ns}$$
    • Cores stall in MOVDIR64B as store buffers fill with unacknowledged posted writes.
  3. Loss Check:
    • Strongly refutes H-loss: across all 60 runs, dsa_arrivals == total_core_writes exactly (0 lost writes in flight).
    • IIO counter uncore_iio_0.txn_wr matches device arrivals within 0.1-0.2% measurement window edge effects.
  4. First Deviating Metric:
    • Core-side ns/write per core is the first counter to deviate from the solo offered load baseline as saturation is reached.

E2: Sharing Under Saturation

Question

Under path saturation (as established in E1 at ~141.5 M/s), how is bandwidth arbitrated among competing cores with asymmetric demand or different NUMA positions?

Competing Hypotheses & Predictions (Written Before Running)

  1. H-fifo (Offered rate proportional / FIFO):
    • Core A (16 off, solo ~141 M/s) vs Core B (1 off, solo ~9.1 M/s): predicted share $16/17 \approx 94.1%$ vs $1/17 \approx 5.9%$.
    • 4 cores × 16 off + 1 core × 1 off: predicted share $16/65 \approx 24.6%$ per fast core (total 98.5%), $1/65 \approx 1.54%$ for the slow core.
  2. H-source-rr (Per-source round-robin):
    • Predicts 50.0% vs 50.0% for Core A vs Core B.
    • Predicts 20.0% equal share for each of the 5 cores in 4+1.
  3. H-flow-rr (Per-flow round-robin across offset addresses):
    • Each offset line is an independent stream; predicts 16:1 ratio, matching H-fifo.
  4. H-pos (Position-based favoritism):
    • Near cores (node 0) favored over far cores (node 1) on cross-socket writes to dsa0.

E2 Verdict

  1. Demand-Proportional Arbitration (H-fifo / H-flow-rr Confirmed):
    • When cores with asymmetric demand compete under saturation, bandwidth is divided strictly in proportion to offered rate / number of concurrent offset flows.
    • In E2-AB, Core A (16 flows) captures 93.7% and Core B (1 flow) captures 6.3% (theoretical $16/17 = 94.12%$).
    • In E2-4p1, each of the 4 fast cores captures 24.6% and the slow core captures 1.6% (theoretical $16/65 = 24.62%$, $1/65 = 1.54%$).
    • Per-source round-robin (H-source-rr) is decisively rejected: cores do not get equal bandwidth regardless of offered rate.
  2. Topological Asymmetry (Near vs Far):
    • Between symmetric 16-offset submitters, Near cores are moderately favored over Far cores (57.6% vs 42.4%, ratio 1.36:1).
    • This matches the ratio of cross-socket UPI transit latencies (~155 ns solo far vs ~110 ns solo near = 1.41 ratio) [INFERENCE].
    • However, flow count completely dominates topology: under heavy cross-socket saturation (E2-NF1-4x16), 4 far cores (64 flows) push the local near core (1 flow) down to 1.9% of device arrivals.

Evidence Types and Consistency

Two independent evidence types were measured for every conclusion:

  1. Core-side timing and completion polling:
    • ticks_to_ns over TSC brackets, measuring core ns/write.
    • Per-descriptor completion record polling after Drain confirming exact accepted counts (status == 1) and dropped counts (status == 0), with 0 bad statuses (status > 1).
  2. Device and Uncore PMU counters:
    • dsa0 PMU category 0 counters EV_DWQ_SUCCESS and EV_DWQ_FULL, verified un-multiplexed (time_running == time_enabled).
    • uncore_iio_0 PMU counter UNC_IIO_TXN_REQ_BY_CPU.MEM_WRITE counting CPU writes to device memory.
    • Exact conservation across all stages: $\text{Core Writes} = \text{IIO Writes} = \text{DSA Arrivals} = \text{SUCCESS} + \text{FULL}$.

Caveats and Open Issues

  • The saturation ceiling of ~141.8 M writes/s ($9.08 \text{ GB/s}$) is lower than the theoretical PCIe Gen5 x16 link write ceiling (~64 GB/s). It reflects the internal MMIO write ingress service time of the DSA device or IIO posted write buffer ring [INFERENCE].
  • Single-core tests at 16 offsets saturate the path (~141.4 M/s) when unrolled, indicating that a single modern SPR core with 16 portal offsets can saturate the entire DSA write datapath alone.
