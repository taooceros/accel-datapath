arb_sat review (audit of E1 saturation and E2 sharing)

Auditor: ChkSat. Audited: probe dsa-lab/src/bin/arb_sat.rs, notes arb_sat.md, and the raw runs in dsa-lab-runs/arb_sat/ (e1-8dwq, e1-4eng, all e2-*). Check probe: dsa-lab/src/bin/arb_sat_chk.rs. Re-run directories are relative to dsa-lab-runs/arb_sat_chk/.

How the check probe differs from arb_sat

  • Count mode. Every core writes exactly n MOVDIR64B. The loop stamps nothing per write: it checks once per 32 writes, the same for every worker.
  • Timed mode (dur=). All workers share one TSC deadline. Each worker records t_first, t_ret (rdtscp after the last write, no fence: the W2X method) and t_fen (after MFENCE).
  • PMU sampling. The coordinator samples DSA PMU SUCCESS + FULL (all WQs) every 10 µs. Reported:
    • the least-squares slope over the 10–90 % part of the burst (slope);
    • a post-Drain bracket (pd). The coordinator checks whether all workers have fenced only at its 10 µs PMU sample points, so Drains start 0–10 µs after the last fence. After the Drains it takes the TSC and SUCCESS / FULL / IIO, subtracts the Drain descriptors, and divides the data arrivals by [first write, post-Drain]. The window therefore contains the sampling delay and the Drain latency. pd is a conservative lower bound, not a clean burst-plus-drain rate.
  • Variants.
    • src=stream,rcr=1 reproduces arb_sat: one distinct source line and completion record per write (16 MB+).
    • src=ring,rcr=0 uses 256 L1-resident descriptors and no completion record.
  • Mesh. The CHA clock is measured over every burst (mesh_ghz_burst).

Answers to the specific suspicions

(a) Metrics are partly circular.

  • arrival_mps = (SUCCESS+FULL)/burst_span (arb_sat.rs:660-664).
  • offered_mps = Σ_i writes_i / (t_last_i − t_first_i) (arb_sat.rs:517-545).
  • burst_span = max t_last − min t_first (arb_sat.rs:508-510). Here t_last is rdtscp after MFENCE (arb_sat.rs:404-405), so the store-buffer tail is included.

Arrivals equal the program count, and every worker's span is within 0.2 % of burst_span (raw: e.g. 1×16 span 1767.3 µs = dt). So "offered == arrival" holds by construction. "Offered" is the core's achieved issue rate, not offered load. It is not evidence of no loss.

The independent no-loss evidence is the count identity: PMU SUCCESS+FULL equals the program count, and the completion statuses (ok/full) equal PMU SUCCESS/FULL in all 60 E1 rows. The re-runs confirm it after Drain (post_drain_lost = 0 in every burst).

IIO is not an exact third witness:

  • arb_sat raw: IIO exceeds arrivals by 348–1758 writes (0.1–0.8 %) in every run with WQ-full drops, and by 0 in every run without drops. arb_sat reads IIO and DSA at the same instant, before Drain. At that instant the DSA count already equals the program count. So the excess is not program writes that IIO had counted but that had not yet reached the device. It is extra IIO counts. A window-edge effect from some other traffic is not excluded by the old data alone.
  • Re-runs after Drain, with the Drain writes subtracted: an excess of 56–150 remains with stream/RCR, 0 with ring/no-RCR, and 1920 for 16 cores on one line. So part of the excess is not a timing tail. Whether the larger old excess (~500 per run) is the same thing is open. Cause unexplained.

Store-buffer tail: t_ret→t_fen is 0.9–1.1 µs for one core at 16–32 lines, i.e. 130–155 write-time equivalents at 7 ns. That interval also contains MFENCE and uncore latency, so it does not prove 130–155 writes in flight. The store buffer bounds outstanding writes at ≤ ~114 per core. For a 1-offset core the tail is 11–19 µs, about 110 write-times.

If the post-MFENCE tail were omitted, the bound on the error would be:

  • 114 / 249 984 = 0.046 % for 1 core × 250k writes;
  • 16 × 114 / ~285k = 0.64 % for 16 cores × ~17.8k writes.

arb_sat's t_last is taken after MFENCE, so it includes this core-side drain. MFENCE does not guarantee arrival at the DSA; only the PMU count, read later, shows that every write arrived. The tail matters only for µs-scale bursts; see (d).

(b) E2 windows: two cases are corrupted.

  • E2-AB, reps 1–2. Core A hits MAX_SLOTS (249 984 writes) at 1880 µs, while B runs on to 2015 µs (raw e2-ab). So the reported "A 124.0 M/s, total 132.4" is an artifact. Rep 0 ran at mesh 2.09 / 1.93 GHz, below the standard condition.
  • E2-NF16-1. Near stops at 1845 µs and far at 2020 µs. The reported "near 123.6 M/s (95.6 %)" is also an artifact.
  • Every case with a 1-offset core. That core finishes 11–19 µs late, because its last ~110 store-buffered writes drain alone. In 4p1 this inflates its share from 1.55 % to 1.59 %.

Timed re-run (e2-timed, equal deadline):

  • AB: A 132.6 M/s, B 8.65 M/s; B's share is 6.2 %, or 6.13 % after removing the tail.
  • NF16-1 (e2-nf-timed): near 135.5 M/s, far 5.77 M/s; far's share is 4.1 %.

(c) Core-loop overhead: none that matters.

  • The loop does one rdtsc per 32 writes (arb_sat.rs:399) and reads a distinct 64 B source line per write from a 16 MB array (arb_sat.rs:340-394).
  • An L1-resident source without completion records is only 1–1.5 % faster: 143.0–143.3 vs 140.6–142.0 M/s.
  • At the same mesh, the ns/write does not move with the core clock: 15.6 cycles/write at 2.2 GHz and 27.6 at 3.9 GHz both give 7.05 ns (h2h-8dwq-r2).

(d) The W2X numbers do not survive a long, drain-bracketed measurement. The cap is real. W2X timed 400 writes (after 200 warm-up writes) from rdtscp to rdtscp with no fence (w2_xport.rs:433-437). With that method the re-runs reproduce W2X:

  • 16 lines: 5.9–6.8 ns.
  • 32 lines: 4.8–5.5 ns.

For the same 608-write bursts, the MFENCE-inclusive time is 7.1–7.9 ns at 16 lines and 6.5–7.0 ns at 32 lines. For bursts of ≥ 4k writes, all methods converge on 6.95–7.16 ns.

The post-Drain bracket gives 134.8–141.9 M/s. It is a conservative lower bound: the window includes 0–10 µs of coordinator sampling delay plus the Drain latency, on bursts of about 280–570 µs. The loss after Drain is 0 in every row. The cap does not depend on WQ count, WQ size or offsets per WQ.

The cap does not depend on the mesh clock either (mesh-idle-r2, no heaters):

  • At a measured mesh of 0.80 GHz, 4 cores × 16 reach 141.4–142.1 M/s and 8 cores × 16 reach 143.0–143.1 M/s.
  • In the same run, 1 core × 1 line slows to 163–218 ns at 0.9–1.3 GHz. So the mesh really was slow.

Caveat on the W2X reproduction above: W2X's 200 warm-up writes could cancel buffer occupancy between the two stamps, so this does not prove the store buffer specifically is the cause. What it shows is that the 5–6 ns figure is a short, retire-only metric. It is consistent with buffering at the endpoints (store buffer and/or uncore), and it disappears with ≥ 4k-write or fence/Drain-bracketed timing.

[INFERENCE] Short fenced bursts exceed the cap (608 writes at 32 lines: 151–153 M/s). So roughly 50 writes are accepted beyond the point where MFENCE retires, i.e. upstream of the 7 ns stage.

(e) Core placement is correct.

  • Workers 2,4,…,30,1 are 16 distinct physical cores on node 0 (lscpu: core id = cpu, SMT sibling = cpu+64).
  • The E1 heaters were 3,5,…,17, which are disjoint from the workers.
  • E1 mesh was 2.20 GHz on node 0 at start and end of both E1 runs.
  • E2 deviations from the standard condition: e2-ab started at 2.09 / 1.93 GHz, e2-nfasym at 1.93 GHz, e2-4p1 at 2.13 GHz.

Verdict per claim

E1-1: the cap is about 141.5 M/s (7.05 ns/write): CONFIRMED. Re-runs give 140–143.3 M/s across three configs, 1–8 cores, core clock 2.2–3.9 GHz and mesh 0.8–2.2 GHz.

E1-2: total flat, ns/write ∝ N: CONFIRMED with one exception. The 16-offset rows give 7.1, 14.1, 28.2, 56.6 and 112.8 ns. The exception is 16 cores × 1 offset on one WQ, i.e. one shared portal line:

  • arb_sat 4eng raw: 110.9 M/s;
  • re-run: 108.6 M/s;
  • the same 16 cores with 2 offsets: 140.3 M/s.

So the notes' "1 DWQ identical, 141.1–141.6" omits this row and is WRONG for it.

E1-3a: zero in-flight loss: CONFIRMED, for MMIO writes only. The PMU count equals the program count before and after Drain. Every posted write reached the device. But under saturation 35–68 % of them were rejected as WQ-full and never executed. Examples from E1 raw: 1×16 35.5 % FULL; 8 DWQ 16×16 67.7 %; 4eng 8×16 51.7 %. "No loss" does not mean every descriptor ran.

E1-3b: "== IIO count": WRONG as stated. IIO over-counts in every run with WQ-full drops (see (a)).

E1-3c: "credit" back-pressure: OVERSTATED.

  • What is shown: the core stalls with a full store buffer (retire-based rate equals fenced rate; MFENCE tail 0.9–1.1 µs, with ≤ ~114 writes per core in the store buffer) and nothing is lost.
  • What is not shown: a credit mechanism, or where the stage sits.

E1 inference "15.5 mesh cycles per write": WRONG. The cap is unchanged at a 0.80 GHz mesh, where 7.05 ns would be 5.6 mesh cycles.

E1 aside "a single core saturates": CONFIRMED.

E2-1: share ∝ outstanding lines (offsets): CONFIRMED, with new tests. In the equal-window runs (e2-timed):

mix measured split 16:k prediction
16 vs 4 79.97 / 20.03 % 80 / 20
16 vs 8 66.7 / 33.3 % 66.7 / 33.3
16 vs 16 50.0 / 50.0 % 50 / 50
4×16 + 4 5.9 % for the slow core 5.88 %

A work-conserving per-source round robin (max-min) would give 16 vs 8 a 50/50 split and the 4p1 slow core its full ~9.4 M/s. That rules it out.

The notes' E2-AB argument does not support this. They predicted 50/50 for round robin, but round robin is work-conserving: B only demands about 9 M/s, so RR would also give B about 6.5 %. E2-AB cannot discriminate, and the "decisively rules out" claim from AB is WRONG.

E2-2: slow core gets 2.3 M/s (1.6 %): CONFIRMED. The re-run gives 2.24 M/s and 1.59 %; after removing the drain tail it is 1.55 %, against a 1/65 prediction of 1.54 %.

E2-3: near/far 57.6 / 42.4: CONFIRMED numerically. The arb_sat windows matched (2001.7 vs 2002.5 µs); the re-run gives 56.7 / 43.3. The "position favoritism" reading (H-pos) is OVERSTATED.

The same mechanism explains the split, with no position-dependent arbiter:

  • Each line's cycle is its own path latency plus a common queue wait W. Solo, the near line takes about 105–110 ns and the far line 165 ns (e2-nf-timed: far solo 1 offset 6.05 M/s; 16 offsets 83.8 M/s).
  • Solving 16/(110+W) + 16/(165+W) = 141.5 M/s gives W ≈ 92 ns, so the model predicts 56 / 44.
  • For 16 near + 32 far the model predicts 37 / 63; the measurement is 38.2 / 61.8. The far socket wins once it has more lines.

E2 rate numbers for AB and NF16-1: WRONG (window artifact). Corrected numbers are in (b).

Corrected numbers

  • Cap: 141.4–142.1 M/s with the arb_sat source pattern, and 143.0–143.3 M/s with an L1-resident source and no completion records. That is 6.98–7.07 ns/write.
  • The cap is independent of WQ configuration, core clock and mesh clock (0.8–2.2 GHz).
  • 16 cores on one portal line: 108.6–110.9 M/s.
  • E2-AB: A 132.6 M/s and B 8.65 M/s, so B has 6.1–6.2 %; the total is 141.2 M/s, not 132.4.
  • E2-NF16-1: near 135.5 M/s (95.9 %), far 5.77 M/s (4.1 %).
  • E2-4p1: slow core 1.55–1.59 %.
  • Near/far 16 vs 16: 56.7–57.6 / 42.4–43.3.

Still needs a new experiment

  1. Locate the mesh-independent 7 ns stage. Run dsa0 together with iax1 (same IIO stop 0000:75), and dsa0 together with dsa2. If the cap is shared, the stage is in the IIO / root port; if each device gets its own, it is device ingress.
  2. Explain the shared-line limit. 16 cores on one line reach only ~109 M/s, which conflicts with W3-1's "core-local" result. Sweep 4, 8, 12 and 16 cores on one line.
  3. Explain the IIO over-count that appears with WQ-full drops plus completion records.
  4. Test the latency-plus-wait model. Inject a known extra per-line latency (e.g. a far line, or SFENCE on one core), and use 4, 8 and 32-offset mixes against the far socket.
  5. Locate the ~50-write buffer that sits past the point where MFENCE retires. This needs PMU sampling at a resolution finer than 10 µs.
