arb_ord (E3) audit

Audited src/bin/arb_ord.rs, notes/arb_ord.md and dsa-lab-runs/E3/*. The original stdout files hold only summaries, with no per-item records, so the statistics could not be recomputed from them. I added src/bin/arb_ord_chk.rs and re-ran on side A with dsa-config/1-engine.conf, 4 KiB, 50 trials, 8 heaters (mesh 2.09–2.20 GHz), and dwq_full = 0 in every run. Run dirs are under dsa-lab-runs/E3chk/.

  • orig mode: the same per-trial flow as arb_ord (issue K writes to portal+0, SFENCE, poll own records in order, stamp rdtsc at first sight). It dumps every item: core, seq, t_issue, t_seen, and pre. pre = the record was already complete when the poller first read it at its turn, so its t_seen is the time the core looked, not a completion edge. Runs: …230908Z-A-orig-n8-s4096 (K=12), …231030Z-A-orig-n4-k24, …230952Z-A-orig-n2-k48, …230953Z-A-orig-n1-k64.
  • split mode: a known-order control. One extra core (cpu18) writes all N·K descriptors in the order j = s·N + c. The true device order is therefore strict round-robin. Record j is polled by poller c (cpus 2..16), using the same polling code. Runs: …230951Z-A-split-n8-d0, …231029Z-A-split-n4-k24, …231028Z-A-split-n2-k48.

Claims

  1. Detector validated by the 1-core control: WRONG (the control is vacuous).

    • The poll loop waits for record i before it reads record i+1 and stamps each record with its own rdtsc (arb_ord.rs:450-457). So per-core t_seen is monotonic and tie-free by construction.

    • The check at :545-552 cannot fail, and inter_comp_ties at N=1 cannot be nonzero.

    • At N=1, 82% of stamps are pre (look-times).

    • The control never tests the only thing that matters, the cross-core merge.

    • The split control does test it, with the true order known:

      N adjacent true pairs seen inverted pairwise inversions measured run length measured T[i][i] measured strict-RR (truth: 1.0 / 0 % / 100 %)
      2 21.4 % 0.45 % 1.61 38.3 % 63.4 %
      4 4.3 % 0.19 % 1.02 2.0 % 86.8 %
      8 7.7 % 0.25 % 1.00 0.0 % 83.5 %

    • Gaps between truly consecutive items (N=8): p1 −465 ns, p5 −29 ns, p50 129 ns, p90 424 ns. So in this control, some stamps lag by about 0.5 µs, which is several completion slots.

    • At N=2, 71.5 % of split stamps (73.5 % of orig) are pre. pre means the record was already complete when that item's turn came, not at poll start. Those stamps are look-times, and the order among them reflects how the pollers scanned. Whether the cause is bursty completion writes or poller lag is not resolved.

    • Caveat: the split control has its own cadence (one submitter at about 110 ns per write) and its own phases. It shows that this detector can misorder under those conditions. It is not a calibrated error bound for the archived runs.

    • So the archived detector has no validated cross-core error bound, and the 4 KiB payload is not shown to be "authoritative" (notes §2).

  2. Run length collapses with N; T[i][i] = 0.12 % at N=8: the trend is UNSUPPORTED (it cannot be told apart from detector error). The N=8 value is plausible.

    • On a true strict alternation, the detector produces 1.61 / 38.3 % / 63.4 % at N=2.
    • Real N=2 (orig) gives 1.575 / 36.9 % / 63.8 %. The notes report 1.56 / 36.4 % / 62–63 %.
    • At N=4: real 1.028 / 2.8 % against split 1.02 / 2.0 %.
    • Because the conditions differ, this does not prove the N=2 and N=4 self-transitions are artifacts. It shows the archived numbers cannot discriminate strict alternation from clumping.
    • A likely confound is K = 96/N: with fewer cores, each poller has more of its own records close together. The share of pre stamps is 73.5 % at N=2, 11 % at N=4 and 0.1 % at N=8. This is an inference, not demonstrated.
    • The notes' "barrier jitter allows runs" mechanism is untested. A strictly alternating arrival order is consistent with the N=2 and N=4 statistics.
    • At N=8 the split control shows no self-transitions, and my orig re-run gives T[i][i] = 0.0 %. Both are consistent with the reported 0.12 %.
    • Strict-RR blocks: orig 67.5 % against split 83.5 %. Because the conditions differ, the share of the deficit that is real round overlap cannot be quantified.

  3. Order matches issue time for 90–99 % of pairs: WRONG as evidence (metric artifact).

    • t_issue is a non-serialising rdtsc placed after MOVDIR64B (:432-433). It can execute out of order relative to the write, so it is only a clustered software timestamp taken near instruction execution. It is not a departure or arrival time.

    • Per-core stamp spreads are 131 ns for 12 writes (N=8), 366 ns for 24 (N=4) and 558 ns for 48 (N=2), i.e. 11–16 ns per write.

    • The ~110 ns same-line departure cadence comes from earlier studies (F1, arb_sat solo ns/write). E3 does not measure it.

    • t_fence is about 180 ns. SFENCE does not order the following rdtsc, so this is not a drain time.

    • Re-run N=8 (E3chk/…230908Z), split by pair population:

      population share of pairs issue-stamp inversions sequence-number model
      same core 11.6 % 0 % matches by construction
      cross-core, different seq 81.0 % 11.8 % 0.61 % violated
      cross-core, same seq 7.4 % 31.4 % leaves them unordered

    • Overall the issue stamps invert 11.9 % of pairs; the same-core pairs inflate the "match" rate.

    • On different-seq pairs, the issue stamps do worse than the sequence index (11.8 % against 0.61 %).

    • On same-seq pairs, the sequence model is silent. The issue stamps invert 31.4 % of them (68.6 % agree): weakly informative, possibly through per-core start offset. This is an inference, and stamps that can execute out of order make it uncertain.

    • H1 was therefore not tested, and "partially supported" is not justified.

  4. "Near cores systematically earlier" ruled out: UNSUPPORTED/OVERSTATED.

    • Every run is side A with cpus 2–16 on node 0 (meta.json sides ["A"]). LAB_FAR_CPU=34 was never used, so far cores are untested.
    • Among node-0 cores, ordering looks systematic within a run. In the split control (different conditions), the per-core rank bias is ≤ 0.09 positions, so the detector alone is an unlikely cause.
    • Real per-core mean ranks still span 44.2–50.2 (re-run) and 44.4–49.2 (t200). A lead of 3 positions is most of a round.
    • The first arrival goes to one core in 160/200 trials (t200, cpu16), 47/50 (r1, cpu4), 39/50 (r2, cpu16) and 38/50 (re-run, cpu8).
    • The winning core changes from run to run, so static mesh distance is not the main cause.
    • The common TSC deadline (:423-426) removes software-barrier wake ordering. It does not remove per-core differences in spin-loop exit latency, interrupts or TSC offsets, so start skew remains a possible cause. It was not measured.
    • The s0 race is also not a clean detector event, since several stamps are only tens of ns apart.

  5. Per-source interleaving is hardware-enforced: OVERSTATED.

    • The pattern is consistent with independent ~110 ns same-line source cadences. The data do not separate that from an ingress arbiter.
    • Arrival times of about t0_c + s·110 ns would give round-robin rounds and run length 1 at N=8. With random t0_c per trial they would also give a uniform 1/7 transition matrix.
    • Within-trial pairwise round order is consistent 0.903 of the time in orig (0.971 in split). That suggests mostly stable per-core phases with some drift.
    • fixed_cycle_fraction = 0 is not evidence of a "dynamic permutation". The metric is also 0.0 on the split control, whose true cycle is fixed.
    • arb_sat E2-4p1 (24.6 % vs 1.6 % shares) already argues against per-source round-robin at the ingress.

Suspicions (a)–(f)

  • (a) Confirmed. See claim 3.

  • (b) Confirmed: no far cores were used.

  • (c) Confirmed: there is no evidence of saturation. At N=8 the bursts are 12 writes per core (about 1.3 µs) at about 73 M/s. arb_sat's own "8 cores × 1 offset" row arrives at 75.8 M/s with the solo cadence of 105.6 ns/write, against a cap of about 141 M/s. Being below the global cap does not exclude momentary request collisions at the ingress. But E3 neither measures them nor reaches the saturated regime, so it does not speak to arbitration under sustained contention. The WQ never filled (dwq_full = 0). Per-descriptor engine time (mean stamp spacing 169–259 ns) comes from the same unvalidated detector and is only indicative.

  • (d) Confirmed as a risk, not as a bound. In the split control, misordering is comparable to the spacing between completions:

    • the median truly-adjacent gap is 108–129 ns;
    • 4–21 % of adjacent pairs are swapped;
    • lags reach 0.5–0.7 µs.

    The archived runs carry no such control.

  • (e) Recomputed from the archived E3/20261101T200244Z-A-n8-s4096-t200/stdout:

    • run_length_hist {1:19169, 2:3, 3:3, 4:1, 12:1} gives 19,177 runs over 19,200 descriptors, so mean run length = 1.00119935, matching mean_run_length.
    • Self-transitions = 19,200 − 19,177 = 23 of 19,000 within-trial transitions, i.e. 0.121 %. The archived diag_mean_pct is 0.1205.
    • Strict-RR = 1775 / 2400 = 73.958 %.
    • The full transition matrix cannot be independently recomputed. Only row-normalised percentages were archived, with no per-item records or raw counts.
    • The notes' "19,176 descriptors in length-1 runs" is wrong: there are 19,169. One trial holds a 12-long single-core run.
    • For comparison, my orig re-run (E3chk/…230908Z) gives run length 1.000, T[i][i] 0 %, strict-RR 67.5 %.

  • (f) Confirmed. See claim 5.

Still needs a new experiment

  • A detector whose cross-core error is below the true spacing, calibrated with the split control. Options: slower descriptors (larger or paced, so that spacing exceeds about 1 µs), or a single poller that scans all records round-robin.
  • Far-core (node 1, --side both) ordering, with the start offset measured separately from mesh distance.
  • Arbitration under real contention: offered load above about 141 M/s, using multi-offset sources. This first needs a check that WQ order across offsets follows arrival order.
