arb_io review (audit of E4: do dsa0 and iax1 behind one IO stop compete?)

Audited src/bin/arb_io.rs, notes/arb_io.md and the five runs in dsa-lab-runs/arb_io/2026110120*. Verification probe src/bin/arb_io_chk.rs (phases given as NAME|dev@cpus|dev@cpus; same descriptors and the same 16-offset rotation as arb_io; --chunk 1 is arb_io's loop with one rdtsc per write, --chunk 32 reads the TSC once per 32 writes like arb_sat). It also records each worker's first and last TSC relative to the shared window, the worker's core GHz, and the mesh GHz of both sockets over each phase. All runs used lab run --side both --conf dsa-config/arb_io.conf with the same iax reload wrapper as the originals, 50 ms windows and 3 reps:

run content
arb_io/20261101T231006Z-AB-chk-repro --verify 1000; A4 B4 C4 A2 B2 C2 C1 D4, chunk 1
arb_io/20261101T231114Z-AB-chk-ctrl source-socket controls (Cfar, Dn0, Rn0, Bfar, A8), node-1 replica (E4 F4 G4), chunk 1
arb_io/20261101T231202Z-AB-chk-c1 A/B/C/D at 1, 2 and 4 cores per device, node-1 replica G4b, chunk 1
arb_io/20261101T231207Z-AB-chk-c32 same phases, chunk 32

In every phase of every chk run, PMU SUCCESS+FULL equals the core write count exactly, mux = false and drain ok.

Claim by claim

  1. dsa0 and iax1 alone each reach ~141 M/s: CONFIRMED. Original A = 141.1–141.5 M/s, B = 141.9–142.1 M/s. Re-runs: A = 141.0–142.3 M/s and B = 141.8–142.4 M/s at 2, 4 and 8 cores (A8 = 141.2–141.4). With chunk 32, one core alone already reaches it (A1 = 141.3–141.7, B1 = 142.0). So 141 M/s is a per-device ceiling, also seen on dsa2 and iax3. It does not depend on how many cores send.

  2. 4+4 cores: sum 239 M/s, 50:50 split: CONFIRMED. Original C4 = 236.6–239.5 M/s. Re-runs C4 = 235.5–240.0 M/s (12 reps). The two devices differ by at most 0.3 % in C2 and C4. The 50:50 split holds only when the two core sets are symmetric: with 1 core per device and chunk 32 it is 121 : 125 (the cores run at 2.2 and 3.8 GHz); with iax1 driven from node 1 (Cfar) it is 128 : 113.

  3. 2+2 cores: sum 208 M/s: CONFIRMED in direction, number at the low end. Original C2 = 206.0, 208.1 and 208.2 M/s. Re-runs C2 = 208.1–222.6 M/s (9 reps, about 216 typical). Across all 12 reps each, every C2 sum is below every C4 sum (max C2 222.6 < min C4 235.5). The notes' "26.5 % deficit" becomes about 24 % on the re-runs.

  4. "Per-core ns/write rises 28.3 → 33.5, so back-pressure reaches the cores": OVERSTATED. In arb_io, ns/write = (t_last − t_first)/writes (arb_io.rs:604). Every window is 50.000 ms, and core writes equal PMU arrivals in 104/104 device-phase entries. The column is therefore just 1/(arrival rate per core); it is not separate evidence and not a latency. That cores are throttled is real, because alone each could issue ≥ 81.5 M/s. The "posted-write credits / store-buffer exhaustion" mechanism is not measured.

  5. dsa0 + dsa2 (different IO stops) = 282, no interference: CONFIRMED, but the original control is confounded. In the original D, dsa2 is driven from node-1 cores, so C (8 node-0 cores) and D (4+4 cores on two sockets) differ in the source socket as well as in the IO stop. Re-runs remove the confound:

    • Dn0, dsa0 + dsa2 both from 8 node-0 cores: 282.0 M/s (×3). The node-0 cores and mesh can emit 282 M/s.
    • Cfar, iax1 driven from node-1 cores: 240.0–241.2 M/s, the same deficit as C4. The shared stage is on the destination side.
    • The node-1 pair dsa2 + iax3 (bus f2) reproduces it: G4b = 237.7–240.0 M/s.
    • D1 with chunk 32 = 281.8–283.7 M/s.

    The original G4 in chk-ctrl (226 M/s) is invalid: the cpu-48 worker stalled at 0.1 M/s in that run. "Localized to the IO stop" is still an [INFERENCE]: the data show a stage shared by the two functions on one root bus. That stage could be the IIO stack or the accelerator fabric behind it.

  6. 1 core each (84 + 84) shows no interference: UNSUPPORTED as evidence against contention. The 84 M/s is the probe's loop, not a device or IAA property (suspicion a):

    • with one rdtsc per write, a core issues 81.5 M/s at 2.2 GHz core clock and 134–139 M/s at 3.5–3.8 GHz (chk-c1, chk-ctrl). The originals ran with core_ghz 2.20;
    • with chunk 32 the same core reaches 141.5 M/s even at 2.2 GHz, which matches arb_sat's 141 (7.07 ns).

    At full offered load, 1 core per device does interfere: C1 = 243.4–246.9 M/s against A1 + B1 = 283.4 (deficit about 13 %, chk-c32). The notes' "threshold" story is also wrong. The C sum is not monotonic in source count: 1+1 cores give 245, 2+2 give about 216 and 4+4 give about 238. Chunk-1 C1 with one fast core offers 216–220 M/s and loses only 1–3 %. The data fit no fixed IO-stop capacity of "~210–240".

Suspicions

  • (b) Window alignment: OK. Rates use the shared [start, end] TSC window (arb_io.rs:579), not per-device times. In the re-runs every worker starts within 66 ns of the shared start. Overrun past the end is ≤ 2.1 µs, except the stalled cpu-48 worker in G4. No side finishes early.
  • (c) IAA counting: OK. The format matches DSA (event = config:4-31, filter_wq = config1:0-31).
    • Single thread, K = 1000 per device: SUCCESS + FULL = K + 1 exactly (the +1 is the Drain), on all four devices.
    • Paced, 1 offset: FULL = 0 and completion records = SUCCESS − 1.
    • Burst over 16 offsets (iax1): SUCCESS 422 + FULL 579 = 1001.
    • The originals also match core writes exactly with millions of FULLs per phase.
  • (d) Cores and heaters: mostly OK, but the notes misstate them. The core sets are disjoint (arb_io.rs:353-357). SMT siblings are n+64, and heaters exclude used CPUs and their siblings (lib.rs:485-497). Node 0 has 32 cores; 17 are used.
    • The node-0 heaters are actually cpus 0,1,3,5,7,9,11,13, not "24..31".
    • The 2c iax1 cores are 10 and 12, not "6, 8".
    • Mesh GHz is measured only at run start and end, not per phase. The 1c run started at 1.98 / 1.75 GHz, which contradicts "2.2 GHz every run". Per-phase re-measurement shows 2.2 GHz on node 0 in every phase.
  • (e) 2c vs 4c: reproducible. See claim 3. C2 spread is 208–223, against C4 235.5–240.
  • (f) Fair comparison: A/B/C are matched; D is not. Phase C uses exactly the A core set plus the B core set, with the same offsets, loop and window (arb_io.rs:486-505). D changes the source socket (see claim 5).

Other notes defects

  • Run 4c-r1 (20261101T200432Z) is not mentioned. Its first phase (A rep 0) recorded 0 writes on every worker, and the cause is not established. The code allows it: start_tsc is fixed at arb_io.rs:523-526, before the mutex and bar_start release. Any stall over 50.2 ms before a worker reaches its loop leaves writes = 0, and nothing flags it.
  • The notes omit the 1c run's D rep 2, where dsa0 runs at 102.0 M/s (9.80 ns) while dsa2 stays at 84.3. That is not cross-device interaction. The 1-core loop is core-clock-bound: in the re-runs the same loop gives 81.5 M/s at 2.2 GHz and 134–139 at 3.5–3.8 GHz, so 102 fits a core at an intermediate clock. The original records no per-worker GHz. The chunk-32 D1 re-run is additive (281.8–283.7).
  • The "~5–6.5 ns/write per core solo" in the header is wrong for this loop: one core manages 11.9 ns.
  • Labels such as "p50" are attached to single-run tables.

Still needs an experiment

  • Mechanism of the shared stage. Why is the C sum non-monotonic in source count (1+1: 245, 2+2: 216, 4+4: 238)? Sweep 1–8 cores per device with chunk 32. Add IIO occupancy/credit events, and test whether the per-device ceiling and the shared stage are the same resource.
  • Placement inside the root bus. Is the shared stage the IIO stack or a fabric behind it? Use a device on a different IIO stack of the same socket (none is enabled now).
  • Per-core clock control. Turbo is uneven: about 3.3–3.9 GHz on one core per group, 2.2 GHz elsewhere. It matters for loop-bound phases (chunk 1, 1 core).
