w2xport group: what serializes the per-core write transport (Q5 follow-up)

Run directories are relative to dsa-lab-runs/. Probe: dsa-lab/src/bin/w2_xport.rs. One core writes a round-robin pattern of streams (wq0.0, wq0.0@64 = 64-byte offset in the portal page, wq0.0@lines4 = 4 streams at offsets 0/64/128/192, mem = an ordinary write-back page). Noop descriptors are built byte by byte, so they are identical for DSA and IAA. Each stream has its own completion records; after every burst the probe Drains every WQ of the pattern and counts records. --pmu adds device EV_DWQ_SUCCESS / EV_DWQ_FULL per WQ. Modes: steady (F1 cadence per pattern and per variant plain / sfence after each write, plus the k-write + MFENCE sweep k = 0..16), decay (long bursts and k-sweeps, each carrying the mesh and core GHz of its own 2-5 ms window, while UFS lowers the mesh) and offsets. All runs: --side both, dsa-config/cadence-2dwq-1g.conf (dsa0: wq0.0 + wq0.1, dsa2: wq2.0 + wq2.1, size 64 each, 4 engines), heaters 8x1@0+8x1@1 (mesh 2.2 GHz on both sockets) unless noted.

Summary of verdicts

  • W2-1: per destination line, not per core, WQ, device or IIO stack. One core alternating between two portals writes at half the solo time. That holds for two WQs on one device, for dsa0 + dsa2, and also for two 64-byte offsets of the same WQ portal page. N distinct lines give c/N per write, down to a floor of ~5-6.5 ns at 16-32 lines. The PMU counts every write as accepted or WQ-full, and none are lost with 1 or 2 streams (completion records). The serial step (≈ 31 ns + b mesh cycles) is a per-(core, destination line) chain, and the chains run concurrently.
  • W2-2 (IAA): not DSA-specific. The IAA portal (iax1, same root bus as dsa0) shows the same per-line serial step: the same a + b/f_mesh form with a ≈ 29 ns, the same halving with two lines, and the same SFENCE behavior. On the 8 sampled offsets (every 8th line), its per-line cadences match dsa0's with the offsets mirrored (IAA offset o ↔ DSA offset o XOR 0xE00): within 0.4 ns at 2.2 GHz, and within 1 mesh cycle of b over 0.8-2.2 GHz for the two pairs fitted. So the step length follows the destination line, not the device type [INFERENCE that it is set by the physical address via a hash]. Every write in the single-stream and DSA + IAA patterns was accepted (IAA PMU and completion records); the IAA multi-offset rows overflowed the 1-engine WQ.
  • W2-3: t(k) = t0 + (L − c) + k·c, linear from k = 1. The 56 ns intercept at 2.2 GHz is mostly the rdtscp + MFENCE overhead t0 = 36.7 ns (≈ 78 core cycles, not mesh-clocked). The true overlap per write is L − c = 14.2 ns + 11.7 mesh cycles (19.5 ns at 2.2 GHz, 29 ns at 0.8 GHz), not ~60 ns. So only ~5 ns of the intercept is mesh-clocked at 2.2 GHz. A single write takes L = 47.6 ns + 181 mesh cycles (130 ns at 2.2 GHz) to be acknowledged; the slope is c = 36.0 + 165.4 mesh cycles. SFENCE after every write removes all cross-line concurrency: ns/write ≈ L + 3-7 ns.

W2-2: is the handshake specific to DSA portals?

IAA (iax1 on root bus 75 with dsa0; iax3 on f2 with dsa2) gets the same noop. Generic core → IIO posted-write step: the IAA portal shows the same cadence as DSA for the same core at 2.2 GHz (within ~2 ns), the same a + b(core)/f_mesh form over the mesh range, and the same b ordering across cores (cpu12 < cpu2 < cpu30). DSA-specific (a device-side ack): IAA differs.

W2-3: overlap structure

t(k) = time for k writes + MFENCE on an empty WQ. Wave 1: t(k) ≈ 58 + 111 k at 2.2 GHz (cpu2 → dsa0). Model: write j leaves the core at j·c and is acknowledged L after it leaves; t(k) = o + L + (k−1)c, so intercept I = o + L − c, with o = rdtscp + empty MFENCE (k = 0, core-clocked). Predictions: t(k) is linear from k = 1 (no kink, i.e. only one write is in the serial step at a time); slope = steady cadence at both mesh clocks; if L and c are both mesh-paced, (I − o) scales with 1/f_mesh; if only c is mesh-paced (the ack latency is fixed), (I − o) grows as the mesh slows less than c. SFENCE between writes: wave 1 shows 1 write + SFENCE ≈ 20 ns (rdtscp pair ≈ 15), so SFENCE does not wait for the ack; prediction: the cadence is unchanged with SFENCE between writes.

W2-0: does a portal page accept writes at every 64-byte offset?

Spec (DSA 9.3): "bits 11:6 are ignored; any 64-byte-aligned address on the page can be used with the same effect". Run W2X/20261101T025111Z-AB-offsets: one noop to each of the 64 offsets of wq0.0, wq0.1 and wq2.0. Result: 64/64 offsets complete with status 0x01 on all three WQs, and the Drain after them completes. Evidence: completion records.

Verdict W2-1. H-core (one serial credit per core) is ruled out: alternating two destinations halves ns/write ((a) 55.1-55.2 vs 107.5-110.6 solo; it would have stayed ~110). For near + far ((b)) the per-write time is 77.0-77.6 = max(near, far)/2, not the mean (132.5). H-dest (per WQ / portal page), H-dev and H-IIO are also ruled out: two offsets of the same WQ portal page give the same halving as two WQs or two devices ((c) 55.1-56.9). Surviving: the serial step applies to consecutive MOVDIR64B to the same 64-byte destination line; writes to different lines run concurrently. N lines give c/N per write (3, 4, 8, 16 lines: 36.7, 28.1, 14.1, 6.5 ns vs 110.5/N = 36.8, 27.6, 13.8, 6.9) down to a floor of about 5-6.5 ns per write at 16-32 lines, which is then the core's own MOVDIR64B issue rate [INFERENCE: ~11-14 core cycles at 2.2 GHz]. Evidence: (1) timing under manipulation of the destination set (3 runs on cpu2, 1 on cpu34, two cores with different b); (2) counts: for every 1- and 2-stream pattern, 0 missing completions and DWQ_SUCCESS = writes + Drains, DWQ_FULL = 0. With ≥ 3 lines to one WQ, the device's noop service (4 engines, WQ size 64) cannot keep up with 36-190 M writes/s, and the losses are WQ-full drops counted by the PMU (SUCCESS + FULL = all writes). The losses do not come from the transport. (3) a second timing signature: in the k-write + MFENCE sweep, writes to different lines complete together, and each line forms its own +c chain. Caveat: these are posted writes from one core. Whether two cores writing the same line also serialize (core-local hazard vs a shared, address-hashed agent) is the next question below.

SFENCE after every write (prediction "unchanged" is ruled out): it removes all cross-line concurrency. Every pattern then runs at ~130-135 ns per write on near lines (cpu2), and near + far gives the mean of the two SFENCE solos (154.8-155.4 vs (132.6 + 177.0)/2 = 154.8). This is the per-core serial behavior that H-core predicted, but it only appears when the core is forced to order the writes. Per write it is L + 3-7 ns (see W2-3) [INFERENCE: the next write waits for the previous write's completion, the event MFENCE waits for, plus fence issue cost]. A single write + SFENCE is still only ~20 ns (wave 1), so SFENCE blocks the next store, not the instruction stream.

Address dependence of the step (side observation). Run W2X/20261101T025503Z-AB-line-scan-cpu2-12 (each of the 64 lines of wq0.0 alone, 3 reps, cpu2 and cpu12, 0 missing): cpu2 → wq0.0 lines span 91.7-113.3 ns (median 104.6). cpu12 → wq0.0 spans 80.5-110.6 (median 104.6). Far cpu2 → wq2.0 every 8th line spans 154-193. The per-line pattern differs between the two cores (r = −0.14 over 64 lines). So wave 1's "b depends on the core" was measured on line 0 only: b is a property of the (core, destination line) pair [INFERENCE: consistent with the line's address being homed at an address-hashed agent at a core-dependent mesh distance; not tested further].

MOVDIR64B to ordinary memory (side observation, not an answer to W2-2). mem (one anonymous write-back page on node0) in r2/r3: one line 136.1 / 125.9 ns per write, two lines 69.9 / 63.4, with SFENCE 172 / 158. Same-line serialization with the same halving, so the per-line chain is not specific to device portals. This path does not cross an IIO, so it says nothing about the IAA question.

Verdict W2-2. The prediction "generic core → IIO posted-write step" holds, and is sharpened: the IAA portal has the same a + b/f_mesh form (a = 28-29 ns for both device types) and the same per-line concurrency. [INFERENCE: the step depends on the line's physical address through a hash in which address bit 17 and offset bits 9-11 interact, which is what an address-hashed home agent (CHA/LLC slice) selection would do. The per-line cadence is then set by the core-to-home-agent distance. Not tested directly.] Caveat: the far IAA row varies between runs on cpu12 (174.7-183.3), unlike any near row.

Verdict W2-3.

  • t(k) is linear from k = 1 (fits over k ≥ 1 and k ≥ 2 give the same intercept within 0.6 ns; rmse 0.7-1.4 ns at a fixed mesh). There is no kink, so only one write of a line is inside the serial step at a time (prediction holds).
  • slope = steady cadence at every mesh clock (prediction holds; now shown over 0.8-2.2 GHz, not only at 2.2).
  • Intercept: the ~56 ns at 2.2 GHz is ~37 ns of measurement overhead (rdtscp + MFENCE, t0, which is core-clocked: 78 cycles at 2.1 and at 3.75 GHz, and does not move with the mesh) plus the true overlap L − c ≈ 19.5 ns. Of that, ~12 mesh cycles (5.3 ns at 2.2 GHz, 14.6 ns at 0.8 GHz) are mesh-clocked; the remaining 14.2 ns is not. The core-clock contrast lowers L − c by 3.5 ns at the same mesh, so part of the 14.2 ns is core-clocked [INFERENCE, ~17 core cycles from two core clocks only]. The two-point heated/idle comparison (r1) agrees: L − c = 15.7-19.0 → 31.7.
  • Correction to wave 1: a single write is acknowledged after L ≈ 126-130 ns at 2.2 GHz (47.6 ns + 181 mesh cycles), not ~170 ns. 170 included t0. The overlap is ~16-20 ns per write, not ~60 ns. The next write to the same line leaves c after the previous one, about 12 mesh cycles + ~14 ns before the previous write's acknowledgement reaches the core.
  • SFENCE between writes: slope = L + 3-7 ns at both mesh clocks (132.8 vs L 126-130 hot; 281.2 vs 276.0 idle), and the intercept falls to ≈ t0, i.e. each write waits for the previous one's acknowledgement [INFERENCE: the 3-7 ns may be fence issue cost, so this is "no overlap", not a separate latency measurement].

Suggested corrections to model.js (the lead edits it)

  • c2p_path / Q5: replace "per-core serial step" with "per (core, destination 64-byte line) serial step; different lines (any offset of the same portal page, other WQs, other devices) proceed concurrently". Per-write step c ≈ 36 ns + 165 mesh cycles for cpu2 → wq0.0 line 0; b depends on the (core, line) pair (92-113 ns across wq0.0's 64 lines from cpu2 at 2.2 GHz).
  • W2-2: the same step applies to IAA portals (iax1: a ≈ 29 ns, b set by the line address; an IAA line and the DSA line at the mirrored offset have the same a and b). Treat it as the generic core → IIO posted-write path, not as a DSA portal property.
  • Overlap: single-write acknowledgement L ≈ 130 ns at 2.2 GHz (47.6 + 181 mesh cycles); overlap L − c ≈ 20 ns (14 ns + 12 mesh cycles); the k-write MFENCE intercept includes ~37 ns of rdtscp + MFENCE overhead. Replace "~60 ns overlap".
  • Submission rate: one core can submit to one DWQ at ~28 ns per descriptor (4 portal offsets, 0 drops in one of two runs at WQ size 64) or ~14 ns (8 offsets, device-limited: WQ-full drops). The ~110 ns cadence is a same-line limit, not a submit-rate limit. Software that rotates portal offsets (spec 9.3: bits 11:6 ignored) avoids it. Ordering is then lost: spec 3.9 guarantees execution in receive order only for one-engine groups and descriptors "submitted to the same WQ using the same portal address". W3-2 measured it: on a one-engine group, 2 or 4 rotated offsets reorder the completion order in ~200/200 trials (displacement ≤ lines − 1), while one offset stays in order (clean run: 0 inversions in 400 trials).
  • W3-1: the per-line serialization is inside each core. Several cores writing the same portal line do not slow each other (2 cores 18.2-19.8 M/s, 4 cores 37.5 M/s on one line). Do not model it as a shared per-address agent.
  • SFENCE after each MOVDIR64B costs ~15-22 ns per write at one line (cpu2 110 → 133; cpu34 97 → 112) and removes all cross-line concurrency.

Next questions

  • Core-local or shared hazard: answered in W3-1 (core-local).
  • What sets b? The per-line cadence follows the physical line address (W2-2 mirror). Map the 64 lines of one portal page against cores (b per (core, line)) and compare with the CHA a line is homed at (e.g. uncore_cha TOR occupancy counters per CHA while one line is written).
  • Descriptor ordering across offsets: answered in W3-2 (it breaks). Open: a data-based second detector (e.g. two descriptors writing the same destination with different sources; the final content names the later one), and whether an SFENCE every N writes is enough to bound reordering at less cost.

W3 (second round, Main's request)

Predictions (written before running)

W3-1: is the same-line hazard core-local or shared? Two cores on node0 (cpu2, cpu4; heaters 8x1@0+8x1@1 exclude both and the coordinating thread's core), each with its own descriptors and completion records, start writing on a common TSC deadline. Phases (interleaved, several reps): A alone on line X (wq0.0@0), B alone on X, B alone on Y (wq0.0@64), A + B both on X, A on X + B on Y, A on wq0.0 + B on wq0.1 (P6 control).

  • Core-local hazard (each core's own same-line rule): A + B on X keep their solo ns/write, aggregate ≈ 2/c (≈ 18 M/s), same as X + Y.
  • Shared, address-hashed agent holding the whole step: A + B on X each slow to ≈ 2c (≈ 220 ns), aggregate stays ≈ 1/c (≈ 9 M/s), while X + Y keeps 2/c.
  • Shared agent holding only part of the step (e.g. the home agent's share, without the core-to-agent transit): aggregate between 1/c and 2/c; 1/aggregate is the length of the shared part. Second evidence: completions per thread after Drain (0 missing) and DWQ_SUCCESS = writes + Drains.

W3-2: does rotating portal offsets break submit order? One-engine group (dsa-config/1-engine.conf: wq0.0 size 128, engine0.0). 32 descriptors per trial, submitted back to back, round-robin over 1 (control, same address: spec 3.9 guarantees order), 2 or 4 offsets of wq0.0. Two order detectors: (i) slow descriptors (memmove 64 KiB, ~µs each on one engine), the order in which completion records become visible to a polling loop; (ii) a data chain: descriptor i copies 8 bytes from slot i to slot i+1, starting from a token in slot 0; any descriptor that runs before its predecessor has written breaks the chain. Prediction: the control is in order in every trial (and the chain is complete unless the engine pipelines reads ahead of earlier writes; the control calibrates that). Writes to different lines leave the core concurrently (W2-1), so arrival at the device may be reordered: rotated offsets → some inversions, mostly within a group of consecutive descriptors on different lines. If the device keeps arrival order and the core emits lines in program order, no inversions.

Verdict W3-1: the same-line hazard is core-local. A shared per-address stage, if any, holds each write for at most 1/37.5 M/s ≈ 27 ns, and the device's WQ limit is reached first. Evidence: (1) timing under manipulation (same line vs different line vs WQ; core pairs cpu2+cpu4 (2 runs) and cpu2+cpu12, plus one 4-core set; 4 runs); (2) counts: PMU SUCCESS + FULL = all writes; no missing on the same-line 2-core phases. This revises the W2 [INFERENCE]: the serialization (one outstanding MOVDIR64B per destination line) is kept inside each core. Only the step length depends on the line's address (W2-1 line scan, W2-2 mirror), e.g. because the response the core waits for comes from an address-dependent place [INFERENCE].

W3-2 results: execution order with rotated offsets

Probe mode order: one-engine group (dsa-config/1-engine.conf: wq0.0 size 128, engine0.0), cpu2, no heaters (ordering, not timing). Per trial: 32 memmove descriptors of 64 KiB each (Cache Control set; distinct destinations, common source), written back to back, round-robin over the pattern's offsets; then a loop polls all 32 completion records and notes the sweep in which each first appears (~1500-2800 sweeps per trial, ~50 sweeps between consecutive completions). An inversion = a pair i < j with j seen in an earlier sweep than i. 200 trials per pattern. Runs: W3/20261101T034337Z-A-order-memmove-r2, ...034402Z-...-r3, ...034403Z-...-r4, ...034415Z-A-order-memmove-r5-touched. In r2-r4 the same-address control had a 0x03 on descriptor 31 in every trial: a probe artifact (the destination buffer's trailing partial page was not faulted in). r5 uses touched() buffers and has no bad statuses. Ordering numbers are the same in all four runs.

Verdict W3-2: with rotated portal offsets, completions no longer follow submit order, even on a one-engine group. With one portal address, the completion order matched submit order in every clean-run trial (r5: 0 inversions in 400 trials, 200 at @0 and 200 at @64). Over all four runs: @0 had 0 inversions in 800 trials (the r2-r4 0x03 artifact hit only the last descriptor), and @64 had 1 inverted pair in one of 800 trials. With 2 or 4 adjacent offsets almost every trial is reordered, bounded within a round of consecutive writes to different lines (displacement ≤ lines − 1, with one exception). The observation is completion-record visibility order. [INFERENCE: on a one-engine group this reflects execution order, and the reordering arises because the writes reach the device in a different order from program order. That fits W2-1: writes to different lines leave the core concurrently and are not ordered with respect to each other.] How often a pair swaps depends on the two lines: adjacent @0/@64 swap in nearly every pair, @0/@2048 rarely [INFERENCE: it follows each line's latency]. This matches spec 3.9, which promises order only for "the same portal address". Evidence: one type (completion-record visibility order with ~1 µs separation). A data-based second detector was tried and failed: descriptor i copies 8 bytes from slot i to i+1 (W3/20261101T034245Z-A-order-chain). It breaks at slot 2 in every trial even for the same-address control, because the engine reads the next source before the previous write is visible. So it detects engine read-ahead, not reordering, and is not used. (The first memmove run ...034245Z-A-order-memmove agrees with the table.) Practical consequence: software that rotates offsets to beat the ~110 ns same-line step must not rely on submit order. Whether an SFENCE between writes restores the order was not tested here. It does remove the cross-line concurrency (W2-1), at ~130 ns per write.
