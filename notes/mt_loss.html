mt_loss: are MOVDIR64B descriptors lost only when the DWQ is full?

Probe: dsa-lab/src/bin/mt_loss.rs. Run dirs are relative to dsa-lab-runs/.

Question

Claim under test: on an Intel DSA dedicated WQ (DWQ), a submitted descriptor is lost only when the WQ is full. It is never lost because several threads write MOVDIR64B to the same DWQ portal at the same time.

Predictions (written before running)

  • H0 (claim): every MOVDIR64B write from any thread reaches the device intact. A descriptor is lost if and only if it arrives while the WQ is full.
  • H1 (alternative): concurrent writes from several cores to one DWQ portal can be lost, merged or corrupted, whether or not the WQ is full.
regime H0 predicts H1 predicts
R1: flow-controlled, total in flight ≤ L = 120 < 128 (never full) 0 lost; PMU FULL = 0; occupancy max < 128 loss > 0 that grows with thread count or with same-address contention
R2: uncontrolled bursts, WQ forced full missing == PMU FULL exactly, and SUCCESS + FULL == writes + Drains; losses cluster in WQ-full time windows (none before ~140 accepted) missing > FULL, or SUCCESS + FULL < writes; losses spread in time, including before the WQ could be full
R3: flow-controlled boundary, L ∈ {128, 140, 150, 200, 400} 0 lost and FULL = 0 for L ≤ 140 (capacity 140 = WQ 128 + 3 × 4 engines) for every N; losses only for L > 140 and then missing == FULL losses that depend on N rather than on L, or missing ≠ FULL
integrity (mm64/mm4096, every regime) every accepted memmove copies exactly its own tag; no destination written without a completion record wrong tag, torn copy, or a destination written for a descriptor that has no record

Notes on the predictions:

  • N = 1 with noops cannot outrun the device (one core ~9.4 M/s; one engine is faster), so R2/R3 noop rows with N = 1 may show 0 loss. A 4 KiB memmove (device ~30 GB/s ≈ 136 ns per descriptor) is slower than one core's ~106 ns cadence, so N = 1 mm4096 bursts must lose, with missing == FULL.

Method

  • One process. N worker threads are pinned to distinct physical cores and share one mmap of /dev/dsa/wq0.0. A coordinator runs on cpu20. Workers start on a common TSC deadline (500 µs ahead). Thread sets: n1 = {2}, n2 = {2,4}, n4 = {2,4,6,8}, n8 = {2,4,…,16} (node 0), and x4 = {2,4} on node 0 plus {34,36} on node 1. All x4 workers write dsa0.
  • Each worker allocates its own memory after pinning: page-aligned regions for descriptors, completion records (one 64-byte line each), src, dst and write stamps, every page prefaulted. Address modes: same (portal+0) and offsets (portal + 64·t).
  • Identity check: for memmove, src[0..64] = (magic, thread, seq) + 6 derived words + checksum. When a record arrives, dst must equal the expected tag, and the rest of dst must equal src. Then dst is zeroed. Also counted: a destination written with no record (dst_without_record) and records that appear after a slot was retired (late).
  • flow (R1, R3). Each thread has at most its share of L descriptors in flight (L split evenly). In each pass it polls its own records. Completed slots are verified, cleared and re-tagged; then one SFENCE and a resubmit of every free slot. A slot with no record after 20 ms counts as LOST and is reused. Each phase runs 2 s (R1) or 1 s (R3).
  • blast (R2). B = 2000 back-to-back MOVDIR64B per thread with no fence, then SFENCE. A TSC stamp follows each write.
  • After every phase or burst: the coordinator waits until occupancy < 128 (R2 rerun only; ≤ 5.8 µs), sends a Drain, every thread scans its records, a second Drain runs, and there is a rescan for late records.
  • Device PMU: 8 events, all filtered to WQ 0, opened with time_enabled/time_running so that multiplexing is detected:
    • EV_DWQ_SUCCESS (0x10), EV_DWQ_FULL (0x20), disp_wq (cat 1, 0x20);
    • op noop / drain / memmove (cat 3);
    • cpl_ok / cpl_err (cat 4).
  • The coordinator reads the WQ occupancy (sysfs pread, an MMIO read) in a loop while the workers run. SWERROR is read before and after each phase.
  • Conditions:
    • dsa-config/4-engine.conf: one DWQ, size 128, 4 engines.
    • --side both, so dsa2 is idle.
    • 8 L2 heaters 8x1@0, which exclude the worker and coordinator CPUs. Mesh node 0 at 2.19-2.20 GHz (R1, R2 rerun), 2.08-2.19 (R3) and 1.99-2.19 (first R2 set); node 1 at 1.90-2.20.
    • Worker cores at 2.2-3.9 GHz after warm_up.

Checks computed per row (all in the run JSON, rows[].checks):

  • success_plus_full_minus_writes_minus_drains = SUCCESS + FULL − writes − Drain attempts (H0: 0).
  • full_minus_missing_minus_dropped_drains (H0: 0). In the R2 rerun, also full_minus_missing (literal, H0: 0).
  • success_minus_records_minus_completed_drains: every accepted descriptor wrote a record (0).

Calibration

MTL/20261101T072552Z-AB-calib-h8: one thread; K = 100 and 1000 noop or mm64; 5 bursts × 2 reps per (op, K), 40 bursts in total. Every record was polled, then 2 Drains.

Result:

  • SUCCESS = K + 2 exactly.
  • FULL = 0.
  • disp_wq = SUCCESS.
  • op_noop or op_memmove = K.
  • time_running == time_enabled in every row (not multiplexed).

Calibration facts:

  • op_drain counts 4 per Drain (once per engine).
  • cpl_ok = K + 4 per Drain.

These two rules hold in every later row; they are checked for all 2,612 rows in the analysis below. The first calibration run (MTL/20261101T072528Z-AB-calib) gave the same counts but had 16 heaters, so it is superseded.

Totals in the primary set:

First set (Drain right after the burst):

  • Runs: MTL-R2/20261101T072934Z-AB-n1-r1, …072935Z-n2-r1, …072936Z-n4-r1, …072938Z-n8-r1, …072940Z-x4-r1, …072941Z-n1-r2, …072942Z-n2-r2, …072943Z-n4-r2, …072944Z-n8-r2, …072945Z-x4-r2.
  • Same results: 2,478,292 lost; FULL = missing + dropped Drains in all 1,080 bursts.
  • Three bursts (n4 and n8 mm4096 same) show FULL = missing + 1. In each, the first Drain attempt hit the still-full WQ: dropped_drains = 1, and the resubmitted Drain completed. These are the 119,127 vs 119,129 seen in the n4-r1 summary.
  • The rerun above removes this case: it waits for occupancy < 128 before the Drain. All its rows then match literally.

Do losses cluster in WQ-full windows? Yes, by four measures:

  • Within each thread, every loss lies at or after the first missing index. That index is ≥ 37 in every multi-thread burst except one (see anomalies), and 1176-1676 for the single thread.
  • In every multi-thread burst, 99-100% of the lost writes fall in a time bin (1/20 of the burst) in which another thread also lost writes (timeline.lost_in_bins_where_another_thread_lost).
  • The per-bin loss fraction is flat during steady state and equal across threads. For example, n8 mm4096 is ≈ 0.78 in every bin, which matches 1 − μ/λ with μ = 4 KiB at ~31 GB/s and offered λ ≈ 33 M/s.
  • Occupancy (sampled max per burst): it reached 128 in all but 5 loss bursts (125-126 there). Bursts without loss peaked at ≤ 126 (most at 0-1). The sampler has no time alignment with individual losses.

Single-thread control (n1 mm4096): it loses only in the second half of the burst (bins 14-19), and missing = FULL there too.

A rough cross-check from (SUCCESS − Drains − 140) / burst span gives the implied device service rate:

  • 8.3 M/s (34 GB/s) for n1 and n2;
  • 8.0 for n4;
  • 7.5 for n8;
  • 7.6-7.8 for x4.

This is close to the ~30 GB/s copy limit in capacity.md. N = 8 is ~9% lower, but by the device's own FULL count those extra losses are still WQ-full drops.

R3 results:

  • For L ≤ 140: 1.06 × 10⁹ descriptors, 0 lost, FULL 0. 95% UB 2.8 × 10⁻⁹.
  • In all 296 R3 rows (summed into the cells above): lost == FULL, every PMU identity holds, 0 non-0x01 status, 0 late records, and 0 tag failures over 4.8 × 10⁸ tag-checked memmoves.
  • With mm65536 the occupancy register reads L − 24 (104 at L = 128, 126 at L = 150). Losses start at the first L where it reaches 128: L = 153-154 for N = 1, 152-153 for N = 8.
  • The losses grow as ≈ (L − 152.5) per 20 ms timeout cycle (for example, 4,750 per 2 s at L = 200). This is the same for N = 1, 4 and 8.
  • With noop and mm4096 the poller keeps the device-side backlog small (occupancy ≤ 21 up to L = 200), and losses appear only at L = 400.

Verdicts (H0 sub-claims)

  1. "Every MOVDIR64B write from any thread reaches the device" (no loss while not full): supported.
    • Evidence (1), direct count: R1 had 3.21 × 10⁹ descriptors from 1-8 cores, same line and different lines, including cross-socket, with 0 timeouts, 0 late records and PMU FULL = 0. Thread count and same-address contention had no effect (0 in every cell).
    • Evidence (2), device counter: SUCCESS + FULL = writes + Drains in every one of the 2,612 rows. Every write was counted by the device as either accepted or dropped-full.
    • Upper bound on concurrency-caused loss: < 9.4 × 10⁻¹⁰ per descriptor (95%) on an almost empty WQ, and < 2.8 × 10⁻⁹ for R3 L ≤ 140.
  2. "Lost if and only if it arrives while the WQ is full": supported.
    • Evidence (1), counts against the device's own drop counter: missing == EV_DWQ_FULL in all 2,160 R2 bursts (literally in the 1,080 rerun bursts; in the first set after counting 3 dropped Drains), and in all R3 rows.
    • Evidence (2), register reads: after every loss phase the probe's SWERROR read decodes to 0x53 (WQ full) on WQ 0. That is 1,295 of 1,295 loss rows: 660 in the R2 rerun, plus 635 in the first R2 set and R3 together. The sticky copy only shows that a full-drop happened, so this is supporting evidence. The sampled occupancy reached 128 in all but 5 loss bursts (125-126 there). In R3 the onset of loss tracks the occupancy register reaching 128, within one L step for N = 1 and N = 8.
    • Evidence (3), time structure: losses co-occur across threads in shared time windows, and the single-thread control loses the same way.
    • The R3 prediction "losses only for L > 140" is supported. The actual onset is L ≈ 153 (152-154), because the occupancy register reads L − 24 at these rates: ~24 in-flight descriptors are not in the WQ. Losses began only once occupancy reached 128.
  3. "Every accepted descriptor is intact" (integrity): supported.
    • Evidence (1), byte comparison: 8.7 × 10⁸ mm64 in R1 and 7.2 × 10⁶ mm64/mm4096 in R2 (64 B tag + full content), plus 4.8 × 10⁸ mm4096/mm65536 in R3 (tag only). 0 integrity failures, 0 destinations written without a record, and only status 0x01 ever seen.
    • Evidence (2), counters: op_noop / op_memmove = accepted descriptors of that type, and cpl_err = 0, in every row. No merged descriptor (it would make FULL < missing) and no corrupted descriptor (it would give a non-0x01 status or a wrong destination) was seen.

Anomalies and caveats (reported plainly)

  • No anomaly against H0 was found. There was no loss in R1, no FULL ≠ missing beyond the three dropped Drains explained above (which the rerun removed), and no integrity failure.
  • disp_wq (EV_NUM_DESC_DISPATCH_WQ) does not equal SUCCESS outside calibration. It is −1 to −20 in 12 of 72 R1 rows, +3 (constant) in R2 mm4096 bursts, and down to −29,776 in R3 noop at L ≥ 150. The semantics of this counter are not understood. It is not used for any verdict: the record counts equal SUCCESS − Drains exactly in every row.
  • Timestamp order is not arrival order. The per-write TSC stamps record instruction issue, which runs ahead of portal arrival by the store-buffer drain. Example: one first-set n8 mm4096 burst (…072944Z-AB-n8-r2, rep 0 iter 7, start skew 42 µs) shows only 59 writes stamped before its first loss, and cpu12's index 0 was lost. The stamp-based global_writes_before_first_loss therefore cannot support a strict "≥ 140 accepted before the first loss" inference. It does not contradict the direct FULL, occupancy and accounting evidence.
  • R2 stamps: the R2 burst loop takes one rdtsc per write. Per-thread ns/write stayed at 104-111 on node 0 (n1-n8 noop/mm64), the same as the uninstrumented cadence in w2xport.md (~106-110 ns at 2.2 GHz). So the stamps did not visibly slow the maximum-rate workload.
  • Occupancy is sampled (about one read per µs), so short full intervals can be missed. In 5 R2 loss bursts (2 first-set n4 noop-offsets, 3 rerun n4 mm64-same) the sampled max was 125-126; FULL still equaled missing.
  • Timeout: 20 ms. No R1 slot ever timed out and no late record appeared, so the choice does not affect R1. In R3 the loss counts scale with 1/timeout, and FULL equality shows that no timed-out descriptor was merely slow.
  • PMU: 8 events, time_running == time_enabled in all rows (never multiplexed). The PMU is device-wide, and only this process submitted (both sides leased).
  • Untested:
    • shared WQs / ENQCMD;
    • IAA and dsa2;
    • more than 8 submitting cores, or SMT siblings submitting together;
    • other WQ sizes or engine counts;
    • batch descriptors;
    • block_on_fault = 1;
    • more than 2 + 2 cross-socket cores;
    • high-rate multi-core writes while the WQ sits at 120-127. R3 mm65536 reached that occupancy only at ~1 M descriptors/s on the same address; R1 ran at up to 67 M/s with an almost empty WQ.

Side observations

  • Same address vs offsets in R2: same-line bursts lose less than offset bursts:

    • n4 noop: 0 vs 567;
    • n8 noop: 75 k vs 91 k;
    • n8 mm64: 122 k vs 152 k.

    The per-thread ns/write is the same (≈ 104-111). [INFERENCE] Writes from several cores to one line reach the device somewhat more spread out. This is not a loss mechanism: FULL equals missing in both cases.

  • The device runs noops at ≥ 67 M/s (8 cores, flow mode), so an empty WQ never fills with noops from ≤ 4 cores in flow mode.

  • x4 noop/mm64 bursts lost 0 in the first set and 10-16 k in the rerun, at the same ns/write. Run-to-run variation; FULL = missing in both.
