arb_ord: arbitration order of concurrent core writes to a single DWQ portal (E3)

Probe: dsa-lab/src/bin/arb_ord.rs. Run dirs are relative to dsa-lab-runs/.

Question (E3)

When multiple CPU cores concurrently write MOVDIR64B descriptors to the same dedicated workqueue (DWQ) portal address (portal+0), in what order do their writes arrive at the device?

On Intel DSA, Spec 3.9 guarantees:

"Descriptors submitted to the same WQ using the same portal address are guaranteed to be executed in the order they are received by the device, provided the workqueue is assigned to a group containing exactly one engine."

With dsa-config/1-engine.conf (one engine, one DWQ of size 128), execution order on the single engine is strictly identical to device arrival order. By submitting tagged descriptors from $N$ cores and observing their completion order, we directly observe the hardware arbitration order across cores.

Hypotheses and Predictions (written before running)

  • H1 (Issue-time FIFO): Writes arrive at the device in the exact order the CPU instructions were issued (t_issue).
    • Prediction: Minimal or zero inversions between core issue timestamp order and observed completion order.
  • H2 (Per-source Round-Robin under load): When multiple cores push the portal simultaneously, the mesh/IIO ingress arbiter arbitrates among requesting sources in round-robin fashion.
    • Prediction: A fixed interleave (e.g., $A \to B \to C \to D \to A \dots$) under load. Run lengths per core equal exactly 1.0. High fraction of strict round-robin cycles. Transition matrix shows off-diagonal cyclic permutation $T[i][(i+1)%N] \approx 1.0$ and $T[i][i] \approx 0$.
  • H3 (FIFO with per-core buffering / clumping): Hardware buffers at the core, mesh stop, or IIO ingress drain bursts from one core before switching to another.
    • Prediction: Clumping of writes from the same core (run lengths > 1). Transition matrix has positive diagonal $T[i][i] > 0$. Low fraction of strict round-robin cycles.
  • H4 (Near cores systematically earlier): Cores physically closer to the IIO block on the 2D mesh have shorter transit latency and win initial races when released simultaneously.
    • Prediction: In simultaneous burst release, near cores (e.g., cpu2) systematically appear in earlier arrival positions than far cores (e.g., cpu16).
  • H5 (Polling resolution boundary): Completion visibility order accurately reflects device execution order if and only if descriptor execution time exceeds cross-core cache-invalidation and polling jitter.
    • Prediction: 1-core control has 0 inversions for all descriptor sizes. For multi-core, larger payloads (e.g., 1 KiB, 4 KiB) provide ~35-140 ns spacing per completion, eliminating polling ties and visibility inversions compared to minimal 64 B descriptors.

Method & Setup

  • Device config: dsa-config/1-engine.conf: wq0.0 (dedicated mode, size 128) attached to engine0.0. All writes go to portal + 0 (no offset rotation, strictly preserving Spec 3.9 arrival ordering).
  • Cores & Layout: sub-threads pinned to distinct physical cores on NUMA node 0 (local to dsa0):
    • $N=1$: cpu2 (control)
    • $N=2$: {cpu2, cpu4}
    • $N=4$: {cpu2, cpu4, cpu6, cpu8}
    • $N=8$: {cpu2, cpu4, cpu6, cpu8, cpu10, cpu12, cpu14, cpu16}
    • Main coordinator pinned to cpu20.
    • Heaters: 8 L2 heaters on node 0 (8x1@0, excluding worker and coordinator CPUs), holding mesh frequency at ~2.19 GHz.
  • Descriptor tagging & verification: Each descriptor is a memmove carrying a 64-byte tag in its source: tag(core, seq) containing magic 0x4152424f, core ID, sequence number, mixing hash, and checksum. Every completed destination is byte-verified against expected tag and content, and zeroed before reuse. Every completion record status byte is checked (must be 0x01).
  • Accounting & Non-dropping guarantee: Total burst size per trial is bounded: $N \times K = 96 \le 120 < 128$. In every trial, zero descriptors are lost: PMU dwq_success = $N \times K$, dwq_full = 0.
  • Visibility vs Execution Order Detector: Each core polls its own page-aligned completion records. Because the device executes on a single engine, descriptors for any given core complete strictly in sequence ($0, 1, \dots, K-1$). At first sight of status != 0, the polling loop stamps the invariant TSC (rdtsc_relaxed()). All completed items across cores are sorted by t_seen.

2. Polling Resolution & Payload Sensitivity

Across multiple cores, completion records are written to different memory addresses and polled by different cores. Cross-core cache invalidation transit across the mesh introduces ~10–20 ns of observation jitter.

When the descriptor execution time is shorter than this jitter, the order in which cores observe completions can swap, creating artificial clumping (inflating run lengths and diagonal transition probabilities).

Quantification of Polling Resolution:

  • At 64 B and 1024 B, the single engine completes descriptors every ~20–35 ns. Nearly half of the completions fall within the cross-core polling jitter window (< 10 ns), causing 35–147 ties and artificial reorderings.
  • At 4096 B, single-engine DMA transfer time (~136 ns at ~30 GB/s) exceeds the cross-core coherency and polling jitter by an order of magnitude. Ties vanish completely (0 ties), sub-10 ns gaps drop to 0.1%, and the true device execution order is resolved cleanly.
  • Therefore, 4096 B memmove is the authoritative detector for hardware arbitration order.

5. Physical Mechanism: Why Per-Source Interleaving Emerges

The observed progression with $N$:

  1. Run length per core:
    • $N=1$: 64.0
    • $N=2$: 1.56
    • $N=4$: 1.01
    • $N=8$: 1.0012
  2. Self-transition probability $T[i][i]$:
    • $N=1$: 100%
    • $N=2$: 36.4%
    • $N=4$: 1.26%
    • $N=8$: 0.12%
  3. Off-diagonal transition probability:
    • $N=4$: ~33% uniform to any other core ($1/(4-1)$)
    • $N=8$: ~14.3% uniform to any other core ($1/(7)$)

Mechanism [INFERENCE]: This behavior is directly driven by the core-side store buffer constraint established in earlier studies (Q1/Q5/W2/W3):

  • A physical core writing to the same 64-byte portal line can only emit one MOVDIR64B every ~106–110 ns (the same-line store buffer drain latency).
  • Under push load with $N=8$ cores, each core emits one write per ~110 ns. The aggregate arrival rate at the portal is 8 writes per ~110 ns, or one write every ~13.7 ns.
  • After core $i$ issues its write, its store buffer is blocked from issuing another write to portal+0 for the next ~110 ns.
  • During that ~110 ns interval, all other 7 cores release their pending writes.
  • Therefore, Core $i$ CANNOT follow itself ($T[i][i] \approx 0$). The device necessarily receives an interleaved stream where each core gets exactly one slot per ~110 ns window.
  • When $N=2$, the inter-arrival gap between the two cores is ~55 ns. Small pipeline or barrier jitter occasionally allows one core's 110 ns window to elapse before the other core submits, permitting short runs of length 2 (self-transition 36%).
  • At $N=8$, with 7 other cores pushing, the 110 ns window is completely filled, driving the self-transition probability to near zero (0.12%) and run length to 1.001.

  • The mean ranks across the entire burst are tightly clustered within [44.4, 49.2] around the mid-point 47.5. No core is starved, and no core systematically dominates the burst.
  • In initial first-arrival races ($s_0$ of each trial): Across runs, the core that wins $s_0$ varies with barrier release skew (e.g. cpu4 won in r1, cpu16 won in r2/t200). Once the burst enters steady state, all 8 cores achieve equal throughput (~1 write per 110 ns per core).

7. Verdicts against Predictions

  1. H1 (Issue-time FIFO): Partially supported.
    • Over all multi-core runs, 90%–99% of descriptor pairs preserve CPU issue timestamp order (inversion rate 1.0%–2.2% at $N=2$, 2.7%–4.0% at $N=4$, and ~10.5% at $N=8$).
    • The ~10% inversions at $N=8$ reflect sub-15 ns mesh transit and arbitration jitter among cores issuing concurrently at the deadline.
  2. H2 (Per-source Round-Robin under load): Supported with qualification.
    • Supported: under push load ($N=8$), the stream is strictly interleaved per source: run length = 1.0012, self-transition $T[i][i] = 0.12%$, and 74.0% of all 8-blocks contain all 8 cores.
    • Qualified: the interleave is a dynamic permutation rather than a static, hard-coded round-robin sequence (fixed_cycle_fraction = 0.0). Transitions from core $i$ to any other core $j \neq i$ are uniform (~14.3% each).
  3. H3 (FIFO with per-core buffering / clumping): Ruled out.
    • Mean run length at $N=8$ is 1.0012 (99.88% of runs have length 1). Hardware does not buffer multiple writes from one core while delaying others.
  4. H4 (Near cores systematically earlier): Ruled out for steady state; qualified for burst onset.
    • Across the burst, mean arrival ranks are uniformly distributed across all cores (44.4–49.2). Mesh proximity to IIO does not grant preferential throughput.
    • Burst onset ($s_0$) is governed by thread barrier release skew rather than static mesh distance.
  5. H5 (Polling resolution boundary): Supported.
    • 1-core control is 100% in order (0 inversions in 19,200 descriptors).
    • Fast descriptors (64 B, execution ~20 ns) produce 47% sub-10 ns completion gaps and 120–150 ties due to cross-core polling jitter.
    • 4 KiB descriptors (execution ~136 ns) eliminate ties (0 ties) and resolve true hardware arrival order with < 0.1% sub-10 ns gaps.

8. Alternative Detector Assessment

The prompt suggested an optional alternative detector: each descriptor copies an 8-byte sequence word into a shared log.

  • Hardware limitation: Intel DSA does not provide atomic fetch-and-add or increment operations in descriptor execution. Multiple descriptors writing to a shared log cannot dynamically allocate monotonic indices.
  • A static single-word copy overwrites earlier values, capturing only the final write.
  • A chained data copy (descriptor $i$ copying to slot $i+1$) was tested in W3-2 and failed because the engine pipelines memory reads ahead of writes, triggering read-before-write hazards.
  • In contrast, the per-core completion record poller on 4 KiB memmoves provides 0 ties, 0 drops, and 100% verified integrity, fully validated on the 1-core control.
