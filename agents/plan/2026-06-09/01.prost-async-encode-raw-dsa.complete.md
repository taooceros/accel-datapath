# Async Prost encode_raw DSA execution plan

Status: complete

## Goal

Implement the opt-in async Prost field-copy path described in `docs/plan/2026-06-09/03.prost-async-encode-raw-dsa.complete.md` without changing ordinary `prost::Message::encode`, `encode_raw`, `tonic-prost`, or Tonic framing.

## Scope completed

- Added a hardware-neutral `AsyncEncodeSink` surface in Prost.
- Added `Message::encode_raw_async` beside `encode_raw` with a CPU default.
- Generated async encode bodies in `prost-derive` that preserve field order and route `string` / `bytes` payload copies through async helpers.
- Kept protobuf structure, keys, lengths, scalar fields, map entry structure, and field order on the CPU.
- Added an opt-in DSA Prost codec/encoder/decoder in `tonic-dsa-bytes-async`.
- Added CPU parity, pending/resume, and hardware smoke coverage.

## Execution notes

- Tonic's owned `Encoder::Encode` future boundary was sufficient; no changes were made to Tonic codec framing/body state.
- DSA device, descriptor, page-fault retry, drop-drain, and no-fallback-after-selection policy stayed inside `tonic-dsa-bytes-async`.
- Generated async encoding is deliberately sequential: a selected payload copy is awaited before later fields are encoded.
- Non-accelerable scalar/map/oneof paths deliberately delegate async encoding to existing synchronous encode helpers instead of duplicating small-type encode logic.
- The DSA Prost encoder maps selected DSA submission/completion failures to `tonic::Status` encode errors instead of copying the payload on the CPU.
